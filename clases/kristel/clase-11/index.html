¿Qué significa persistir?

La diferencia entre tener un dato en memoria y conservarlo.

Persistencia significa que el estado de los datos puede sobrevivir al ciclo de vida de la ejecución del programa.

Memoria de la aplicación

Un ArrayList<Estudiante> existe mientras el programa mantiene esa estructura accesible.

Si cerramos la aplicación: ese estado desaparece.

Almacenamiento persistente

Un archivo o una base de datos conserva información para recuperarla después.

Si cerramos la aplicación: los datos pueden seguir allí.

¿Por qué no basta con guardar en archivos?

TXT, XML y serialización siguen siendo persistencia, pero resuelven problemas diferentes.

Archivo

La aplicación normalmente decide cómo leer, buscar, modificar y mantener la estructura.

Base de datos

El SABD administra estructuras, restricciones, consultas, concurrencia, seguridad y recuperación.

Cuando crece el sistema

Buscar, relacionar, validar y modificar miles o millones de registros requiere capacidades especializadas.

Idea clave

La base de datos no reemplaza a la aplicación: ambas colaboran y tienen responsabilidades distintas.

¿Qué es un SABD?

Sistema Administrador de Bases de Datos.

Base de datos = los datos organizados.

SABD / DBMS = el software que permite definir, almacenar, consultar, modificar y administrar esos datos. 

-- Esto es lo que un SABD resuelve por ti
SELECT carnet, nombre
FROM   estudiante
WHERE  id_carrera = 3
ORDER BY nombre;

Ejemplos

  • MySQL
  • PostgreSQL
  • Oracle Database
  • SQL Server

No confundir

IntelliJ Database Tools no es el SABD. Es una herramienta cliente/IDE que ayuda a conectarse y trabajar con un SABD.

Las responsabilidades del SABD

No es simplemente un lugar donde “se guardan tablas”.

Definición

Permite definir estructuras como bases de datos, tablas, columnas, claves y restricciones.

Manipulación

Permite insertar, consultar, modificar y eliminar datos mediante SQL.

Integridad

Puede impedir datos inválidos mediante restricciones y relaciones.

Acceso

Controla quién puede acceder y qué operaciones puede realizar.

Concurrencia

Permite que múltiples usuarios/procesos trabajen sobre los datos con reglas de consistencia.

Persistencia

Se encarga del almacenamiento y recuperación de la información.

La idea de un modelo de datos

Antes de crear tablas, necesitamos una forma de representar la realidad.

Realidad

Estudiantes, cursos, matrículas, profesores…

Modelo

Entidades, atributos, relaciones y reglas.

Implementación

Tablas, columnas, claves, índices y restricciones.

Diseñar una BD es modelar. No empezamos escribiendo CREATE TABLE; primero decidimos qué información existe y cómo se relaciona.

Modelo relacional: la idea central

El modelo relacional representa los datos mediante relaciones, que en la implementación cotidiana vemos como tablas.

Concepto En una tabla Ejemplo
Relación Tabla ESTUDIANTE
Atributo Columna carnet, nombre
Tupla Fila/registro 20260123, Ana…
Dominio Conjunto de valores permitidos nota: números válidos

CREATE TABLE estudiante (

  nombre  VARCHAR(60)  NOT NULL,

Una tabla no es “solo una lista de objetos”

El modelo relacional tiene reglas propias.

Columnas

Describen qué propiedades almacena cada registro.

Filas

Representan ocurrencias concretas de los datos.

Orden

El orden físico de filas y columnas no define el significado de la relación.

Restricciones

Las claves, NOT NULL, UNIQUE, CHECK y FOREIGN KEY ayudan a proteger la integridad.

Claves: ¿cómo identificamos un registro?

Las claves son fundamentales para poder distinguir y relacionar filas.

Clave primaria (PK)

Identifica de forma única cada fila de una tabla. Una tabla tiene una sola PK, aunque puede ser compuesta.

Clave candidata

Una combinación mínima de atributos que podría identificar de forma única una fila.

Clave alternativa

Una clave candidata que no fue elegida como PK.

Clave foránea (FK)

Atributo(s) que referencia(n) una clave de otra tabla para representar una relación.

Ejemplo de PK y FK

Veamos la relación entre estudiantes y carreras.

CARRERA (padre)

CREATE TABLE carrera (
  id_carrera INT PRIMARY KEY,
  nombre     VARCHAR(60) NOT NULL
);

La PK de CARRERA es referenciada desde ESTUDIANTE.

ESTUDIANTE (hija)

CREATE TABLE estudiante (
  carnet     VARCHAR(10) PRIMARY KEY,
  nombre     VARCHAR(60) NOT NULL,
  id_carrera INT,
  FOREIGN KEY (id_carrera)
    REFERENCES carrera(id_carrera)
);

Cada estudiante tiene una carrera asociada.

Resultado: una carrera puede estar asociada a muchos estudiantes; cada estudiante referencia una carrera.

Integridad: la base de datos también protege reglas

No queremos que cualquier combinación de valores sea aceptada.

Integridad de entidad

La PK identifica filas y no debe quedar indefinida.

Integridad referencial

Una FK debe respetar la relación con la tabla referenciada según las reglas definidas.

Integridad de dominio

Los valores deben pertenecer a dominios/tipos y restricciones válidas.

Unicidad

UNIQUE evita duplicados donde el negocio exige valores únicos. 

-- Las reglas del negocio declaradas en la propia tabla
CREATE TABLE estudiante (
  carnet VARCHAR(10) PRIMARY KEY,    -- entidad
  email  VARCHAR(80) UNIQUE NOT NULL, -- unicidad
  nota   DECIMAL(4,2) CHECK (nota BETWEEN 0 AND 100)
);

Relaciones y cardinalidad

La relación entre tablas debe expresar cómo se comporta la realidad.

1 : 1

Una persona ↔ un pasaporte, según el modelo del sistema.

1 : N

Una carrera → muchos estudiantes.

N : M

Muchos estudiantes ↔ muchos cursos. Normalmente requiere una tabla intermedia. 

-- 1 : N  → la FK vive en el lado "muchos"
ALTER TABLE estudiante
  ADD FOREIGN KEY (id_carrera) REFERENCES carrera(id_carrera);

-- N : M  → tabla intermedia con clave compuesta
CREATE TABLE matricula (
  carnet   VARCHAR(10),
  id_curso INT,
  PRIMARY KEY (carnet, id_curso)
);

Pregunta para el diseño: “¿Cuántos registros de un lado pueden asociarse con cuántos del otro?”

¿Por qué normalizamos?

La normalización busca organizar los datos para reducir redundancia y evitar anomalías.

Anomalía de inserción

No puedo registrar un dato nuevo sin inventar otro dato que todavía no existe.

Anomalía de actualización

Un mismo dato está repetido en varias filas y debo actualizarlo en todas.

Anomalía de eliminación

Al eliminar una fila termino perdiendo información que conceptualmente quería conservar.

Normalizar no significa “hacer muchas tablas porque sí”. Significa separar dependencias de datos de forma razonada.

Primera Forma Normal — 1FN

Empezamos por una regla básica: los atributos deben ser atómicos dentro del modelo elegido.

✗ No cumple 1FN

INSERT INTO estudiante VALUES
  (1, 'Ana', '8888-1111, 8888-2222');
-- dos teléfonos dentro de una sola celda

Una celda contiene varios valores del mismo atributo.

✓ Sí cumple 1FN

CREATE TABLE telefono (
  id_telefono   INT PRIMARY KEY,
  id_estudiante INT,
  telefono      VARCHAR(20) NOT NULL
);

Cada valor queda representado de manera individual.

Segunda Forma Normal — 2FN

Primero debe cumplirse 1FN; después eliminamos dependencias parciales respecto de una clave compuesta.

Imagine una tabla INSCRIPCION con PK compuesta (estudiante_id, curso_id).

estudiante_id curso_id nombre_estudiante nombre_curso nota
10 5 Ana Programación III 92

Problema: nombre_estudiante depende solo de estudiante_id, y nombre_curso solo de curso_id. No dependen de toda la clave compuesta.

Solución conceptual: separar ESTUDIANTE, CURSO e INSCRIPCION. 

-- Solución: cada tabla depende de SU propia clave
CREATE TABLE curso (
  id_curso INT PRIMARY KEY,
  nombre   VARCHAR(60) NOT NULL
);
CREATE TABLE inscripcion (
  carnet   VARCHAR(10),
  id_curso INT,
  nota     DECIMAL(4,2),
  PRIMARY KEY (carnet, id_curso)
);

Tercera Forma Normal — 3FN

Primero 2FN; después evitamos dependencias transitivas entre atributos no clave. 

-- ✗ 3FN violada: nombre_carrera depende de id_carrera, no de la PK
CREATE TABLE estudiante (
  id_estudiante  INT PRIMARY KEY,
  nombre         VARCHAR(60),
  id_carrera     INT,
  nombre_carrera VARCHAR(60)  -- redundante
);

Si id_estudiante → id_carrera y id_carrera → nombre_carrera, entonces el nombre de la carrera depende transitivamente del estudiante.

ESTUDIANTE

id_estudiante, nombre, id_carrera

CARRERA

id_carrera, nombre_carrera

Normalización: el ejemplo completo

Veamos cómo una mala tabla puede revelar el problema.

estudiante carrera curso profesor nota
Ana Sistemas Prog III Luis 92
Carlos Sistemas Prog III Luis 88
Redundancia:
Sistemas y Prog III se repiten.
Actualización:
si cambia el profesor, hay varias filas.
Diseño:
separamos entidades y relaciones. 
-- El diseño corregido: 4 tablas, sin redundancia
CREATE TABLE carrera    (id_carrera INT PRIMARY KEY, nombre VARCHAR(60));
CREATE TABLE curso      (id_curso INT PRIMARY KEY, nombre VARCHAR(60), id_profesor INT);
CREATE TABLE estudiante (carnet VARCHAR(10) PRIMARY KEY, nombre VARCHAR(60), id_carrera INT);
CREATE TABLE matricula  (carnet VARCHAR(10), id_curso INT, nota DECIMAL(4,2),
                         PRIMARY KEY (carnet, id_curso));

Modelo de objetos vs. modelo relacional

Aquí aparece una de las ideas más importantes de todo el tema.

Orientación a objetos Relacional

Atributos Columnas

JDBC · Java Database Connectivity

¿Para qué sirve?

Es la API estándar de Java para conectarse a una base de datos y ejecutar SQL desde el programa.

¿Por qué lo usamos?

Porque el mismo código Java sirve para MySQL, PostgreSQL u Oracle: solo cambia el driver y la URL.

¿Cómo se usa?

En cuatro pasos: conexión, sentencia, ejecución y cierre. Lo vemos en las siguientes diapositivas.

La arquitectura que veremos en práctica

No basta con saber SQL: debemos entender quién hace cada cosa.

Java

→

↓

Conexión → SQL → SABD → resultado

La aplicación no “entra mágicamente” a una tabla: hay una cadena de acceso. 

// El driver MySQL Connector/J se registra solo (JDBC 4+)
Connection cn = DriverManager.getConnection(url, user, pwd);   // 1. conexión
PreparedStatement ps = cn.prepareStatement(sql);          // 2. sentencia
ps.setInt(1, idCarrera);                                     // 3. parámetro
ResultSet rs = ps.executeQuery();                          // 4. resultado

El ciclo JDBC completo

Conectar, preparar, ejecutar y cerrar: siempre en ese orden. 

String url = "jdbc:mysql://localhost:3306/academia";
String sql = "SELECT carnet, nombre FROM estudiante WHERE id_carrera = ?";

try (Connection cn = DriverManager.getConnection(url, user, pwd);
     PreparedStatement ps = cn.prepareStatement(sql)) {

    ps.setInt(1, 3);                                  // 1. enlazar el parámetro
    try (ResultSet rs = ps.executeQuery()) {              // 2. ejecutar
        while (rs.next()) {                          // 3. recorrer las filas
            System.out.println(rs.getString("carnet"));
        }
    }
}   // 4. try-with-resources cierra rs, ps y cn solo

executeQuery()

Devuelve un ResultSet. Se usa con SELECT.

executeUpdate()

Devuelve las filas afectadas (int). Se usa con INSERT, UPDATE y DELETE.

Cierre de recursos

try-with-resources cierra ResultSet, PreparedStatement y Connection sola, incluso si hay excepción.

PreparedStatement: la defensa contra la inyección SQL

El dato del usuario nunca se concatena al texto del SQL.

✗ Concatenar el dato (Statement)

String sql = "SELECT * FROM estudiante "
           + "WHERE carnet = '" + carnet + "'";
// Si carnet vale  x' OR '1'='1
// el SQL devuelve TODA la tabla.

El dato se confunde con el código SQL: eso es la inyección.

✓ Usar marcadores (PreparedStatement)

String sql = "SELECT * FROM estudiante "
           + "WHERE carnet = ?";

PreparedStatement ps = cn.prepareStatement(sql);
ps.setString(1, carnet);  // los índices empiezan en 1

El valor viaja aparte: se trata siempre como dato, nunca como código.

¿Para qué sirve?

Para ejecutar SQL con valores variables sin que esos valores se mezclen con el código de la consulta.

¿Por qué lo usamos?

Es la defensa contra la inyección SQL, y el SABD reutiliza la consulta ya preparada.

¿Cómo se usa?

? en el SQL → prepareStatement(sql) → setXxx(n, valor) → executeQuery() o executeUpdate().

Regla práctica: si el SQL lleva cualquier valor que viene del usuario, usá ?. Statement solo cuando el SQL es completamente fijo.

Conexión, sesión y fuente de datos

Tres palabras que vamos a usar mucho.

Conexión

Canal lógico mediante el cual la aplicación/cliente se comunica con el servidor de base de datos.

Sesión

Contexto asociado a una conexión en el que se ejecutan operaciones y se mantiene determinado estado.

Data Source

En IntelliJ, es una configuración que almacena datos necesarios para establecer la conexión: host, puerto, BD, driver, etc.

Conexión local vs. remota

La ubicación del SABD no cambia el modelo relacional, pero sí cambia la infraestructura de comunicación.

Local

La aplicación y el servidor de BD pueden estar en la misma computadora. 

String url = "jdbc:mysql://localhost:3306/academia";

Remota

La aplicación/IDE se comunica por red con un servidor distinto. 

String url = "jdbc:mysql://aiven.io:3306/academia?ssl=true";

Una conexión remota agrega preocupaciones de red, autenticación, permisos, firewall, SSL/SSH y disponibilidad.

Conexiones dependientes de la plataforma y de sistema

El programa menciona esta distinción dentro de la administración de conexiones.

Dependiente de la plataforma

La forma concreta de conectarse puede depender de características del sistema operativo, rutas, sockets, drivers o mecanismos disponibles.

Idea: la infraestructura de conexión puede no ser idéntica en Windows, Linux o macOS.

Conexión de sistema

El acceso puede apoyarse en configuraciones administradas por el sistema/entorno, en lugar de que toda la información sea construida manualmente por cada aplicación.

Idea: separar la configuración del código puede facilitar administración.

Nota docente: esta sesión introduce el concepto; la configuración concreta se trabajará en laboratorio cuando veamos las herramientas de IntelliJ.

DDL y DML: dos familias que debemos distinguir

El programa dice “DLM”, pero la terminología estándar que usaremos es DDL y DML.

DDL · Data Definition Language

Define o modifica la estructura de los objetos de la base de datos. 

CREATE TABLE estudiante (
  carnet VARCHAR(10) PRIMARY KEY,
  nombre VARCHAR(60)
);
ALTER TABLE estudiante
  ADD COLUMN email VARCHAR(80);
DROP TABLE estudiante_borrador;

DML · Data Manipulation Language

Trabaja con los datos almacenados.

INSERT INTO estudiante VALUES (1, 'Ana', 3);
SELECT * FROM estudiante WHERE id_carrera = 3;
UPDATE estudiante SET nombre = 'Ana María';
DELETE FROM estudiante WHERE carnet = 1;

Nota: el programa del curso literalmente escribe “DLM”; para la práctica y la bibliografía técnica trabajaremos con la nomenclatura habitual DDL/DML.

CRUD e IMEC: dos formas de hablar de lo mismo

CRUD es una forma conceptual de describir las operaciones básicas sobre datos.

CRUD IMEC SQL habitual Objetivo
Create Insertar INSERT Crear datos
Read Consultar SELECT Leer datos
Update Modificar UPDATE Cambiar datos
Delete Eliminar DELETE Eliminar datos

CRUD describe qué quiere hacer la aplicación; SQL expresa cómo solicitarlo al SABD. 

INSERT INTO estudiante (carnet, nombre, id_carrera)
       VALUES ('20260123', 'Ana', 3);            -- Create
SELECT * FROM estudiante WHERE carnet = '20260123';   -- Read
UPDATE estudiante SET id_carrera = 5 WHERE carnet = '20260123';  -- Update
DELETE FROM estudiante WHERE carnet = '20260123';      -- Delete

¿Qué significa mapear datos?

Traducir estructuras entre el mundo de objetos y el mundo relacional.

Objeto Java

public class Estudiante {
  private int id;
  private String nombre;
  private Carrera carrera;  // objeto
}

Registro relacional

CREATE TABLE estudiante (
  id         INT PRIMARY KEY,
  nombre     VARCHAR(60),
  carrera_id INT              -- FK
);

Mapear implica decidir cómo cada atributo, relación e identidad del objeto se representa en columnas, claves y tablas.

Del ResultSet al objeto Java

El mapeo, en código: cada columna se convierte en un atributo del objeto. 

private Estudiante mapear(ResultSet rs) throws SQLException {
    Estudiante e = new Estudiante();
    e.setCarnet(rs.getString("carnet"));
    e.setNombre(rs.getString("nombre"));
    e.setCarreraId(rs.getInt("carrera_id"));  // la FK se vuelve atributo
    return e;
}

No es el objeto

El ResultSet es un cursor sobre las filas que devolvió el SELECT, no un objeto de negocio.

El DAO traduce

Nadie más que la capa de datos sabe qué columna corresponde a qué atributo.

Una fila, un objeto

Cada rs.next() avanza una fila y se construye un objeto nuevo para agregarlo a la lista.

¿Y las listas y relaciones?

Una colección dentro de un objeto no cabe literalmente dentro de una columna relacional normal.

Java

class Estudiante {
  List<Curso> cursos;
}

Un objeto contiene una colección de otros objetos.

Relacional

ESTUDIANTE
CURSO
MATRICULA

La relación muchos-a-muchos suele representarse mediante una tabla intermedia.

Este es uno de los motivos por los que el mapeo es una decisión de diseño, no una simple copia de atributos.

Patrones de acceso a datos

El programa cierra este bloque con patrones: formas reutilizables de organizar la interacción con la persistencia.

DAO

Encapsula operaciones de acceso a datos para una fuente o entidad. El resto de la aplicación no necesita conocer todos los detalles de SQL.

Repository

Presenta una abstracción orientada al dominio para recuperar y persistir objetos/agregados.

Service

Coordina casos de uso y reglas; normalmente no debería convertirse en una bolsa de SQL.

DTO

Transporta datos entre límites sin necesariamente exponer el objeto de dominio completo.

DAO vs. Repository

No son simplemente dos nombres intercambiables.

DAO

Suele pensarse desde la tecnología de persistencia:

  • consultar
  • insertar
  • actualizar
  • eliminar

Repository

Suele pensarse desde el modelo/dominio:

  • obtener entidades
  • buscar por criterios del dominio
  • guardar cambios
public interface EstudianteDAO {
    Estudiante buscarPorCarnet(String carnet) throws SQLException;
    List<Estudiante> listarTodos() throws SQLException;
    void guardar(Estudiante e) throws SQLException;
}

Para el curso: el DAO esconde el SQL y el Repository esconde el origen de los datos. Los dos separan la lógica de negocio del acceso a datos.
