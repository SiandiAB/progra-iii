Introducción

En laboratorios anteriores construimos aplicaciones Java con programación orientada a objetos y luego dimos el salto a las interfaces gráficas con Swing. En este laboratorio avanzamos un paso más: desarrollaremos una aplicación de escritorio más estructurada utilizando JavaFX, la tecnología moderna de interfaces de escritorio de Java.

El proyecto consiste en un sistema para gestionar una flota vehicular formada por distintos tipos de vehículos:

Vehículo ├── Vehículo de combustión ├── Vehículo eléctrico └── Vehículo pesado

El sistema permitirá operaciones como registrar, consultar, editar y eliminar vehículos (CRUD), así como reglas de negocio propias: iniciar rutas, finalizar rutas, gestionar mantenimiento y cargar mercancía.

Antes de construir la interfaz gráfica, desarrollaremos primero el modelo del sistema. Este orden no es accidental: seguiremos la arquitectura MVC (Model - View - Controller):

MODEL ↓ CONTROLLER ↓ VIEW
Importante: este laboratorio se realiza de forma individual y cubre el Model completo, los recursos (CSS + imágenes) y la configuración del proyecto. La construcción del Controller y de la View (con Scene Builder) se realizará posteriormente junto con la profesora durante la clase.
Objetivos del laboratorio:
  • Configurar un proyecto JavaFX utilizando IntelliJ IDEA, Maven y JDK 25.
  • Comprender la función de JavaFX dentro de una aplicación de escritorio.
  • Comprender la función de Scene Builder y del formato FXML.
  • Organizar correctamente el código Java (src/main/java) y los recursos (src/main/resources).
  • Aplicar herencia (jerarquía de vehículos), abstracción, polimorfismo y sobrescritura.
  • Crear e implementar interfaces y utilizar enumeraciones (enum).
  • Aplicar encapsulamiento y trabajar con colecciones (List, ArrayList, Queue, LinkedList).
  • Utilizar clases genéricas con límites (ColaMantenimiento<T extends Vehiculo>).
  • Implementar las operaciones básicas de un CRUD en memoria.
  • Separar las reglas de negocio de la futura interfaz gráfica.
  • Preparar los recursos: crear la hoja de estilos CSS y descargar los iconos de la interfaz.
  • Configurar IntelliJ para trabajar con Scene Builder.

1.2 ¿Qué es JavaFX?

JavaFX es una tecnología para desarrollar interfaces gráficas de escritorio en Java. Nos proporciona componentes como Label, Button, TextField, ComboBox, TableView, ImageView y Alert; y contenedores como VBox, HBox, GridPane, AnchorPane y BorderPane.

A diferencia de Swing, JavaFX permite separar con bastante claridad la lógica Java, el diseño de la interfaz y los estilos, utilizando tres tipos de archivo:

.java // la lógica del programa .fxml // la descripción de la interfaz (XML) .css // los estilos visuales (colores, fuentes, tamaños)
¿Por qué JavaFX y no Swing?

JavaFX es el sucesor moderno de Swing: permite separar el diseño visual (FXML + CSS) del código Java, tiene estilos mucho más flexibles y se integra con herramientas como Scene Builder para arrastrar y soltar componentes. Ambos sirven para lo mismo (GUI), pero JavaFX facilita el trabajo en equipo y el mantenimiento gracias a la separación Model - View - Controller.

1.3 ¿Qué es FXML?

FXML es un archivo que describe la interfaz gráfica utilizando XML. Por ejemplo, una ventana puede contener:

VBox ├── Label ├── TextField └── Button

Esa estructura puede almacenarse dentro de un archivo llamado flotaView.fxml. Esto nos evita crear manualmente toda la interfaz desde Java.

1.4 ¿Qué es Scene Builder?

Scene Builder es una herramienta visual para crear archivos FXML. En lugar de programar:

Button boton = new Button("Registrar");

podemos abrir Scene Builder y arrastrar visualmente un botón. La relación será:

SCENE BUILDER ↓ crea/modifica ↓ FXML ↓ JavaFX ↓ Controller

Scene Builder no reemplaza Java. Scene Builder diseña principalmente la View; el comportamiento sigue programándose en Java (en el Controller).

Paso 4: Conocer la Estructura Maven

4.1 La estructura que genera IntelliJ

Un proyecto Maven tendrá esta estructura general:

Estas dos carpetas tienen funciones diferentes, y es importante comprenderlas porque organizaremos todo nuestro proyecto alrededor de ellas.

4.2 src/main/java — el código Java

Aquí vive el código fuente Java. Por ejemplo:

Vehiculo.java Flota.java Main.java FlotaController.java // se creará en clase
4.3 src/main/resources — los recursos

Aquí viven recursos que utiliza la aplicación pero que no son clases Java. Por ejemplo: los archivos .fxml (vistas), las hojas de estilo .css y las imágenes e iconos.

¿Por qué separar código y recursos? Porque así la interfaz (FXML), los estilos (CSS) y las imágenes se pueden editar sin tocar el código Java, y Maven los empaqueta junto a las clases al compilar. Más adelante tendremos algo como:
resources/ └── lab/ └── flotavehicular/ ├── assets/ │ ├── css/ │ │ └── style.css │ └── images/ └── view/ └── flotaView.fxml

Paso 5: Revisar el pom.xml

5.1 ¿Para qué sirve el pom.xml?

Maven utiliza pom.xml para conocer la versión de Java, las librerías (dependencias), los plugins y la versión de JavaFX. Abre el archivo pom.xml que generó IntelliJ y revísalo.

Busca el plugin maven-compiler-plugin que generó IntelliJ. Este plugin es el que le indica a Maven con qué versión de Java compilar el proyecto (en nuestro caso, Java 25). En el pom suele venir comentado (como en tu proyecto):

<!-- <plugin> <groupId>org.apache.maven.plugins</groupId> <artifactId>maven-compiler-plugin</artifactId> <version>3.13.0</version> <configuration> <source>25</source> <target>25</target> </configuration> </plugin> -->
¿Qué hace el maven-compiler-plugin?

Le dice a Maven con qué versión de Java debe compilar el proyecto. Aquí <source>25</source> y <target>25</target> indican que compilamos para Java 25 (el mismo JDK 25 que configuramos en el Paso 3). Está comentado porque IntelliJ compila por su cuenta, pero es útil conocerlo. Además, en la sección <properties> del mismo pom se definen otras configuraciones del proyecto, como la codificación UTF-8 de los archivos.

5.2 Las dependencias de JavaFX

Dentro de <dependencies> verificamos que existan estas cuatro dependencias de JavaFX, todas en la versión 26.0.2:

<dependency> <groupId>org.openjfx</groupId> <artifactId>javafx-controls</artifactId> <version>26.0.2</version> </dependency> <dependency> <groupId>org.openjfx</groupId> <artifactId>javafx-fxml</artifactId> <version>26.0.2</version> </dependency> <dependency> <groupId>org.openjfx</groupId> <artifactId>javafx-web</artifactId> <version>26.0.2</version> </dependency> <dependency> <groupId>org.openjfx</groupId> <artifactId>javafx-swing</artifactId> <version>26.0.2</version> </dependency>
¿Para qué sirve javafx-controls?

Contiene los componentes gráficos: Button, Label, TextField, ComboBox, TableView, Alert, etc. Es la librería visual de JavaFX y la usaremos para construir la interfaz.

¿Para qué sirve javafx-fxml?

Permite utilizar FXMLLoader, la anotación @FXML y los archivos .fxml. Los necesitaremos al aplicar MVC.

¿Y javafx-web y javafx-swing?

Son módulos opcionales que la plantilla de IntelliJ incluye por defecto: javafx-web permite mostrar contenido web/HTML dentro de la aplicación y javafx-swing sirve para integrar componentes de Swing en JavaFX. Nuestra aplicación no los utiliza, pero quedan declarados en el pom por si algún día se necesitan.

Observa que la versión 26.0.2 aparece directamente en cada dependencia. Las dos primeras (controls y fxml) son las esenciales para nuestro proyecto; las otras dos vienen incluidas por la plantilla.

Paso 9: Preparar module-info.java

9.1 ¿Qué es un módulo?

Los proyectos Java modernos pueden utilizar el sistema de módulos (JPMS). Un archivo module-info.java declara qué librerías necesita nuestra aplicación (requires), qué paquetes expone (exports) y qué paquetes abre para reflexión (opens).

Si IntelliJ no lo creó automáticamente, crea el archivo module-info.java en src/main/java con este contenido:

module lab.flotavehicular { // Módulos de JavaFX incluidos en el proyecto requires javafx.controls; requires javafx.fxml; requires javafx.web; // Librerías adicionales seleccionadas al crear el proyecto (Paso 3.3) requires org.controlsfx.controls; requires com.dlsc.formsfx; requires net.synedra.validatorfx; requires org.kordamp.ikonli.javafx; requires org.kordamp.bootstrapfx.core; requires eu.hansolo.tilesfx; // Abre el paquete del controller para que JavaFX (FXML) acceda por reflexión opens lab.flotavehicular.controller to javafx.fxml; // Paquetes que exponemos al exterior exports lab.flotavehicular; exports lab.flotavehicular.model; }
¿Qué significa requires?

Declara los módulos que necesita nuestra aplicación. Aquí tenemos los tres de JavaFX (javafx.controls para los componentes gráficos, javafx.fxml para leer los archivos FXML y javafx.web para contenido web) y las librerías adicionales (Controlsfx, Formsfx, ValidatorFX, Ikonli, BootstrapFX y TilesFX) que IntelliJ agregó automáticamente porque las seleccionamos en el Paso 3.3.

¿Qué significa exports?

Permite que otro módulo acceda a las clases públicas de un paquete. Exportamos lab.flotavehicular (donde vive Main) y lab.flotavehicular.model.

¿Por qué usamos opens?

JavaFX utiliza reflexión para conectar el FXML con el Controller. Por eso necesitaremos opens lab.flotavehicular.controller to javafx.fxml;. Sin esta instrucción podríamos obtener errores como IllegalAccessException cuando FXMLLoader intente crear el Controller.

Posible aviso (warning): como el paquete controller aún está vacío, IntelliJ podría mostrar un aviso del estilo "package lab.flotavehicular.controller is empty". Es normal y esperado: el aviso desaparecerá cuando agreguemos la clase FlotaController en clase. No es un error.

// Indica que esta clase vive dentro del paquete lab.flotavehicular.model package lab.flotavehicular.model; // enum: los tres estados posibles de un vehículo public enum EstadoVehiculo { DISPONIBLE, EN_RUTA, TALLER }
11.2 ¿Por qué usar enum en lugar de String?

Podríamos almacenar String estado; y escribir "Disponible", "En Ruta" o "Taller"... pero eso permitiría errores como:

"DISPOINBLE" // error de tipeo "taler" // error de tipeo "ruta" // inconsistente con "En Ruta"

El enum limita los valores posibles: el compilador garantiza que un estado solo pueda ser DISPONIBLE, EN_RUTA o TALLER. Nada más. Así eliminamos toda una familia de errores.

Paso 14: Crear la Interfaz Mantenible

14.1 Crear el archivo

New → Java Class con Kind = Interface y nombre Mantenible.

// Indica que esta clase vive dentro del paquete lab.flotavehicular.model package lab.flotavehicular.model; // Interfaz: define un CONTRATO, no la implementación public interface Mantenible { // Todo vehículo que implemente esto DEBE saber evaluar su estado String evaluarEstadoGeneral(); }
14.2 ¿Qué representa una interfaz?

Una interfaz define un contrato. En este caso: "todo objeto mantenible debe saber evaluar su estado general". No especificamos cómo se hace: eso dependerá de cada tipo de vehículo.

La clase Vehiculo implementará esta interfaz, y cada subclase concreta (combustión, eléctrico, pesado) sobrescribirá evaluarEstadoGeneral() con su propia lógica.

Paso 15: Crear la Clase Abstracta Vehiculo

15.1 Crear el archivo

New → Java Class con Kind = Class y nombre Vehiculo. Escribiremos la palabra abstract manualmente.

// Paquete al que pertenece la clase package lab.flotavehicular.model; // Clase abstracta: NO se puede instanciar con 'new'. Implementa la interfaz Mantenible public abstract class Vehiculo implements Mantenible {
¿Por qué Vehiculo es abstract?

Porque en nuestro sistema no tiene sentido crear new Vehiculo(...): un vehículo debe ser de algún tipo específico (combustión, eléctrico o pesado). Además, la clase abstracta obliga a las clases hijas a definir ciertos comportamientos.

15.2 Declarar los atributos protegidos
// 'protected': visible para las subclases (herencia), no para cualquiera protected String placa; // Marca del vehículo (ej. Toyota, Volvo) protected String marca; // Kilometraje acumulado protected int kilometraje; // Estado actual del vehículo (enum) protected EstadoVehiculo estado;
¿Por qué 'protected' y no 'private'?

protected es un nivel intermedio de acceso: el atributo es visible para la propia clase y para sus subclases. Como las subclases (por ejemplo VehiculoPesado) necesitan modificar kilometraje directamente, usamos protected.

15.3 Escribir el constructor
// Constructor: recibe los datos básicos y asigna el estado inicial DISPONIBLE public Vehiculo(String placa, String marca, int kilometraje) { this.placa = placa; this.marca = marca; this.kilometraje = kilometraje; // Todo vehículo nace DISPONIBLE (no está en ruta ni en taller) this.estado = EstadoVehiculo.DISPONIBLE; }
15.4 Métodos abstractos y finalizarRuta()

Declaramos dos métodos abstractos (sin cuerpo: cada subclase dirá cómo los implementa) y un método concreto finalizarRuta() que es común a todos:

// Método abstracto: cada tipo de vehículo se mueve distinto (polimorfismo) public abstract void iniciarRuta(); // Método concreto: finalizar la ruta es igual para todos los vehículos public void finalizarRuta() { // Regla de negocio: solo se puede finalizar si está EN_RUTA if (estado != EstadoVehiculo.EN_RUTA) { throw new IllegalStateException( "El vehículo [" + placa + "] no se encuentra en ruta." ); } // Regresa a DISPONIBLE estado = EstadoVehiculo.DISPONIBLE; } // Método abstracto: cada subclase devuelve su propio tipo public abstract TipoVehiculo getTipo();
¿Qué es un método abstracto?

Es un método declarado sin cuerpo (termina en ;). Solo dice "esto debe existir". Toda subclase concreta está obligada a implementarlo. Es la base del polimorfismo: cada vehículo define su propia versión de iniciarRuta().

15.5 Getters, setter y toString()

Como los atributos son protected, la vista (el futuro Controller) necesita métodos públicos para leerlos. Agrupamos todos los getters, el setter y el toString():

// Getter público: permite leer la placa desde fuera de la clase public String getPlaca() { return placa; } // Getter público: permite leer la marca public String getMarca() { return marca; } // Getter público: permite leer el kilometraje public int getKilometraje() { return kilometraje; } // Getter público: permite leer el estado actual public EstadoVehiculo getEstado() { return estado; } // Setter público: permite cambiar el estado (lo usará la cola de mantenimiento) public void setEstado(EstadoVehiculo estado) { this.estado = estado; } // Sobrescritura: así se mostrará el vehículo en la futura lista (ListView) @Override public String toString() { return marca + " [" + placa + "]"; } }
¿Qué hace la anotación @Override?

Le indica al compilador que estamos sobrescribiendo un método que ya existe en la superclase (Object). Es opcional pero recomendada: si nos equivocamos en la firma, el compilador nos avisa con un error.

¿Por qué el toString() tiene ese formato?

Cuando la interfaz muestre la lista de vehículos, cada elemento llamará automáticamente a toString(). Con el formato "marca [placa]" veremos, por ejemplo, "Volvo [PES-003]" en lugar de una dirección de memoria ilegible.

16.4 Métodos obligatorios (polimorfismo y sobrescritura)

Aquí implementamos los tres métodos obligatorios: iniciarRuta() (abstracto del padre), getTipo() (abstracto del padre) y evaluarEstadoGeneral() (de la interfaz Mantenible). Cada uno lleva @Override porque estamos sobrescribiendo:

@Override // Sobrescritura: cómo inicia ruta un vehículo de combustión public void iniciarRuta() { // Regla 1: si está en el taller, no puede salir if (estado == EstadoVehiculo.TALLER) { throw new IllegalStateException( "El vehículo [" + placa + "] está en el taller. No puede salir." ); } // Regla 2: si ya está en ruta, no puede iniciar otra if (estado == EstadoVehiculo.EN_RUTA) { throw new IllegalStateException( "El vehículo [" + placa + "] ya se encuentra en ruta." ); } // Regla 3: no puede salir con menos de 10% de combustible if (nivelCombustible < 10) { throw new IllegalStateException( "Combustible insuficiente. Debe ir a la gasolinera." ); } // Lógica propia: consume 10% y avanza 50 km nivelCombustible -= 10; kilometraje += 50; estado = EstadoVehiculo.EN_RUTA; } @Override // Sobrescritura: este vehículo es de tipo COMBUSTION public TipoVehiculo getTipo() { return TipoVehiculo.COMBUSTION; } @Override // Sobrescritura (interfaz Mantenible): evalúa el estado según el combustible public String evaluarEstadoGeneral() { // Operador ternario: si hay menos de 15% avisa; si no, todo bien return nivelCombustible < 15 ? "Requiere ir a la gasolinera" : "Niveles óptimos"; } }
¿Qué hace el operador ternario condición ? a : b?

Es un if/else resumido en una línea: si nivelCombustible < 15 es verdadero devuelve "Requiere ir a la gasolinera"; en caso contrario devuelve "Niveles óptimos".

¿Por qué lanzar excepciones?

Estas son reglas de negocio: el sistema no debe permitir acciones inválidas (salir del taller, doble ruta, sin combustible). Lanzar IllegalStateException detiene la operación y le avisa al llamador con un mensaje claro. El Controller mostrará ese mensaje en un Alert en clase.

17.4 Métodos obligatorios (polimorfismo)

Misma estructura que VehiculoCombustion, pero con las reglas de un vehículo eléctrico. Nota cómo cambia la lógica: aquí validamos la batería en vez del combustible:

@Override // Sobrescritura: cómo inicia ruta un vehículo eléctrico public void iniciarRuta() { // Regla 1: no puede iniciar una ruta si ya está en ruta if (estado == EstadoVehiculo.EN_RUTA) { throw new IllegalStateException( "El vehículo [" + placa + "] ya se encuentra en ruta." ); } // Regla 2: si está en el taller, no puede salir if (this.estado == EstadoVehiculo.TALLER) { throw new IllegalStateException( "El vehículo [" + placa + "] está en el taller. No puede salir." ); } // Regla 3: no puede salir con menos de 15% de batería if (this.porcentajeBateria < 15.0) { throw new IllegalStateException( "Batería insuficiente (" + porcentajeBateria + "%). Conecte al cargador." ); } // Lógica propia: consume 15% de batería y avanza 50 km this.porcentajeBateria -= 15.0; this.kilometraje += 50; this.estado = EstadoVehiculo.EN_RUTA; } @Override // Sobrescritura: este vehículo es de tipo ELECTRICO public TipoVehiculo getTipo() { return TipoVehiculo.ELECTRICO; } @Override // Sobrescritura (interfaz Mantenible): evalúa el estado de la batería public String evaluarEstadoGeneral() { // Un eléctrico con muchos ciclos de carga tiene la batería degradada if (ciclosDeCarga > 1000) { return "Alerta: Batería muy degradada, requiere reemplazo"; } // Si no, revisamos el porcentaje actual else if (porcentajeBateria < 20) { return "Requiere conexión a estación de carga"; } // Si está por encima del 20%, todo bien else { return "Batería y sistemas óptimos"; } } }
¿Dónde se ve el polimorfismo aquí?

Fíjate: VehiculoCombustion y VehiculoElectrico son dos objetos distintos, pero ambos son Vehiculo:
Vehiculo v1 = new VehiculoCombustion(...);
Vehiculo v2 = new VehiculoElectrico(...);
Si escribimos v1.iniciarRuta(); y v2.iniciarRuta();, Java ejecutará implementaciones diferentes según el tipo real del objeto. Eso es polimorfismo.

18.1 Crear el archivo

Vehiculo ↑ VehiculoCombustion ↑ VehiculoPesado
18.2 Atributos y constructor
package lab.flotavehicular.model; // Herencia multinivel: pesado es una clase de combustión, que es un vehículo public class VehiculoPesado extends VehiculoCombustion { // Cuántas toneladas puede transportar como máximo private double tonelajeMaximo; // Toneladas cargadas actualmente (arranca en 0.0) private double cargaActual; // Tipo de carga que transporta (enum) private TipoCarga tipoCarga; // Constructor: recibe los datos del abuelo (super de Combustion) + los suyos public VehiculoPesado( String placa, String marca, int kilometraje, double nivelCombustible, double tonelajeMaximo, TipoCarga tipoCarga) { // Llama al constructor de VehiculoCombustion (que a su vez llama al de Vehiculo) super(placa, marca, kilometraje, nivelCombustible); this.tonelajeMaximo = tonelajeMaximo; this.cargaActual = 0.0; this.tipoCarga = tipoCarga; }

18.4 Métodos de negocio: cargarMercancia, iniciarRuta y finalizarRuta

Estos tres métodos contienen las reglas de negocio específicas del camión. Observa cómo se combinan la lógica propia con super.iniciarRuta() y super.finalizarRuta() para reutilizar el comportamiento del padre:

// Regla de negocio: cargar mercancía en el camión public void cargarMercancia(double pesoEnToneladas) { // No se puede cargar un peso negativo o cero if (pesoEnToneladas <= 0) { throw new IllegalArgumentException( "El peso de la mercancía debe ser mayor que cero." ); } // No se puede exceder el tonelaje máximo (sobrecarga) if (pesoEnToneladas > tonelajeMaximo) { throw new IllegalArgumentException( "Sobrecarga: el camión solo soporta " + tonelajeMaximo + " toneladas." ); } // Si pasó las validaciones, se registra la carga this.cargaActual = pesoEnToneladas; } @Override // Sobrescritura: un camión NO puede salir vacío a ruta public void iniciarRuta() { // Regla propia del pesado: debe llevar carga if (cargaActual == 0.0) { throw new IllegalStateException( "El camión [" + placa + "] no puede salir a ruta vacío." ); } // Reutiliza TODA la validación y lógica del padre (combustible, estado...) super.iniciarRuta(); // Y agrega su comportamiento particular: un camión pesado recorre más (150 km) this.kilometraje += 150; } @Override // Sobrescritura: al finalizar la ruta se descarga el camión public void finalizarRuta() { // Reutiliza la lógica del padre (valida estado y vuelve a DISPONIBLE) super.finalizarRuta(); // Y agrega su comportamiento particular: la carga se vacía this.cargaActual = 0.0; }
¿Para qué sirve super.iniciarRuta()?

Permite reutilizar el comportamiento del padre y luego agregar comportamiento particular. Sin esa línea, el camión no validaría el combustible ni cambiaría su estado correctamente. Con ella, primero se ejecuta todo lo del padre y después lo propio (los +150 km). Es la esencia de la sobrescritura responsable.

18.5 Métodos sobrescritos: getTipo y evaluarEstadoGeneral

Por último, los dos métodos que identifican al camión. evaluarEstadoGeneral() es especial porque reutiliza el resultado del padre con super.evaluarEstadoGeneral() y le agrega una alerta extra:

@Override // Sobrescritura: este vehículo es de tipo PESADO public TipoVehiculo getTipo() { return TipoVehiculo.PESADO; } @Override // Sobrescritura (interfaz Mantenible): estado del camión, con alerta de ejes public String evaluarEstadoGeneral() { // Guarda primero el texto que devuelve el padre (nivel de combustible) String estadoPadre = super.evaluarEstadoGeneral(); // Un camión con mucho kilometraje necesita revisión de ejes y frenos de aire if (kilometraje > 150000) { return estadoPadre + " | Alerta: Requiere revisión de ejes y frenos de aire."; } // Si el kilometraje es normal, devolvemos solo lo que dijo el padre return estadoPadre; } }
¿Por qué llamar a super.evaluarEstadoGeneral()?

El camión también es un vehículo de combustión, así que primero pregunta al padre qué dice del combustible y luego agrega su propia alerta mecánica. Así evitamos repetir código: el padre evalúa el combustible, y el pesado solo añade lo que le corresponde.

Paso 19: Crear Flota (CRUD en memoria)

19.1 Crear el archivo

New → Java Class (Kind = Class) con nombre Flota. Esta clase almacena todos los vehículos en una lista y ofrece las operaciones CRUD.

19.2 Atributo y constructor
package lab.flotavehicular.model; // Importamos las colecciones que vamos a usar import java.util.ArrayList; import java.util.List; public class Flota { // La lista de vehículos. 'List' es la interfaz, 'ArrayList' la implementación private List<Vehiculo> vehiculos; public Flota() { // Se inicializa como un ArrayList vacío this.vehiculos = new ArrayList<>(); }
¿Por qué List y no ArrayList directamente?

Porque usamos el mismo principio de interfaz vs implementación: List es la interfaz (el "contrato") y ArrayList es la implementación concreta. Así podemos cambiar la implementación en el futuro (ej. a LinkedList) sin tocar el resto del código.

19.3 CREATE + READ

agregarVehiculo (Create) valida que la placa no esté duplicada usando un stream con anyMatch. obtenerVehiculos (Read) devuelve una copia de la lista para proteger los datos internos:

// CREATE: registra un vehículo nuevo en la flota public void agregarVehiculo(Vehiculo vehiculo) { // Stream + anyMatch + lambda: ¿ya existe algún vehículo con esa placa? boolean existe = vehiculos.stream() .anyMatch(v -> v.getPlaca().equalsIgnoreCase( vehiculo.getPlaca() ) ); // Regla de negocio: las placas no pueden repetirse (sin importar mayúsculas) if (existe) { throw new IllegalArgumentException( "Ya existe un vehículo con esa placa." ); } // Si no existe, se agrega a la lista vehiculos.add(vehiculo); } // READ: devuelve una copia de la lista (para que nadie la modifique desde afuera) public List<Vehiculo> obtenerVehiculos() { return new ArrayList<>(vehiculos); }
¿Qué hace vehiculos.stream().anyMatch(...)?

Un stream es una forma moderna de recorrer una colección. anyMatch(lambda) devuelve true si al menos un elemento cumple la condición. La lambda v -> v.getPlaca().equalsIgnoreCase(...) dice: "¿existe un vehículo v cuya placa, ignorando mayúsculas, sea igual a la nueva?"

19.4 UPDATE + DELETE

actualizarVehiculo (Update) recorre la lista buscando por placa y reemplaza el objeto en esa posición. eliminarVehiculo (Delete) usa removeIf con una lambda:

// UPDATE: reemplaza un vehículo existente por su versión actualizada public void actualizarVehiculo(Vehiculo vehiculoActualizado) { // Recorremos la lista con un índice for (int i = 0; i < vehiculos.size(); i++) { // Si encontramos la placa (ignorando mayúsculas) ... if (vehiculos.get(i).getPlaca() .equalsIgnoreCase(vehiculoActualizado.getPlaca())) { // ... la reemplazamos por el objeto nuevo y terminamos vehiculos.set(i, vehiculoActualizado); return; } } // Si el ciclo termina sin encontrar la placa, es un error throw new IllegalArgumentException( "No se encontró el vehículo." ); } // DELETE: elimina el vehículo con la placa indicada public void eliminarVehiculo(String placa) { // removeIf + lambda: elimina todos los que cumplan la condición boolean eliminado = vehiculos.removeIf( vehiculo -> vehiculo.getPlaca().equalsIgnoreCase(placa) ); // removeIf devuelve true si borró algo; si no, la placa no existía if (!eliminado) { throw new IllegalArgumentException( "No se encontró el vehículo." ); } } }
¿Qué hace removeIf(lambda)?

Recorre la lista y elimina todos los elementos para los que la lambda devuelve true. Devuelve true si eliminó al menos uno. Aquí la lambda dice: "elimina todo vehículo cuya placa sea igual a la recibida".

Paso 21: Crear ColaMantenimiento (Genéricos + Queue)

21.1 Crear el archivo

New → Java Class (Kind = Class) con nombre ColaMantenimiento. Esta clase utiliza genéricos con límite y la estructura de datos Queue.

package lab.flotavehicular.model; // Colecciones necesarias: LinkedList (implementa Queue), Queue (interfaz), etc. import java.util.LinkedList; import java.util.Queue; import java.util.List; import java.util.ArrayList; // <T extends Vehiculo> garantiza que esta cola es EXCLUSIVAMENTE para vehículos public class ColaMantenimiento<T extends Vehiculo> { // Usamos la interfaz Queue de Java Collections (FIFO) private Queue<T> filaDeEspera; public ColaMantenimiento() { // LinkedList implementa la interfaz Queue (Primero en entrar, primero en salir) this.filaDeEspera = new LinkedList<>(); }
¿Qué significa <T extends Vehiculo>?

Significa: T puede ser Vehiculo o cualquier clase hija de Vehiculo. Por ejemplo, ColaMantenimiento<Vehiculo> puede recibir VehiculoCombustion, VehiculoElectrico o VehiculoPesado. Pero no podría usarse ColaMantenimiento<String>, porque String NO extends Vehiculo.

¿Por qué utilizamos Queue?

Una cola utiliza normalmente FIFO (First In, First Out): el primero en entrar es el primero en salir. Si entran al taller ABC-001, ELE-002 y PES-003, al atender sale ABC-001. Es justo lo que necesitamos para un taller de mantenimiento.

21.2 Métodos de la cola: encolar y atenderSiguiente
// Agregar un vehículo a la cola (offer agrega al final) public void encolar(T vehiculo) { // Regla: no se puede encolar un vehículo que ya está en mantenimiento if (vehiculo.getEstado() == EstadoVehiculo.TALLER) { throw new IllegalStateException( "El vehículo ya se encuentra en mantenimiento." ); } // Regla: no se puede enviar a mantenimiento un vehículo que está en ruta if (vehiculo.getEstado() == EstadoVehiculo.EN_RUTA) { throw new IllegalStateException( "No puede enviar a mantenimiento un vehículo que está en ruta." ); } // Cambia el estado a TALLER y lo agrega al final de la fila vehiculo.setEstado(EstadoVehiculo.TALLER); filaDeEspera.offer(vehiculo); } // Atender al primer vehículo de la cola (poll lo quita del frente) public T atenderSiguiente() { // Regla: no hay nada que atender si la cola está vacía if (filaDeEspera.isEmpty()) { throw new IllegalStateException( "No hay vehículos en la cola de mantenimiento." ); } // poll() saca al primero (FIFO) y lo regresa como atendido T vehiculoAtendido = filaDeEspera.poll(); // Al salir del taller queda DISPONIBLE para trabajar vehiculoAtendido.setEstado(EstadoVehiculo.DISPONIBLE); return vehiculoAtendido; }
¿Qué hacen offer() y poll()?

offer() agrega un elemento al final de la cola. poll() retira el elemento del frente (el primero que entró) y lo devuelve. Con esas dos operaciones implementamos el comportamiento FIFO.

21.3 Métodos utilitarios para la vista

Estos métodos serán útiles cuando construyamos la interfaz gráfica (para saber cuántos vehículos esperan y mostrarlos):

// ¿Está vacía la cola? public boolean estaVacia() { return filaDeEspera.isEmpty(); } // ¿Cuántos vehículos hay pendientes? public int cantidadPendientes() { return filaDeEspera.size(); } // Devuelve una copia de la lista de pendientes (para mostrarla en la vista) public List<T> obtenerListaPendientes() { return new ArrayList<>(filaDeEspera); } }
¿Cómo se relacionan Queue y LinkedList?

Observa: private Queue<T> filaDeEspera; es la interfaz, pero construimos new LinkedList<>(), la implementación concreta. Esto funciona porque LinkedList implementa Queue. Es el mismo principio que usamos con List<Vehiculo> vehiculos = new ArrayList<>().

23.3 Crear la hoja de estilos style.css

En la carpeta assets/css crea un archivo nuevo llamado style.css (New → File). En JavaFX, los estilos usan propiedades con el prefijo -fx-. Lo escribiremos por secciones para entender cada bloque:

a) Fondo y fuente general (.root)

/* .root aplica a TODA la aplicación (es el contenedor raíz) */ .root { -fx-font-family: "Segoe UI"; /* tipo de letra global */ -fx-background-color: #F4F7FA; /* color de fondo de la ventana */ }

.root es el selector especial que estiliza toda la aplicación: aquí definimos la fuente y el fondo general.

b) Títulos

/* Título principal de la ventana */ .titulo-principal { -fx-font-size: 24px; /* tamaño de la letra */ -fx-font-weight: bold; /* negrita */ -fx-text-fill: #1F3A5F; /* color del texto (azul oscuro) */ } /* Subtítulo (texto secundario) */ .subtitulo { -fx-font-size: 14px; -fx-text-fill: #5F6B7A; /* gris azulado */ } /* Título de cada sección o tarjeta */ .titulo-seccion { -fx-font-size: 16px; -fx-font-weight: bold; -fx-text-fill: #234E70; }

Los selectores por clase (.titulo-principal, .subtitulo, .titulo-seccion) se asignarán en Scene Builder a los Label correspondientes. Cada propiedad -fx-... equivale a una propiedad de estilo (tamaño, peso, color del texto).

c) Paneles o tarjetas (.tarjeta)

/* Tarjeta: un panel blanco con bordes redondeados */ .tarjeta { -fx-background-color: white; /* fondo blanco */ -fx-background-radius: 12; /* esquinas redondeadas del fondo */ -fx-border-radius: 12; /* esquinas redondeadas del borde */ -fx-border-color: #D9E2EC; /* color del borde */ -fx-padding: 18; /* espacio interior alrededor del contenido */ }

-fx-background-radius redondea el fondo y -fx-border-radius redondea el borde; -fx-padding es el espacio interno (que el contenido no "pegue" al borde).

d) Campos de texto y listas desplegables

/* text-field (cajas de texto) y combo-box (listas) */ .text-field, .combo-box { -fx-background-radius: 6; -fx-border-radius: 6; -fx-border-color: #C9D3DD; -fx-background-color: white; } /* Estado :focused = cuando el usuario hace clic en el campo */ .text-field:focused, .combo-box:focused { -fx-border-color: #2F80ED; /* el borde se pone azul */ -fx-border-width: 1.5; /* y un poco más grueso */ }

La pseudo-clase :focused se activa cuando el campo está "enfocado" (el usuario hizo clic o presionó Tab para escribirlo). Aprovechamos eso para resaltar el campo activo con un borde azul.

e) Botones en general

/* Estilos comunes a todos los botones */ .button { -fx-background-radius: 7; /* esquinas redondeadas */ -fx-cursor: hand; /* cursor de "manito" al pasar el mouse */ -fx-font-weight: bold; /* texto en negrita */ -fx-padding: 7 14 7 14; /* 7px arriba/abajo, 14px izquierda/derecha */ }

Al estilizar el selector .button, TODOS los botones de la aplicación heredan estas propiedades. Después, cada botón específico agrega su color con su propia clase.

f) Botones del CRUD

/* Registrar: azul */ .boton-registrar { -fx-background-color: #2D9CDB; -fx-text-fill: white; } /* Editar: amarillo (texto oscuro para que se lea) */ .boton-editar { -fx-background-color: #F2C94C; -fx-text-fill: #333333; } /* Eliminar: rojo */ .boton-eliminar { -fx-background-color: #EB5757; -fx-text-fill: white; } /* Limpiar: gris claro */ .boton-limpiar { -fx-background-color: #E0E6ED; -fx-text-fill: #333333; }

Cada clase (.boton-registrar, .boton-editar, etc.) define el color de fondo (-fx-background-color) y el color del texto (-fx-text-fill). En Scene Builder asignaremos una clase a cada botón.

g) Botones de operaciones

/* Iniciar ruta: verde */ .boton-ruta { -fx-background-color: #27AE60; -fx-text-fill: white; } /* Finalizar ruta: naranja */ .boton-finalizar { -fx-background-color: #F2994A; -fx-text-fill: white; } /* Mantenimiento: morado */ .boton-mantenimiento { -fx-background-color: #6C63FF; -fx-text-fill: white; }

Los colores "significan" algo: verde para acciones positivas (iniciar), naranja para detener/finalizar y morado para mantenimiento.

h) Tabla (TableView)

/* La tabla completa */ .table-view { -fx-background-color: white; -fx-border-color: #D9E2EC; -fx-border-radius: 8; } /* La fila de encabezados (columna) */ .table-view .column-header { -fx-background-color: #1F3A5F; /* fondo azul oscuro */ } /* El texto dentro de cada encabezado */ .table-view .column-header .label { -fx-text-fill: white; /* texto blanco */ -fx-font-weight: bold; }

Observa el selector combinado .table-view .column-header .label: significa "el Label que está dentro de un column-header que está dentro de un table-view". Así estilizamos solo los encabezados de la tabla y no las celdas.

i) Etiqueta de estado de mantenimiento

/* Etiqueta que muestra cuántos vehículos están en mantenimiento */ .estado-mantenimiento { -fx-background-color: #E8F1FA; /* fondo azul muy claro */ -fx-background-radius: 8; -fx-padding: 8 12 8 12; /* relleno interior */ -fx-text-fill: #1F3A5F; /* texto azul oscuro */ -fx-font-weight: bold; }

Este bloque le da aspecto de "píldora" a la etiqueta que informará el estado del mantenimiento en la futura interfaz.

Paso 24: Crear el Punto de Entrada Main.java

24.1 La clase que lanza la aplicación

En el paquete lab.flotavehicular crea la clase Main (Kind = Class) que extiende Application (la clase base de toda aplicación JavaFX):

package lab.flotavehicular; // Importaciones de JavaFX necesarias para lanzar la app import javafx.application.Application; import javafx.fxml.FXMLLoader; import javafx.scene.Scene; import javafx.stage.Stage; import java.io.IOException; // Main hereda de Application: la clase base de toda app JavaFX public class Main extends Application { @Override // start() es donde JavaFX "muestra" la ventana principal (el Stage) public void start(Stage stage) throws IOException { // FXMLLoader lee el archivo FXML (la vista). Aún NO existe, lo crearemos en clase FXMLLoader loader = new FXMLLoader( Main.class.getResource("/lab/flotavehicular/view/flotaView.fxml") ); // La escena se construye cargando el FXML Scene scene = new Scene(loader.load()); // Configura el título de la ventana stage.setTitle("Gestión de Flota Vehicular"); // Asigna la escena a la ventana y la muestra stage.setScene(scene); stage.show(); } public static void main(String[] args) { // launch() arranca el ciclo de vida de JavaFX launch(args); } }
No intentes ejecutarla todavía. Esta clase carga flotaView.fxml, que aún no existe (la crearemos en clase con Scene Builder). Si la ejecutas ahora, lanzará una excepción: "Resource not found". Es el comportamiento esperado: Main está lista, pero le falta su vista.
¿Qué es Stage, Scene y FXMLLoader?

Stage es la ventana del sistema operativo. Scene es el contenido que va dentro de la ventana. FXMLLoader es la clase que lee un archivo .fxml y lo convierte en una escena real (creando todos los componentes y conectándolos con el Controller). Esta es la pieza que une View y Controller.

Paso 25: Configurar IntelliJ con Scene Builder

25.1 Indicarle a IntelliJ dónde está Scene Builder

Para poder abrir los archivos .fxml directamente con Scene Builder desde IntelliJ:

  1. Ve a File → Settings (en Windows) o IntelliJ IDEA → Preferences (en macOS).
  2. Navega a Languages & Frameworks → JavaFX.
  3. En el campo Path to SceneBuilder, haz clic en el icono de carpeta y selecciona el ejecutable de Gluon Scene Builder instalado en el Paso 2.
  4. Haz clic en OK.

Con esto, cuando en clase doble hagas clic en un archivo .fxml, IntelliJ te preguntará si quieres abrirlo con Scene Builder, o podrás usar Right click → Open In Scene Builder.
