Introducción al Laboratorio

En la Semana 8 cerraron la persistencia con archivos: binaria con MessageDAO y en XML con MessageXmlExporter. Ambas funcionan, pero comparten un límite: los datos viven solo en el disco de cada computadora. Si dos personas corrieran Mini-Discord en máquinas distintas, cada una tendría su propio mensajes.dat, sin forma de compartir el historial.

Hoy resuelven eso arrancando una base de datos MySQL real — el mismo tipo de motor que corre detrás de aplicaciones de producción. No van a borrar lo que ya tienen: van a crear una interfaz (MessageRepository) que separa "qué necesita el Controller" de "cómo se guarda realmente", y una nueva implementación (JdbcMessageRepository) que cumple esa interfaz hablando con MySQL por JDBC.

Enfoque Pedagógico: Igual que en la Semana 8, cada paso importante trae una caja morada "¿Cómo se llega a esta decisión?" con el razonamiento detrás. El código nuevo de hoy está marcado con comentarios en verde y en negrita ("Nuevo de la clase 11: ..."). Los comentarios grises son código que ya existía y no cambió.

¿Cómo se llega a esta decisión?

Todo lo de hoy vuelve a vivir en data.dao, la misma regla de la Semana 8: acceso a datos es problema de la capa de Datos, sin importar si el "dato" está en un archivo o en una base de datos. Lo único que cambia es la tecnología detrás del DAO — no la capa a la que pertenece.

Paso 2: Modelar la base de datos

2.1 De dos clases Java a dos tablas normalizadas

Message tiene un User adentro. En SQL eso se traduce en dos tablas relacionadas por una llave foránea — nunca en repetir el nombre de usuario en cada fila de mensaje (eso violaría 3FN, como vimos en la clase de hoy).

¿Cómo se llega a esta decisión?

La pregunta guía es: "¿esta información depende del mensaje, o depende del usuario?". El nombre de usuario depende del usuario (no cambia mensaje a mensaje), así que vive en su propia tabla. El contenido y la fecha dependen del mensaje específico, así que viven en mensajes. Esa separación — preguntarse de qué "entidad" depende cada dato — es exactamente lo que hacen las formas normales de manera formal.

2.2 Crear la base y las tablas (DDL)

En IntelliJ, abran una consola SQL contra su servidor MySQL (o usen mysql desde terminal) y ejecuten:

schema.sql
CREATE DATABASE IF NOT EXISTS minidiscord;
USE minidiscord;

CREATE TABLE usuarios (
    id INT AUTO_INCREMENT PRIMARY KEY,
    username VARCHAR(50) NOT NULL UNIQUE
);

CREATE TABLE mensajes (
    id INT AUTO_INCREMENT PRIMARY KEY,
    usuario_id INT NOT NULL,
    contenido VARCHAR(500) NOT NULL,
    fecha_envio DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (usuario_id) REFERENCES usuarios(id)
);
Nota: esto es DDL (Data Definition Language) — se corre una sola vez para crear la estructura. Todo lo que viene después (INSERT, SELECT) es DLM y va a vivir dentro del código Java, no en una consola manual.
2.3 Conectar IntelliJ Database Tools

View → Tool Windows → Database → botón "+" → Data Source → MySQL. Completen host (localhost), puerto (3306), usuario, contraseña y la base minidiscord. Pulsen Test Connection (IntelliJ puede pedir descargar el driver la primera vez — acéptenlo) y luego Apply. Con esto pueden explorar las tablas visualmente desde el IDE.

3.2 Diseñar MessageRepository — la interfaz antes que la implementación

Igual que en la Semana 8 diseñaron primero la firma del DAO, hoy hacen lo mismo pero como interfaz, para que el Controller nunca dependa de si por detrás hay un archivo o una base de datos:

MessageRepository.java
package cr.ac.una.est.minidiscord.data.dao;

import cr.ac.una.est.minidiscord.business.model.Message;
import java.util.List;

// Nuevo de la clase 11: interfaz — el Controller programa contra esto, nunca contra una clase concreta
public interface MessageRepository {
    void guardar(Message mensaje);
    List<Message> obtenerTodos();
}

¿Cómo se llega a esta decisión?

guardar(Message) reemplaza a guardarTodos(List) de la Semana 8. En un archivo, reescribir todo el historial en cada envío era razonable porque no había otra forma. Con una base de datos SÍ hay una forma mejor: un INSERT agrega una sola fila sin tocar las demás. Cambiar la firma del método es una señal de que están diseñando para la tecnología real, no forzando el mismo molde de la semana pasada.

Paso 4: Implementar JdbcMessageRepository

4.1 Conexión y guardar()

En data.dao, junto a MessageDAO:

JdbcMessageRepository.java
package cr.ac.una.est.minidiscord.data.dao;

import cr.ac.una.est.minidiscord.business.model.Message;
import cr.ac.una.est.minidiscord.business.model.User;
import java.sql.*;
import java.util.ArrayList;
import java.util.List;

// Nuevo de la clase 11: implementación de MessageRepository que habla con MySQL por JDBC
public class JdbcMessageRepository implements MessageRepository {

    private static final String URL = "jdbc:mysql://localhost:3306/minidiscord";
    private static final String USUARIO = "root";
    private static final String CLAVE = "CAMBIAR_POR_SU_CLAVE";

    // Devuelve el id del usuario, creándolo primero si todavía no existe
    private int obtenerOcrearUsuario(Connection con, String username) throws SQLException {
        try (PreparedStatement buscar = con.prepareStatement("SELECT id FROM usuarios WHERE username = ?")) {
            buscar.setString(1, username);
            try (ResultSet rs = buscar.executeQuery()) {
                if (rs.next()) return rs.getInt("id");
            }
        }
        try (PreparedStatement crear = con.prepareStatement(
                "INSERT INTO usuarios (username) VALUES (?)", Statement.RETURN_GENERATED_KEYS)) {
            crear.setString(1, username);
            crear.executeUpdate();
            try (ResultSet claves = crear.getGeneratedKeys()) {
                claves.next();
                return claves.getInt(1);
            }
        }
    }

    @Override
    public void guardar(Message mensaje) {
        try (Connection con = DriverManager.getConnection(URL, USUARIO, CLAVE)) {
            int usuarioId = obtenerOcrearUsuario(con, mensaje.getAuthor().getUsername());
            try (PreparedStatement stmt = con.prepareStatement(
                    "INSERT INTO mensajes (usuario_id, contenido) VALUES (?, ?)")) {
                stmt.setInt(1, usuarioId);
                stmt.setString(2, mensaje.getContent());
                stmt.executeUpdate();
            }
        } catch (SQLException e) {
            System.out.println("No se pudo guardar en la base de datos: " + e.getMessage());
        }
    }
}
Ver explicación del código línea por línea.

obtenerOcrearUsuario: como usuarios y mensajes son tablas separadas (normalización), antes de insertar un mensaje hay que saber el id del usuario que lo escribió. Este método primero busca si ya existe; si no, lo crea y devuelve el id recién generado con RETURN_GENERATED_KEYS.

Cada try (Connection con = ...) abre y cierra la conexión en cada llamada — sencillo para el laboratorio de hoy. En un sistema real esto se reemplaza por un pool de conexiones, pero eso queda fuera del alcance de esta clase.

CLAVE como constante en el código es solo para este laboratorio. En un proyecto real, la contraseña de la base de datos nunca se escribe en el código fuente — se lee de una variable de entorno o un archivo de configuración fuera del repositorio.

4.2 Leer el historial: obtenerTodos() con JOIN

Agreguen dentro de la misma clase:

JdbcMessageRepository.java (continuación)
    // Nuevo de la clase 11: continúa la misma clase — trae el historial completo con un JOIN
    @Override
    public List<Message> obtenerTodos() {
        List<Message> resultado = new ArrayList<>();
        String sql = "SELECT u.username, m.contenido " +
                     "FROM mensajes m JOIN usuarios u ON m.usuario_id = u.id " +
                     "ORDER BY m.fecha_envio";
        try (Connection con = DriverManager.getConnection(URL, USUARIO, CLAVE);
             PreparedStatement stmt = con.prepareStatement(sql);
             ResultSet rs = stmt.executeQuery()) {

            while (rs.next()) {
                User autor = new User(rs.getString("username"));
                resultado.add(new Message(autor, rs.getString("contenido")));
            }
        } catch (SQLException e) {
            System.out.println("No se pudo leer el historial: " + e.getMessage());
        }
        return resultado;
    }
Ver explicación del código línea por línea.

JOIN es la operación que "deshace" la normalización cuando la necesitan: reconstruye, fila por fila, la combinación de un mensaje con el username de su autor — exactamente la información que antes vivía junta dentro de un solo objeto Message en memoria.

Este método reconstruye objetos de dominio (User, Message) a partir de filas planas — es el "mapeo de datos" mencionado en el programa del curso: pasar de filas y columnas de vuelta a objetos Java.

Paso 5: Conectar el repositorio al Controller

Cambien en ChatViewController.java el tipo de la variable a la interfaz, no a la clase concreta:

ChatViewController.java
// Nuevo de la clase 11: el campo es del TIPO de la interfaz, la instancia es la implementación JDBC
private final MessageRepository messageRepository = new JdbcMessageRepository();

@FXML
public void initialize() {
    messageListView.setItems(messages); // ya existía

    // Nuevo de la clase 11: el historial ahora se carga desde MySQL, no desde mensajes.dat
    for (Message m : messageRepository.obtenerTodos()) {
        historial.add(m);
        messages.add(m.toString());
    }
}

@FXML
private void handleSendMessage() {
    try {
        Message nuevoMsg = chatService.processMessage(currentUser, messageInputField.getText()); // ya existía
        historial.add(nuevoMsg);
        messages.add(nuevoMsg.toString());
        messageInputField.clear();

        // Nuevo de la clase 11: se guarda directo en MySQL (un INSERT, no se reescribe todo el historial)
        messageRepository.guardar(nuevoMsg);
    } catch (IllegalArgumentException e) {
        System.out.println("Aviso de Validación: " + e.getMessage()); // ya existía
    }
}

¿Cómo se llega a esta decisión?

Fíjense qué NO cambió: chatService.processMessage(...), la validación, y cómo se pinta la lista siguen exactamente igual. Esa es la prueba de que la arquitectura de la Semana 7-8 estaba bien separada — cambiar la tecnología de persistencia (de archivo a base de datos) solo tocó la capa de Datos y una línea del Controller.
