¿Qué es una biblioteca?

Un conjunto de clases ya compiladas (normalmente un .jar) que otro proyecto puede referenciar (declarar como dependencia) y usar, sin ver ni recompilar su código fuente. JavaFX mismo es una biblioteca externa que ya referencian en su pom.xml.

<!-- pom.xml: referencia a una biblioteca -->
<dependency>
  <artifactId>javafx-controls</artifactId>
</dependency>

La regla de dependencia

Las flechas de dependencia siempre apuntan "hacia adentro". Nunca al revés.

DAO vs. DTO: dos siglas, dos trabajos distintos

Se confunden por el nombre parecido, pero no compiten — se necesitan el uno al otro.

DAO — Data Access Object

"El que SABE HACER el trabajo"

Una clase con lógica: métodos que saben leer y escribir datos (a un archivo, XML, base de datos). Vive fijo en la capa de Datos.

MessageDAO.guardarTodos(lista);
MessageDAO.cargarTodos();

DTO — Data Transfer Object

"El que SOLO VIAJA con los datos adentro"

Una clase plana: solo atributos + getters/setters, sin lógica. Es la caja que se transporta entre capas, nunca decide nada.

new MessageDTO(autor, contenido);

Analogía: el DAO es el camión repartidor — sabe manejar, conoce la ruta, hace el trabajo de llevar y traer. El DTO es la caja de cartón que va adentro del camión — no maneja nada, solo contiene el producto de forma ordenada para el viaje.

public void exportar(List<Message> mensajes) {
    List<MessageDTO> dtos = new ArrayList<>();
    for (Message m : mensajes) {
        // el DAO (este exportador) CONVIERTE el dominio a un DTO antes de exportarlo
        dtos.add(new MessageDTO(m.getAuthor().getUsername(), m.getContent()));
    }
    encoder.writeObject(dtos); // lo que realmente viaja al archivo es el DTO
}

Para que quede claro:

El DAO decide cuándo y cómo usar el DTO. El DTO nunca decide nada por sí mismo — ni siquiera sabe que existen las otras capas.

Transferencia de datos: el rol del DTO

Hoy los objetos de dominio (Message, User) viajan directo entre capas — válido para este tamaño de proyecto. El DTO (objeto plano, sin lógica) es el mecanismo formal cuando el proyecto crece o las capas viven en máquinas físicas distintas (n-tier real). Sin DTO, exponer el Message completo expone también la estructura interna del dominio.

La pregunta más importante de la clase:

"Si mañana el MessageDAO, en vez de leer un archivo, llamara a un servidor remoto por sockets, ¿qué otras clases tendrían que modificar?"

Respuesta: ninguna otra. Solo el DAO cambia — esa es la prueba de que la arquitectura está bien separada.

Glosario de Términos Clave — Semana 8

  • Biblioteca: conjunto de clases compiladas y empaquetadas que otro proyecto referencia y reutiliza sin ver su código fuente.
  • Regla de dependencia: Presentación depende de Negocio, Negocio depende de Datos. Nunca al revés.
  • Serialización binaria: convertir un objeto a bytes con ObjectOutputStream/ObjectInputStream. Rápida, pero ilegible fuera de Java.
  • Serialización XML: con XMLEncoder/XMLDecoder o JAXB. Legible y portable, pero más pesada.
  • Patrones creacionales: resuelven cómo se instancian los objetos (Singleton, Builder).
  • Patrones estructurales: resuelven cómo se ensamblan/relacionan objetos (Composite, Adapter).
  • Patrones de comportamiento: resuelven cómo se comunican en tiempo de ejecución (Observer, Strategy).
  • DTO: objeto plano (solo atributos, getters/setters) para transportar datos entre capas sin exponer lógica interna.
