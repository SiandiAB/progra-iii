¿Qué problema intentamos resolver?

Una tarea lenta puede congelar toda la interfaz si se ejecuta en el mismo hilo.

Imaginemos una aplicación de escritorio que permite consultar información, guardar cambios y descargar un reporte. Si todo el trabajo ocurre de forma secuencial en el mismo hilo de la interfaz, una tarea lenta puede congelar la ventana.

Sin trabajo concurrente

  1. La persona hace clic en “Generar reporte”.
  2. La aplicación procesa todo en la interfaz.
  3. Mientras espera, la ventana deja de responder.

Con trabajo separado

  1. La interfaz recibe el clic.
  2. Una tarea de fondo prepara el reporte.
  3. La interfaz puede seguir respondiendo y mostrar el resultado al terminar.

La concurrencia no hace que una operación lenta sea automáticamente más rápida; permite organizar varias tareas para que progresen sin bloquear innecesariamente a las demás.

Programa, proceso e hilo no son lo mismo

Tres conceptos que conviene distinguir antes de programar.

Programa

Conjunto de instrucciones almacenadas, por ejemplo, un archivo JAR de Java.

Es el código que puede ejecutarse.

Proceso

Instancia de un programa en ejecución, con recursos y espacio de memoria propios.

Dos ejecuciones del mismo programa pueden ser procesos distintos.

Hilo (thread)

Flujo de ejecución dentro de un proceso. Los hilos del mismo proceso comparten memoria y recursos.

Comparten estado, así que también pueden interferirse.

Proceso vs. hilo

Diferencias que influyen en el diseño de una aplicación.

Aspecto Proceso Hilo
Memoria Espacio de memoria separado de otros procesos. Comparte el espacio del proceso con otros hilos.
Comunicación Normalmente requiere mecanismos explícitos entre procesos, como sockets o canales. Puede compartir objetos; requiere coordinación para evitar conflictos.
Coste de creación Generalmente mayor. Generalmente menor que crear otro proceso.
Fallo Un fallo suele estar más aislado del resto de procesos. Un fallo no controlado puede afectar a la aplicación completa.
Uso habitual Aislar aplicaciones o servicios. Atender tareas simultáneas dentro de una aplicación.

Son tendencias generales, no garantías absolutas: el comportamiento depende del sistema operativo, la JVM y el diseño de la aplicación.

¿Qué significa multithreading?

Varios hilos dentro del mismo proceso.

Es la técnica de ejecutar varios hilos dentro de un mismo proceso. Los hilos pueden avanzar de manera concurrente; en equipos con varios núcleos, algunos también pueden ejecutarse en paralelo.

Concurrencia

Varias tareas avanzan durante el mismo intervalo. El sistema puede alternar entre ellas.

Tarea A
Tarea B
Tarea C

Paralelismo

Dos o más tareas se ejecutan literalmente al mismo tiempo en diferentes núcleos de procesamiento.

CPU 1
Tarea A
CPU 2
Tarea B

Importante: crear varios hilos no garantiza una mejora. Si compiten por el mismo recurso o hacen muy poco trabajo, pueden agregar complejidad sin aportar beneficios.

Crear y ejecutar un hilo en Java

Implementar Runnable y entregarlo a un Thread.

Una forma habitual es implementar Runnable, que representa una tarea que puede ejecutarse. Luego se entrega esa tarea a un objeto Thread. 

public class TareaReporte implements Runnable {
    @Override
    public void run() {
        System.out.println("Preparando reporte...");
        // Aquí iría el trabajo de fondo
    }
}

public class Principal {
    public static void main(String[] args) {
        Runnable tarea = new TareaReporte();
        Thread hilo = new Thread(tarea);
        hilo.start();
    }
}

start()

Solicita iniciar un nuevo hilo; la JVM invoca su método run() en ese flujo de ejecución.

run()

Contiene el trabajo. Llamarlo directamente es una llamada normal de método: no crea un hilo nuevo.

Estados de un hilo

En Java, Thread.State describe el ciclo de vida.

NEW

Nuevo

El objeto Thread existe, pero todavía no se ha iniciado.

RUNNABLE

Listo o ejecutándose

Puede estar ejecutándose o listo para recibir tiempo de CPU.

BLOCKED

Bloqueado

Espera entrar en una sección protegida por un monitor.

WAITING

Esperando

Espera una acción de otro hilo sin un límite de tiempo definido, por ejemplo, un join().

TIMED_WAITING

Espera temporal

Espera durante un tiempo, por ejemplo, con sleep(1000).

TERMINATED

Terminado

El método run() finalizó o terminó por una excepción no capturada.

El estado RUNNABLE no distingue entre “está usando CPU ahora” y “está listo para ejecutarse”.

Esperar por un hilo: join()

Coordinar el momento en que continúa la tarea principal.

Si una tarea principal necesita usar el resultado de una tarea de fondo, debe coordinar cuándo continúa. join() hace que el hilo que lo llama espere a que termine el hilo indicado. 

Thread hilo = new Thread(() -> {
    System.out.println("Calculando...");
});
hilo.start();

try {
    hilo.join();
    System.out.println("La tarea terminó.");
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    System.out.println("La espera fue interrumpida.");
}

¿Por qué se captura InterruptedException?

Porque la espera puede ser interrumpida. Si se decide no propagar la excepción, restablecer el indicador con interrupt() conserva la señal de interrupción.

Sobre la sintaxis lambda

Se muestra como una forma breve de expresar Runnable; la idea central es iniciar y coordinar el hilo.

¿Qué ocurre cuando dos hilos comparten datos?

Un incremento puede perder actualizaciones.

Supongamos que dos hilos intentan incrementar el mismo contador. La operación contador++ no es necesariamente atómica: conceptualmente lee, suma y escribe.

Hilo A
Lee 10
Hilo B
Lee 10
Hilo A
Escribe 11
Hilo B
Escribe 11

El resultado final podría ser 11 cuando se esperaban 12. Este tipo de error se conoce como condición de carrera: el resultado depende del orden de ejecución.

Riesgos

  • Actualizaciones perdidas.
  • Lecturas inconsistentes.
  • Resultados difíciles de reproducir.

Alternativas

  • Evitar compartir estado cuando sea posible.
  • Proteger secciones críticas con sincronización.
  • Usar clases concurrentes apropiadas.

Proteger una sección crítica con synchronized

Coordinar el acceso a un recurso compartido.

Una sección crítica es una parte del código que accede a un recurso compartido y que debe ejecutarse bajo una coordinación adecuada. 

class Contador {
    private int valor = 0;

    public synchronized void incrementar() {
        valor++;
    }

    public synchronized int obtener() {
        return valor;
    }
}

Qué aporta

En un mismo objeto, los métodos sincronizados coordinan el acceso mediante su monitor. Evita que dos hilos ejecuten simultáneamente esas secciones protegidas por el mismo monitor.

Qué no resuelve automáticamente

No corrige errores de lógica, no hace seguro todo el programa ni evita por sí solo todos los interbloqueos. También puede reducir el paralelismo si se usa demasiado.

El ejemplo ilustra sincronización básica. En sistemas reales también existen herramientas como AtomicInteger, bloqueos explícitos y colecciones concurrentes.

Clases activas: objetos con actividad propia

Reciben solicitudes y las procesan en su propio flujo de ejecución.

¿Qué es una clase activa?

Es un componente que tiene actividad propia: no solo guarda estado, también recibe solicitudes y las procesa mediante un hilo o una tarea de ejecución.

  • Recibe mensajes o llamadas.
  • Administra una cola o trabajadores.
  • Puede responder de inmediato o más tarde.

Objeto pasivo vs. clase activa

Objeto pasivo
Trabaja en el hilo del llamador
Clase activa
Recibe, encola y procesa en su propio flujo

La actividad no exige un hilo exclusivo: puede compartir un pool de trabajadores. 

class ServicioSolicitudes {
    private final ExecutorService workers =
        Executors.newFixedThreadPool(4);

    Future<Respuesta> recibir(Solicitud solicitud) {
        return workers.submit(() -> procesar(solicitud));
    }
}

Más adelante, en 7.3.2: el servidor de sockets es una clase activa. Escucha en un puerto, recibe conexiones y atiende cada solicitud en una tarea separada, mientras sigue aceptando nuevas conexiones.

¿Qué significa comunicarse dentro de una aplicación?

Componentes que colaboran mediante contratos claros.

En una aplicación modular, los componentes no deberían depender de detalles internos de otros componentes. Se comunican mediante contratos claros: métodos, interfaces, eventos o mensajes.

Llamada directa a un método

Un componente invoca una operación de otro objeto y normalmente espera su resultado.

Ejemplo: servicio.registrarSolicitud(datos).

Envío de mensajes o eventos

Un componente comunica que ocurrió algo o solicita una acción mediante un mensaje. El receptor puede procesarlo después.

Ejemplo: “SolicitudRegistrada”.

Idea clave: “local” describe que los componentes forman parte de la misma aplicación o entorno local. No implica necesariamente que estén en el mismo hilo.

¿Qué debe contener un mensaje bien diseñado?

Claro, estable y suficiente para el propósito.

Un mensaje es información que un componente entrega a otro para solicitar una operación o comunicar un hecho. Conviene que el formato sea claro, estable y suficiente para el propósito.

Identidad

Tipo o nombre que permite interpretar el mensaje. Ej.: CONSULTAR_ESTADO.

Datos

Valores necesarios para procesar la solicitud. Ej.: identificador de solicitud.

Resultado

Respuesta, confirmación o error con significado definido. Ej.: estado, código y descripción. 

// Ejemplo conceptual de un mensaje local
record SolicitudConsulta(String codigoSolicitud) {}
record RespuestaConsulta(String estado, String detalle) {}

Un record es una forma compacta de modelar datos en Java moderno. Si la versión del entorno no lo permite, puede utilizarse una clase con campos y métodos de acceso.

record RegistrarSolicitud(String codigo, String detalle) {}
record RespuestaRegistro(String codigo, String estado) {}

class BandejaSolicitudes {
    private final BlockingQueue<RegistrarSolicitud> solicitudes = new LinkedBlockingQueue<>();
    private final BlockingQueue<RespuestaRegistro> respuestas = new LinkedBlockingQueue<>();

    void enviar(RegistrarSolicitud s) { solicitudes.offer(s); }
    void responder(RespuestaRegistro r) { respuestas.offer(r); }

    RegistrarSolicitud recibir() throws InterruptedException { return solicitudes.take(); }
    RespuestaRegistro esperar() throws InterruptedException { return respuestas.take(); }
}

El emisor usa enviar y esperar; el servicio usa recibir y responder. La cola desacopla tiempos: la vista no ejecuta el procesamiento.

¿Cuándo necesitamos comunicación por red?

Cuando los componentes viven en programas o equipos distintos.

Cuando dos componentes se ejecutan en programas o equipos distintos, una llamada de método directa ya no basta. Necesitamos un mecanismo que transporte información entre los extremos.

Importante: un socket transporta datos; no define por sí solo qué significan esos datos. El programa debe acordar el protocolo.

¿Qué es un socket?

Un extremo de comunicación para enviar o recibir datos.

Un socket es un extremo de comunicación que una aplicación utiliza para enviar o recibir datos. En Java, las clases de java.net permiten crear conexiones de red.

Socket TCP

  • Comunicación orientada a conexión.
  • Entrega un flujo de bytes fiable y ordenado.
  • Es común para protocolos cliente-servidor.

ServerSocket

  • Se utiliza para escuchar conexiones entrantes TCP.
  • Se asocia a un puerto local.
  • Al aceptar un cliente, devuelve un Socket conectado.

TCP transporta bytes, no mensajes. La aplicación debe acordar cómo delimita cada mensaje: salto de línea, longitud prefijada o una estructura explícita como JSON. readLine() solo funciona si ambos lados usan el mismo delimitador.

La conexión no reemplaza el protocolo

TCP entrega bytes; la aplicación define los mensajes.

TCP entrega un flujo de bytes, no una colección automática de mensajes. Una lectura puede recibir menos bytes de los enviados, o puede agrupar datos que el emisor escribió en varias operaciones.

Error de suposición

“Hice un write(), por tanto el servidor recibirá exactamente un mensaje completo en un solo readLine()”.

Esto solo funciona si ambos lados implementan el mismo formato y delimitación.

Solución de diseño

Definir cómo termina cada mensaje: salto de línea, longitud prefijada o estructura de protocolo explícita.

En el ejemplo siguiente usaremos una línea terminada en salto de línea.

Acuerdos mínimos del protocolo de ejemplo

  • El cliente envía una línea de texto UTF-8.
  • El servidor responde con una línea.
  • Una solicitud equivale a una línea completa.
  • Si ocurre un error, se devuelve un mensaje comprensible y se cierran los recursos.

Servidor TCP sencillo en Java

Escucha, acepta un cliente, lee una línea y responde.

Este servidor escucha en el puerto 5000, acepta un cliente, lee una línea y devuelve una respuesta. Es un ejemplo didáctico de un solo cliente a la vez. 

import java.io.*;
import java.net.*;
import java.nio.charset.StandardCharsets;

public class Servidor {
    public static void main(String[] args) {
        try (ServerSocket servidor = new ServerSocket(5000)) {
            System.out.println("Servidor escuchando en 5000...");
            try (Socket cliente = servidor.accept();
                 BufferedReader entrada = new BufferedReader(
                     new InputStreamReader(
                         cliente.getInputStream(), StandardCharsets.UTF_8));
                 PrintWriter salida = new PrintWriter(
                     cliente.getOutputStream(), true,
                     StandardCharsets.UTF_8)) {
                String mensaje = entrada.readLine();
                salida.println("Servidor recibió: " + mensaje);
            }
        } catch (IOException e) {
            System.err.println("Error del servidor: " + e.getMessage());
        }
    }
}

La variante de PrintWriter con Charset está disponible en Java moderno. En versiones anteriores se puede crear un OutputStreamWriter con UTF-8 y envolverlo en un BufferedWriter.

Cliente TCP que envía una solicitud

Conecta, escribe una línea, lee la respuesta y cierra.

El cliente conoce el host y el puerto del servidor. Abre la conexión, escribe una línea, lee la respuesta y cierra sus recursos. 

import java.io.*;
import java.net.*;
import java.nio.charset.StandardCharsets;

public class Cliente {
    public static void main(String[] args) {
        try (Socket socket = new Socket("localhost", 5000);
             BufferedReader entrada = new BufferedReader(
                 new InputStreamReader(
                     socket.getInputStream(), StandardCharsets.UTF_8));
             PrintWriter salida = new PrintWriter(
                 socket.getOutputStream(), true,
                 StandardCharsets.UTF_8)) {
            salida.println("CONSULTAR_ESTADO");
            String respuesta = entrada.readLine();
            System.out.println("Respuesta: " + respuesta);
        } catch (IOException e) {
            System.err.println("No se pudo comunicar: " + e.getMessage());
        }
    }
}

Orden correcto

  1. Ejecutar el servidor.
  2. Ejecutar el cliente.
  3. Revisar la salida de ambos.

¿Por qué localhost?

Se refiere al mismo equipo donde se ejecuta el cliente. Para equipos distintos se necesita la dirección del servidor y una configuración de red adecuada.

¿Qué pasa si llegan varios clientes?

Un servidor real permanece escuchando y decide cómo atender.

El servidor anterior atiende un cliente y termina. Un servidor real suele permanecer escuchando y necesita decidir cómo manejar varias conexiones.

Si una solicitud tarda mucho, las siguientes deben esperar.

Servidor con hilos

Puede atender conexiones de forma concurrente, según los recursos disponibles. 

try (ServerSocket servidor = new ServerSocket(5000)) {
    while (true) {
        Socket cliente = servidor.accept();
        Thread hilo = new Thread(() -> atender(cliente));
        hilo.start();
    }
}

Fragmento conceptual: atender(cliente) debe implementar el protocolo y cerrar el socket incluso si ocurre un error. En producción conviene limitar recursos mediante un pool de hilos, manejar el apagado y aplicar controles de seguridad.

Qué se comparte

  • El puerto que escucha.
  • El pool de hilos o trabajadores.

  • Cliente lento o desconectado.

while (true) {
    Socket cliente = servidor.accept();
    trabajadores.submit(() -> atender(cliente));

Si atender se ejecuta en el hilo que acepta, el servidor vuelve a ser secuencial. El pool limita los recursos y permite atender varias conexiones.

Un servidor no solo debe “funcionar”

Recursos, errores y seguridad.

Recursos

  • Cerrar sockets y flujos.
  • Evitar crear hilos ilimitados.
  • Definir tiempos de espera.

Errores

  • Capturar y registrar fallos.
  • No asumir que el cliente siempre responde.
  • Definir qué pasa si se corta la conexión.

Seguridad

  • Validar los mensajes recibidos.
  • No confiar en datos del cliente.
  • No exponer servicios en interfaces de red innecesarias.

TCP no cifra los datos por sí mismo. En aplicaciones que transportan información sensible se necesita diseñar una protección apropiada, por ejemplo, mediante TLS y controles de autenticación y autorización.

¿Dónde se usan estas ideas?

Cuatro escenarios habituales.

Aplicaciones distribuidas

Un cliente de escritorio solicita datos a un servicio remoto, que consulta una base de datos y responde.

Intervienen red, protocolo, errores de conexión y validación.

Operaciones asíncronas

Una aplicación registra una solicitud de generación de reporte y continúa con otras tareas mientras se procesa.

Intervienen estados, notificaciones y manejo de fallos.

Servidores

Un proceso escucha en un puerto y atiende conexiones de distintos clientes.

Intervienen sockets, concurrencia y límites de recursos.

Trabajo de fondo

Una interfaz descarga datos o prepara un archivo sin congelarse durante la operación.

Intervienen hilos, coordinación y comunicación con la interfaz.
