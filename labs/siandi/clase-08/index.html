Introducción al Laboratorio

En el laboratorio anterior armaron la Arquitectura MVC del Mini-Discord: la Vista captura el clic, el Controlador delega, el Service valida y el ObservableList repinta la pantalla sola gracias al patrón Observer. Todo eso funciona perfectamente... hasta que cierran la aplicación. En ese momento, todos los mensajes desaparecen, porque viven únicamente en la memoria RAM.

Hoy van a cerrar ese círculo. Message y User ya implementan Serializable desde la semana pasada, pero esa promesa nunca se cumplió: nadie ha escrito esos objetos a disco todavía. Van a construir dos formas de persistencia — una binaria (rápida, para uso interno del programa) y una en XML (legible, usando un DTO) — y, de paso, van a entender la diferencia real entre un DAO y un DTO, dos siglas que se confunden todo el tiempo.

Enfoque Pedagógico: Este manual no solo le muestra QUÉ escribir. En cada paso va a encontrar una caja morada titulada "¿Cómo se llega a esta decisión?" — ahí se explica el razonamiento que lleva de un problema a la solución, para que la próxima vez que enfrenten un problema parecido (aunque no sea exactamente este), sepan cómo pensarlo desde cero. Además, dentro del código van a ver comentarios en verde y en negrita que dicen "Nuevo de la clase 8: ..." — esos marcan exactamente qué línea es nueva de hoy. Los comentarios grises normales son código que ya existía desde el laboratorio anterior y no cambió.

¿Cómo se llega a esta decisión?

Antes de escribir código, siempre pregúntense: "¿qué capa es responsable de este problema?". Persistir datos es un problema de la capa de Datos. Por eso todo lo que construyan hoy relacionado con guardar/leer archivos va a vivir en data.dao, nunca en el Controller ni en el Service. Esta pregunta — "¿de quién es este problema?" — es la herramienta mental más útil de todo el curso.

Paso 2: Construir el MessageDAO (persistencia binaria)

2.1 Diseñar la firma de los métodos ANTES de programar

Es tentador abrir MessageDAO.java y empezar a escribir código de una vez. Resistan esa tentación un minuto y respondan primero: ¿qué necesita el Controller pedirle al DAO? Necesita poder guardar el historial completo, y poder recuperarlo completo al iniciar. Nada más, nada menos.

¿Cómo se llega a esta decisión?

Podrían haber diseñado guardarUno(Message m) y cargarUno(int id) en su lugar. ¿Por qué no? Porque en esta etapa del Mini-Discord no hay una base de datos con identificadores únicos — solo hay una lista completa de mensajes en memoria. Diseñar la interfaz del DAO significa preguntarse "¿cómo está organizada la información en el lado que la usa (el Controller)?" y calcar esa forma. Si mañana agregan una base de datos, ahí sí tendría sentido guardar/cargar de uno en uno — por ahora, sería complejidad que no necesitan.

Con eso decidido, la firma queda así:

  • void guardarTodos(List<Message> mensajes) — recibe el historial completo y lo persiste.
  • List<Message> cargarTodos() — devuelve el historial completo (o una lista vacía si todavía no hay nada guardado).
2.2 Implementar guardarTodos()

Abran MessageDAO.java y escriban:

MessageDAO.java
package cr.ac.una.est.minidiscord.data.dao;

import cr.ac.una.est.minidiscord.business.model.Message;
import java.io.*;
import java.util.ArrayList;
import java.util.List;

// Nuevo de la clase 8: este archivo estaba vacío — hoy se implementa toda la persistencia binaria.
// Esta clase es la ÚNICA responsable de saber CÓMO se guardan y se leen los mensajes.
// Ni el Service ni el Controller deben saber que existe un archivo llamado "mensajes.dat".
public class MessageDAO {

    private static final String ARCHIVO = "mensajes.dat";

    public void guardarTodos(List<Message> mensajes) {
        try (ObjectOutputStream salida = new ObjectOutputStream(new FileOutputStream(ARCHIVO))) {
            salida.writeObject(new ArrayList<>(mensajes));
        } catch (IOException e) {
            System.out.println("No se pudo guardar el historial: " + e.getMessage());
        }
    }
}
Ver explicación del código línea por línea.

try (ObjectOutputStream ...): Es un try-with-resources. Java cierra automáticamente el archivo al salir del bloque, incluso si ocurre un error a la mitad de la escritura. Sin esto, tendrían que acordarse de llamar salida.close() manualmente en un finally — y es muy fácil olvidarlo, dejando el archivo "trabado".

salida.writeObject(...): Esta única línea serializa TODA la lista de una vez — cada Message, con su User adentro, se convierte en bytes automáticamente. Java recorre el grafo de objetos completo porque tanto Message como User implementan Serializable.

new ArrayList<>(mensajes): Se envuelve la lista recibida en un ArrayList nuevo (en vez de serializar directamente un ObservableList) porque ObservableList no es Serializable — es una clase especial de JavaFX pensada para la interfaz gráfica, no para guardarse en disco.

¿Cómo se llega a esta decisión?

El detalle del ArrayList nuevo no es obvio la primera vez — normalmente se descubre por prueba y error: si intentan serializar el ObservableList directamente, van a obtener un NotSerializableException en tiempo de ejecución. Ese mensaje de error es una pista, no un fracaso: les está diciendo exactamente qué clase no puede convertirse a bytes. Aprender a leer el nombre de la excepción y buscar qué clase la origina es una destreza que van a usar todo el semestre.

2.3 Implementar cargarTodos() — pensando primero en el caso frontera

Antes de escribir el "camino feliz" (el archivo ya existe y se lee bien), pregúntense: ¿qué pasa la PRIMERA vez que alguien ejecuta el programa? El archivo mensajes.dat todavía no existe. Si intentan abrirlo igual, el programa truena con un FileNotFoundException apenas lo abran — y eso pasaría siempre en la primera ejecución de cada compañero que pruebe el proyecto.

MessageDAO.java (continuación)
    // Nuevo de la clase 8: continúa el mismo MessageDAO — método para leer el historial guardado
    @SuppressWarnings("unchecked")
    public List<Message> cargarTodos() {
        File archivo = new File(ARCHIVO);
        if (!archivo.exists()) {
            return new ArrayList<>(); // primera ejecución: no hay nada guardado todavía
        }
        try (ObjectInputStream entrada = new ObjectInputStream(new FileInputStream(archivo))) {
            return (List<Message>) entrada.readObject();
        } catch (IOException | ClassNotFoundException e) {
            System.out.println("No se pudo leer el historial: " + e.getMessage());
            return new ArrayList<>();
        }
    }
}
Ver explicación del código línea por línea.

@SuppressWarnings("unchecked"): Java no puede verificar en tiempo de compilación que lo que devuelve readObject() sea realmente un List<Message> (esa información de tipo genérico se pierde al serializar). Esta anotación silencia la advertencia del compilador porque nosotros sabemos con certeza qué guardamos ahí — fuimos nosotros quienes lo escribimos con guardarTodos.

if (!archivo.exists()): Este es el caso frontera resuelto ANTES de tocar el archivo. Nunca lanza una excepción por algo tan predecible como "todavía no existe" — devuelve una lista vacía, que es un resultado perfectamente válido y esperado.

catch (IOException | ClassNotFoundException e): ClassNotFoundException puede ocurrir si el archivo fue guardado con una versión anterior de la clase Message que ya no coincide con la actual — es el tipo de error que van a ver en el mundo real cuando una aplicación evoluciona pero los datos guardados no.

2.4 Conectar el DAO con el Controller

Abran ChatViewController.java y agreguen una instancia del DAO y una lista "espejo" con los objetos Message reales (el ObservableList actual solo guarda String, y el DAO necesita los objetos completos para poder volver a serializarlos):

ChatViewController.java
// Nuevo de la clase 8: instancia del DAO para poder guardar y cargar el historial
private final MessageDAO messageDAO = new MessageDAO();
// Nuevo de la clase 8: lista "espejo" con los objetos Message reales — el DAO necesita
// los objetos completos, el ObservableList de abajo solo guarda el texto para pintar la pantalla
private final List<Message> historial = new ArrayList<>();

@FXML
public void initialize() {
    messageListView.setItems(messages); // esta línea ya existía la clase pasada

    // Nuevo de la clase 8: al abrir la ventana, se pide el historial guardado y se muestra de una vez
    for (Message m : messageDAO.cargarTodos()) {
        historial.add(m);
        messages.add(m.toString());
    }
}

@FXML
private void handleSendMessage() {
    try {
        // esta línea ya existía la clase pasada, no cambió
        Message nuevoMsg = chatService.processMessage(currentUser, messageInputField.getText());
        // Nuevo de la clase 8: guardamos también el objeto de dominio (no solo el texto)
        historial.add(nuevoMsg);
        // estas dos líneas ya existían la clase pasada, no cambiaron
        messages.add(nuevoMsg.toString());
        messageInputField.clear();

        // Nuevo de la clase 8: se persiste el historial completo cada vez que se agrega un mensaje válido
        messageDAO.guardarTodos(historial);
    } catch (IllegalArgumentException e) {
        System.out.println("Aviso de Validación: " + e.getMessage()); // ya existía
    }
}
Ver explicación del código línea por línea.

@FXML public void initialize(): Este método lo llama automáticamente el FXMLLoader DESPUÉS de inyectar todos los campos @FXML (como messageListView). Por eso el DAO se consulta aquí y no en el constructor: en el constructor, messageListView todavía sería null, porque JavaFX aún no ha terminado de leer el FXML.

historial vs. messages: son dos colecciones con propósitos distintos. messages (ObservableList<String>) es solo para PINTAR la pantalla. historial (List<Message>) es la fuente de verdad que se persiste. Nunca se persiste directamente lo que se muestra en pantalla — se persisten los datos de dominio.

¡A probar! Ejecuten App, envíen 2 o 3 mensajes, cierren la ventana y vuelvan a ejecutar. Los mensajes anteriores deben seguir apareciendo. Si no aparecen, revisen primero si se creó el archivo mensajes.dat en la raíz del proyecto.

Paso 3: DAO vs. DTO — antes de tocar código, entender la diferencia

Van a construir una segunda forma de persistencia en XML. Antes de escribir nada, es importante distinguir dos siglas que se confunden todo el tiempo: DAO (Data Access Object, lo que acaban de construir) y DTO (Data Transfer Object, lo que van a construir ahora).

DAODTO
Qué esUna clase CON lógica: sabe leer y escribir datos.Una clase plana SIN lógica: solo atributos y getters/setters.
Responde a"¿CÓMO se guarda o se lee la información?""¿QUÉ datos viajan, sin exponer el dominio completo?"

AnalogíaEl camión repartidor: sabe manejar y conoce la ruta.La caja de cartón dentro del camión: no maneja nada, solo contiene el producto.
3.1 El problema: XMLEncoder no entiende a Message

Podrían pensar: "ya tengo Message serializable, ¿por qué no lo exporto directo a XML?". Inténtenlo y van a chocar con un problema: XMLEncoder (la herramienta nativa de Java para exportar a XML) exige que la clase tenga un constructor vacío y setters para cada atributo — porque reconstruye el objeto llamando al constructor vacío y después "rellenando" cada campo con su setter.

Message no tiene nada de eso a propósito: su único constructor exige author y content, y sus campos son final (inmutables, sin setters). Esa inmutabilidad la diseñaron con intención la semana pasada, para evitar que un mensaje cambie después de creado.

¿Cómo se llega a esta decisión?

La primera reacción de casi todo el mundo es "voy a agregarle un constructor vacío y setters a Message para que XMLEncoder lo acepte". Eso sería un error de diseño: estarían debilitando el Modelo de dominio (quitándole la inmutabilidad que le da seguridad) solo para satisfacer una herramienta externa de un formato de archivo específico. La regla general es: el dominio nunca se deforma para acomodar una tecnología de infraestructura. La solución correcta es crear una clase paralela, que solo existe para el viaje: el DTO.

3.2 Crear MessageDTO.java

En el paquete business.dto (nuevo — créenlo), agreguen:

MessageDTO.java
package cr.ac.una.est.minidiscord.business.dto;

// Nuevo de la clase 8: archivo (y paquete business.dto) completos — no existían la clase pasada
public class MessageDTO {

    private String autor;
    private String contenido;

    // XMLEncoder necesita este constructor vacío para poder reconstruir el objeto
    public MessageDTO() { }

    public MessageDTO(String autor, String contenido) {
        this.autor = autor;
        this.contenido = contenido;
    }

    public String getAutor() { return autor; }
    public void setAutor(String autor) { this.autor = autor; }

    public String getContenido() { return contenido; }
    public void setContenido(String contenido) { this.contenido = contenido; }
}
Ver explicación del código línea por línea.

Noten lo que NO tiene esta clase: ningún if, ninguna validación, ninguna referencia a User ni a ChatService. Un DTO es deliberadamente "tonto" — es una caja de transporte, no un objeto de negocio. Si alguna vez sienten la tentación de agregarle lógica a un DTO, esa lógica probablemente pertenece a otra clase.

¿Por qué autor es un String y no un User completo? Porque el DTO solo lleva lo mínimo necesario para reconstruir la información en el otro extremo — exponer todo el objeto User (que en el futuro podría tener contraseña, correo, etc.) sería filtrar más del dominio de lo que el archivo XML necesita saber.

3.3 Crear MessageXmlExporter.java (el DAO de la versión XML)

En data.dao, junto a MessageDAO, agreguen:

MessageXmlExporter.java
package cr.ac.una.est.minidiscord.data.dao;

import cr.ac.una.est.minidiscord.business.dto.MessageDTO;
import cr.ac.una.est.minidiscord.business.model.Message;
import java.beans.XMLEncoder;
import java.io.*;
import java.util.ArrayList;
import java.util.List;

// Nuevo de la clase 8: archivo completo — el "DAO" de la versión en XML, junto a MessageDAO
public class MessageXmlExporter {

    private static final String ARCHIVO_XML = "mensajes.xml";

    public void exportar(List<Message> mensajes) {
        List<MessageDTO> dtos = new ArrayList<>();
        for (Message m : mensajes) {
            // El DAO CONVIERTE el dominio (Message) a un DTO antes de exportarlo
            dtos.add(new MessageDTO(m.getAuthor().getUsername(), m.getContent()));
        }

        try (XMLEncoder encoder = new XMLEncoder(new BufferedOutputStream(new FileOutputStream(ARCHIVO_XML)))) {
            encoder.writeObject(dtos); // lo que realmente viaja al archivo es el DTO, no el Message
        } catch (IOException e) {
            System.out.println("No se pudo exportar a XML: " + e.getMessage());
        }
    }
}
Ver explicación del código línea por línea.

m.getAuthor().getUsername(): para leer estos valores, Message necesita exponer getAuthor() y getContent(). Si su Message de la semana pasada no los tenía, agréguenlos ahora — son getters de solo lectura, no rompen la inmutabilidad (no hay setters).

El ciclo completo: Message (dominio, inmutable) → se CONVIERTE a MessageDTO (plano, mutable) → SOLO el DTO se le entrega a XMLEncoder. El dominio nunca toca directamente la herramienta de serialización.

¿Cómo se llega a esta decisión?

¿Por qué esta clase se llama "Exporter" y no "DAO"? Cualquier nombre sirve mientras el equipo lo entienda, pero fíjense en el patrón: esta clase, igual que MessageDAO, vive en data.dao porque cumple el mismo rol arquitectónico — sabe CÓMO persistir datos, solo que en un formato distinto. El nombre de la clase es una etiqueta; lo que define su capa es su responsabilidad.

Paso 4 (Opcional): PersistenceManager — Patrón Singleton

Este paso es un reto opcional. Ahora mismo, cada clase que necesita persistencia crea su propia instancia de MessageDAO con new MessageDAO(). Funciona bien porque el proyecto es pequeño, pero imaginen que en el futuro agregan UserDAO, ConfigDAO, etc., y varias clases distintas intentan escribir al mismo tiempo en la misma carpeta de datos — ahí es donde conviene centralizar el acceso.

¿Cómo se sabe que este es el momento de usar un Singleton?

La pregunta que activa este patrón es: "¿le conviene a mi aplicación que exista MÁS de una instancia de esta clase al mismo tiempo?" Si la respuesta es "no, y además tener dos causaría problemas (como pisarse al escribir el mismo archivo)", ahí es donde el patrón Singleton (categoría creacional: resuelve CÓMO se instancian los objetos) resuelve exactamente ese problema.

PersistenceManager.java
package cr.ac.una.est.minidiscord.data.dao;

// Nuevo de la clase 8 (opcional): archivo completo — Singleton que centraliza el acceso al MessageDAO
public class PersistenceManager {

    private static PersistenceManager instancia;
    private final MessageDAO dao;

    // Constructor PRIVADO: nadie fuera de esta clase puede hacer "new PersistenceManager()"
    private PersistenceManager() {
        this.dao = new MessageDAO();
    }

    public static synchronized PersistenceManager getInstance() {
        if (instancia == null) {
            instancia = new PersistenceManager();
        }
        return instancia;
    }

    public MessageDAO getMessageDAO() { return dao; }
}
Ver explicación del código línea por línea.

private PersistenceManager(): el constructor privado es lo que hace imposible que otra clase escriba new PersistenceManager() — es la regla que garantiza que solo pueda existir una instancia.

if (instancia == null): se crea la única instancia la PRIMERA vez que alguien llama getInstance() (inicialización perezosa). Las siguientes llamadas devuelven siempre la misma instancia ya creada.

synchronized: protege el método para que, si dos hilos llamaran getInstance() exactamente al mismo tiempo, no terminen creando dos instancias por accidente. No es el foco de hoy, pero es la razón técnica de por qué aparece esa palabra.

Para usarlo, reemplacen en el Controller new MessageDAO() por PersistenceManager.getInstance().getMessageDAO().
