Antes de MySQL: ¿qué es, literalmente, una base de datos?

La definición que deberían poder repetir de memoria, sin tecnicismos.

"Una base de datos es una colección organizada de información, guardada de forma que se pueda buscar, agregar, modificar y borrar fácilmente — sin tener que leer todo desde el principio cada vez."

Agenda de contactos del celular

Cada contacto es una fila. Nombre, teléfono, correo son las columnas. Buscar "Ana" no obliga a leer los 500 contactos en orden.

Hoja de cálculo compartida

Varias personas la consultan y editan al mismo tiempo, sin mandarse el archivo por correo cada vez que algo cambia.

Archivador de oficina

Carpetas organizadas por categoría, no una pila de papeles sueltos. La organización es lo que hace rápida la búsqueda.

Mini-Discord YA tiene algo parecido, desde la Semana 8 — pero le faltan piezas

mensajes.dat y mensajes.xml ya son "información organizada guardada en disco". Lo que NO tienen es:

  • Acceso simultáneo: solo una aplicación, en una sola computadora, puede leer/escribir ese archivo a la vez.
  • Relaciones sin duplicar: si quisieran relacionar mensajes con usuarios sin repetir datos, tendrían que programarlo todo a mano.
  • Búsquedas rápidas: para buscar un mensaje hay que leer el archivo completo, no hay forma de "saltar" directo al dato.

Eso es exactamente lo que resuelve una base de datos relacional como MySQL.

El SABD: el programa que administra esos datos

Los datos y el programa que los cuida no son la misma cosa.

SABD = Sistema Administrador de Bases de Datos. Es el software — no los datos en sí — que crea, organiza, protege y da acceso a la base de datos. MySQL es un SABD: uno entre varios que existen.

Mientras el SABD esté corriendo en segundo plano, cualquier cliente — la app de Java, Workbench, o incluso otra computadora en la red — se puede conectar a pedirle o guardarle datos. Por eso, más adelante en el curso, van a ver que ese servicio también puede vivir en otra computadora distinta — una base de datos remota — no necesariamente en la misma máquina donde corre la aplicación.

El modelo de objetos y el modelo relacional no hablan el mismo idioma

A esa fricción se le llama "impedance mismatch" (desajuste de impedancia).

Modelo de objetos (Java)

  • Un Message contiene una referencia directa a un User.
  • La relación entre objetos es navegación por referencia (m.getAuthor().getUsername()).
  • Soporta herencia, polimorfismo, encapsulamiento.

Modelo relacional (Codd, 1970)

  • Todo es una tabla (filas y columnas). No hay objetos ni referencias.
  • Las relaciones se expresan con llaves foráneas (un número que apunta al id de otra tabla).
  • No sabe qué es herencia ni polimorfismo — solo filas.

El mismo dato, en los dos modelos

PK = llave primaria (identifica la fila, única y nunca vacía) · FK = llave foránea (un número que apunta al id de otra tabla — así se representa una relación sin repetir datos)

¿Y cómo desaparece esa fricción?

No desaparece sola — se traduce a mano, en código, en las dos direcciones.

Al guardar (objeto → tabla)

El User completo NO se guarda dentro de mensajes. Solo se extrae su id y se guarda como usuario_id, con un INSERT.

Al leer (tabla → objeto)

No hay referencia automática. Hay que reconstruirla: un JOIN trae usuario y mensaje juntos, y código Java arma de nuevo el objeto Message con su User adentro.

A esa reconstrucción se le llama mapeo de datos — y es justo lo que van a programar hoy en obtenerTodos(). No es un detalle opcional: sin ese código, la impedancia no se resuelve sola.

Pregunta para la clase:

Con el MessageDAO binario de la Semana 8, ¿cómo "viajaba" la relación Message→User? ¿Y ahora, con una tabla?

Antes: el objeto User completo iba serializado DENTRO del Message (referencia en memoria/bytes). Ahora: la tabla mensajes solo guarda un número (usuario_id) que apunta al id de la tabla usuarios — la relación es un JOIN, no una referencia.

Reglas para que una tabla no repita ni contradiga información.

"ana" se repite en cada fila. Si cambia su nombre de usuario, hay que actualizar N filas — y si alguien escribe mal "ana" en una fila, el dato queda inconsistente.

Antes de las tres reglas: ¿qué significa "depende de"?

Decimos que la columna B depende de la columna A cuando, sabiendo el valor de A, se puede saber EXACTAMENTE el valor de B, sin ambigüedad. Ejemplo: sabiendo el id de un mensaje, ¿se sabe su contenido? Sí, exactamente uno — por eso contenido depende de id. Las tres reglas de la siguiente diapositiva son solo una forma ordenada de revisar esto, columna por columna.

1FN, 2FN, 3FN — las reglas aplicadas

El mismo criterio de la diapositiva anterior, en tres pasos concretos.

1FN

Cada columna guarda un solo valor atómico (nada de "ana,pedro" en una celda).

2FN

Todo atributo depende de la llave completa (aplica sobre todo con llaves compuestas).

3FN

Ningún atributo depende de otro atributo que no sea la llave (sin dependencias transitivas).

JDBC: el puente entre Java y MySQL

Java Database Connectivity — una API estándar, un driver distinto por motor de BD.

JDBC define QUÉ se puede hacer (conectar, consultar, actualizar) de forma genérica. El driver — el mysql-connector-j que agregan al pom.xml — es la pieza que sabe CÓMO decírselo específicamente a MySQL.

El control remoto (analogía)

Aprietan "subir volumen" sin saber qué circuito se activa adentro. JDBC es ese botón: métodos con nombre fijo que alguien más ya construyó — ustedes los llaman, no ven el código de adentro.

Si cambiaran de motor de BD

Cambiarían el driver (otro .jar), pero el código Java que llama a la API de JDBC casi no cambia. Esa es la ventaja de programar contra una API y no contra un motor específico.

JDBC en código: las 4 piezas

El mismo patrón se repite en guardar() y en obtenerTodos().

DriverManager.getConnection(url, user, pass) Connection PreparedStatement ResultSet
Ejemplo mínimo
String url = "jdbc:mysql://localhost:3306/minidiscord"; // protocolo jdbc + máquina + puerto + nombre de la BD
try (Connection con = DriverManager.getConnection(url, "root", "clave")) { // abre la conexión; se cierra sola al salir
    String sql = "INSERT INTO mensajes (usuario_id, contenido) VALUES (?, ?)"; // el SQL con huecos: los valores van después
    try (PreparedStatement stmt = con.prepareStatement(sql)) { // prepara la instrucción; se cierra sola
        stmt.setInt(1, usuarioId); // llena el ? 1 con el id (int)
        stmt.setString(2, contenido); // llena el ? 2 con el texto, aparte del SQL = sin inyección
        stmt.executeUpdate(); // ejecuta el INSERT; devuelve cuántas filas cambió
    } // cierra el PreparedStatement
} // cierra la Connection

PreparedStatement, no Statement: los ? se rellenan de forma segura — evita inyección SQL (concatenar el texto del usuario directo en el SQL es una vulnerabilidad real, no un detalle académico).

DLM vs. DDL — no son lo mismo

DDL (Data Definition Language) define la estructura: CREATE TABLE, ALTER TABLE. DLM (Data Manipulation Language) manipula los datos que ya viven dentro de esa estructura: INSERT, SELECT, UPDATE, DELETE. La próxima sesión, cuando conecten MySQL de verdad, van a usar un poco de DDL (crear las tablas, una sola vez) y el resto del curso van a usar sobre todo DLM (desde el código Java).

Hoy van a crear MessageRepository, una interfaz con los métodos que el Controller necesita. MessageDAO (binario, Semana 8) y el nuevo JdbcMessageRepository (MySQL, hoy) pueden implementarla por igual — el Controller nunca se entera de cuál está usando.

Glosario de Términos Clave — Semana 11

  • SABD: Sistema Administrador de Bases de Datos — el motor que guarda, organiza y protege los datos (MySQL, en este curso).
  • Impedance mismatch: la fricción entre el modelo de objetos (Java) y el modelo relacional (tablas).
  • Normalización: reglas (1FN, 2FN, 3FN) para eliminar redundancia e inconsistencia en las tablas.
  • Llave primaria (PK): columna (o combinación de columnas) que identifica de forma única cada fila — no se repite entre filas y no puede quedar vacía.
  • Llave compuesta: una llave primaria formada por dos o más columnas juntas (ninguna por separado identifica la fila, solo la combinación de ambas). Ejemplo: en una tabla de "inscripciones", la fila la identifica (estudiante_id, curso_id) junta, no cada una por su lado.
  • Llave completa: término que se usa al hablar de 2FN — significa "todas las columnas que forman la llave primaria", en contraste con solo una parte de una llave compuesta. Un atributo "depende de la llave completa" cuando necesita las DOS columnas de la llave compuesta para determinarse; si le alcanza con una sola, viola 2FN.
  • Llave foránea (FK): columna que referencia la PK de otra tabla — así se modelan las relaciones.
  • API (Application Programming Interface): un conjunto de métodos ya definidos (nombre, parámetros, qué devuelven) que alguien más construyó para que otro programa los use, sin tener que saber cómo están implementados por dentro. Ejemplo: DriverManager.getConnection(...) es parte de la API de JDBC — la llaman, pero no ven ni tocan su código interno.
  • JDBC: Java Database Connectivity — la API estándar de Java para hablar con cualquier motor de base de datos.
  • DLM: Data Manipulation Language — INSERT, SELECT, UPDATE, DELETE (manipula datos, no estructura).
  • IMEC: Insertar, Mostrar, Editar, Cancelar — el CRUD en español, tal como aparece en el programa del curso.
  • Repository / DAO: patrón que aísla el "cómo se accede a los datos" detrás de una interfaz intercambiable.

La forma insegura: concatenar el texto del usuario

Este código funciona, pero el texto del usuario se mete DENTRO del SQL — y lo que escriba se interpreta como parte del comando.

Inseguro.java
String url = "jdbc:mysql://localhost:3306/minidiscord";
try (Connection con = DriverManager.getConnection(url, "root", "clave")) {
    String sql = "INSERT INTO mensajes (usuario_id, contenido) VALUES (" + usuarioId + ", '" + contenido + "')"; // ⚠ el texto del usuario va DENTRO del SQL
    try (Statement stmt = con.createStatement()) { // Statement simple: no hay huecos ?
        stmt.executeUpdate(sql); // ejecuta el SQL tal cual quedó concatenado
    }
}
El ataque
// Si el usuario escribe esto en el campo contenido:
hola'); DROP TABLE mensajes; --
// el SQL final que se ejecuta queda así:
INSERT INTO mensajes (usuario_id, contenido) VALUES (1, 'hola'); DROP TABLE mensajes; --')
// ← primero inserta 'hola' y después ¡BORRA la tabla mensajes!

¿La diferencia con el código seguro? Allá los valores van con ? y setString, separados del SQL. Aquí van dentro de la cadena: la comilla ' del atacante no se escapa, se interpreta.
