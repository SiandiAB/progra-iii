Es un archivo de texto con sentencias SQL que se ejecutan en orden, de arriba a abajo. Nosotros lo escribimos una vez y lo podemos volver a ejecutar cuando queramos: todas las sentencias están protegidas (IF NOT EXISTS, DROP ... IF EXISTS) para que no fallen al repetirse.

Paso 3 · Sección 1 · La base de datos y la tabla

Esta es la primera sección del script. Cópiela tal cual en database/01_flota_segura.sql, debajo de la banda de comentarios de la sección 1.

3.1 CREATE DATABASE — crear la base de datos
CREATE DATABASE IF NOT EXISTS flota_vehicular CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
  • CREATE DATABASE flota_vehicular → crea un esquema: una “carpeta” que contiene tablas y procedimientos.
  • IF NOT EXISTS → si ya existe, no da error. Así el script se puede ejecutar muchas veces.
  • CHARACTER SET utf8mb4 → guarda bien acentos, ñ y emojis. Con un juego viejo como latin1 los acentos se verían como Ã±.
3.2 USE — seleccionar la base activa
USE flota_vehicular;

Todas las sentencias siguientes se aplican a esa base, sin repetir flota_vehicular. delante de cada nombre. Sin esta línea nada funcionaría, porque MySQL no sabría en qué base trabajar.

3.3 CREATE TABLE vehiculo — escribirla completa
CREATE TABLE IF NOT EXISTS vehiculo ( placa VARCHAR(12) PRIMARY KEY, marca VARCHAR(80) NOT NULL, kilometraje INT NOT NULL, estado ENUM('DISPONIBLE','EN_RUTA','TALLER') NOT NULL, tipo ENUM('COMBUSTION','ELECTRICO','PESADO') NOT NULL, nivel_energia DECIMAL(5,2) NOT NULL, ciclos_carga INT NOT NULL DEFAULT 0, tonelaje_maximo DECIMAL(8,2) NULL, carga_actual DECIMAL(8,2) NULL, tipo_carga ENUM('NORMAL','PELIGROSA','REFRIGERADA') NULL, CONSTRAINT chk_kilometraje CHECK (kilometraje >= 0), CONSTRAINT chk_energia CHECK (nivel_energia >= 0 AND nivel_energia <= 100), CONSTRAINT chk_ciclos CHECK (ciclos_carga >= 0), CONSTRAINT chk_pesado CHECK ((tipo = 'PESADO' AND tonelaje_maximo > 0 AND carga_actual >= 0 AND tipo_carga IS NOT NULL) OR (tipo <> 'PESADO' AND tonelaje_maximo IS NULL AND carga_actual IS NULL AND tipo_carga IS NULL)) );

Ahora, columna por columna, qué significa cada una:

ColumnaTipoPor qué existe
placaVARCHAR(12)Identifica cada vehículo. Es la clave primaria.
marcaVARCHAR(80)Texto libre, pero obligatorio (NOT NULL).
kilometrajeINTEntero: no tiene sentido un kilómetro con decimales.
estadoENUM(...)Solo permite los tres valores del enum EstadoVehiculo de su modelo.
tipoENUM(...)Corresponde a TipoVehiculo. Es la columna que decide qué subclase reconstruir.
nivel_energiaDECIMAL(5,2)Combustible o batería, según el tipo. Hasta 999.99 con 2 decimales.
ciclos_cargaINT DEFAULT 0Solo lo usa el eléctrico. El valor por defecto evita enviarlo siempre.
tonelaje_maximoDECIMAL(8,2) NULLSolo lo usa el pesado. Por eso admite NULL.
carga_actualDECIMAL(8,2) NULLSolo lo usa el pesado.
tipo_cargaENUM(...) NULLSolo lo usa el pesado.
Observe el patrón: las tres últimas columnas son NULL porque no todos los vehículos tienen esos datos. En objetos eso lo resuelven la herencia y las subclases; en una tabla plana, columnas opcionales. Ese es el desfase objeto–relacional que vimos en clase.
3.4 placa PRIMARY KEY — la clave primaria

Una clave primaria hace dos cosas a la vez: identifica la fila y prohíbe duplicados.

Es decir: aunque Java olvide validar, la base no aceptará dos vehículos con la misma placa. Y eso importa porque dos personas podrían registrar la misma placa al mismo tiempo: la validación en memoria de cada programa no basta.

3.5 Las cuatro restricciones CHECK

Van al final, dentro del mismo CREATE TABLE. Ya están incluidas en el bloque de arriba; esto es lo que hace cada una:

RestricciónQué impide
chk_kilometrajeQue el kilometraje sea negativo.
chk_energiaQue el nivel de energía (o batería) se salga del rango 0 a 100.
chk_ciclosQue los ciclos de carga sean negativos.
chk_pesadoLa parte más interesante: si el tipo es PESADO, las tres columnas de pesado son obligatorias; si no lo es, esas tres columnas deben ser NULL. Así la tabla no queda incoherente.
¿Por qué validamos en Java y en MySQL? Java da mensajes amigables (“El nivel de combustible debe estar entre 0 y 100”). La base protege la integridad aunque alguien se salte la interfaz, use otra herramienta o haya varios usuarios a la vez. Cada capa cumple su papel.

Paso 4 · Sección 2 · Los usuarios

Esta es la sección más importante de la Parte A. Léala completa antes de escribir el código.

Antes de nada: las DOS contraseñas. El código de esta sección trae dos textos de relleno: ESCRIBE_TU_CLAVE_DEL_DEFINER y ESCRIBE_TU_CLAVE_DE_LA_APP. Reemplácelos por sus propias contraseñas antes de ejecutar la sección.
4.1 Cómo debe ser cada contraseña
  • Mínimo 8 caracteres (recomendado 12 o más).
  • Mezcle mayúsculas, minúsculas, números y algún símbolo.
  • Distintas entre sí y distintas también de la de root.
  • No use su nombre, su cédula, ni 1234, admin, mysql.
  • Evite la comilla simple ' y el punto y coma ;: rompen el SQL.

Anótelas fuera del proyecto (gestor de contraseñas o un archivo local). La de flota_app la va a necesitar en el Paso 12.

4.2 ¿Qué es un “usuario” en MySQL?

Un usuario de MySQL no es solo un nombre. Su identidad tiene dos partes:

'nombre_de_usuario'@'host_desde_donde_se_conecta' ^ ^ el nombre el origen permitido

Por eso escribimos 'flota_app'@'localhost' y no simplemente flota_app:

  • 'flota_app' → quién.
  • 'localhost' → desde dónde. localhost significa “solo desde la misma máquina donde corre MySQL”.
Consecuencia práctica: si copia el proyecto a otra computadora y se conecta a su MySQL local, todo funciona igual, porque localhost es “esa” máquina. En cambio, una cuenta 'flota_app'@'localhost' no puede conectarse desde otra PC de la red.
4.3 Escribir la sección completa

Copie esto debajo de la banda de comentarios de la sección 2, reemplazando los dos textos de relleno por sus contraseñas:

-- Cuenta definidora de privilegios mínimos. No usar root como DEFINER. CREATE USER IF NOT EXISTS 'flota_definer'@'localhost' IDENTIFIED BY 'ESCRIBE_TU_CLAVE_DEL_DEFINER'; GRANT SELECT, INSERT, UPDATE, DELETE ON flota_vehicular.vehiculo TO 'flota_definer'@'localhost'; CREATE USER IF NOT EXISTS 'flota_app'@'localhost' IDENTIFIED BY 'ESCRIBE_TU_CLAVE_DE_LA_APP'; REVOKE ALL PRIVILEGES, GRANT OPTION FROM 'flota_app'@'localhost';

Cuando el archivo esté completo, estas dos líneas serán las líneas 33 y 35 (las dos que empiezan con CREATE USER). Son las únicas que debe cambiar.

4.4 Qué hace cada una de las cuatro sentencias

CREATE USER IF NOT EXISTS 'flota_definer'@'localhost' IDENTIFIED BY '...'

  • CREATE USER → crea la cuenta.
  • IF NOT EXISTS → no falla si ya existe (pero no cambia la clave; si necesita cambiarla use ALTER USER, ver acordeón).
  • IDENTIFIED BY '...' → aquí se define la contraseña. MySQL la guarda cifrada, no en texto plano.

Recién creada, la cuenta todavía no puede hacer nada. Solo puede conectarse; no tiene permisos sobre ninguna tabla.

GRANT SELECT, INSERT, UPDATE, DELETE ON flota_vehicular.vehiculo TO 'flota_definer'@'localhost'

GRANT se lee: “otorga estas acciones, sobre este objeto, a este usuario”.

Parte de la sentenciaQué significa
SELECT, INSERT, UPDATE, DELETELas cuatro operaciones sobre datos (leer, insertar, modificar, borrar).
ON flota_vehicular.vehiculoSolo esa tabla. No toda la base, no otros esquemas.
TO 'flota_definer'@'localhost'El usuario exacto, incluido el host.
Fíjese lo que NO aparece: no aparece CREATE USER, ni DROP, ni ALTER, ni ningún privilegio de administración del servidor. Eso es el principio de mínimo privilegio.

CREATE USER IF NOT EXISTS 'flota_app'@'localhost' IDENTIFIED BY '...'

Esta es la cuenta que usará su aplicación Java. Guárdela: la escribirá en el Paso 12.

REVOKE ALL PRIVILEGES, GRANT OPTION FROM 'flota_app'@'localhost'

REVOKE es lo contrario de GRANT: retira permisos.

  • ALL PRIVILEGES → todos los permisos que tuviera.
  • GRANT OPTION → le quita también la capacidad de otorgar permisos a otros.

¿Por qué, si la cuenta acaba de nacer? Porque MySQL le deja el privilegio USAGE (puede conectarse y nada más). Esta línea garantiza que no quede ningún resto, incluso si el script se ejecuta sobre una base donde el usuario ya existía con permisos previos. Es defensa en profundidad.

4.6 Resumen: las tres cuentas
CuentaQuién la usaQué puede hacer
rootUsted, desde WorkbenchTodo. Crear bases, usuarios, borrar el servidor. Por eso la aplicación no la usa.
flota_definerNadie directamente: es el definidor de los procedimientosSELECT, INSERT, UPDATE, DELETE sobre flota_vehicular.vehiculo, más el EXECUTE que recibe en el Paso 6. Nada de administración del servidor.
flota_appSu aplicación JavaEjecutar (EXECUTE) los cuatro procedimientos. No puede leer la tabla directamente.
¿Qué significa el privilegio USAGE?

Significa “puede iniciar sesión, y nada más”. MySQL lo crea automáticamente con cada usuario. Cuando en SHOW GRANTS solo ve USAGE ON *.*, la cuenta no tiene ningún permiso real: es exactamente lo que queremos para flota_app antes de darle los EXECUTE.

¿Por qué dos cuentas y no una sola?

Porque cumplen funciones distintas:

  • Los procedimientos necesitan tocar la tabla → para eso existe flota_definer, con permisos de tabla pero sin permisos de administración.
  • La aplicación solo necesita pedir operaciones → para eso existe flota_app, que no sabe hacer SELECT ni DELETE por su cuenta.

Si usáramos una sola cuenta con permisos de tabla, la aplicación podría ejecutar cualquier DELETE FROM vehiculo que apareciera en el código (por un error o por un ataque). Separando las cuentas, el servidor impone el límite.

¿Puedo conectarme con root desde la aplicación “solo para probar”?

Técnicamente sí, y funcionaría. No lo haga. Si se acostumbra, el día que el código llegue a un servidor real la aplicación tendrá permisos administrativos y un simple error podría borrar toda la base. Además, en este laboratorio se revisa que la aplicación se conecte como flota_app.

Paso 5 · Sección 3 · Los procedimientos almacenados

Aquí es donde Java y MySQL se ponen de acuerdo. Escriba esta sección debajo de la banda de comentarios de la sección 3.

5.1 DROP PROCEDURE IF EXISTS — borrar los anteriores
DROP PROCEDURE IF EXISTS sp_listar_vehiculos; DROP PROCEDURE IF EXISTS sp_insertar_vehiculo; DROP PROCEDURE IF EXISTS sp_actualizar_vehiculo; DROP PROCEDURE IF EXISTS sp_eliminar_vehiculo;

Es la misma idea que CREATE DATABASE IF NOT EXISTS, pero al revés: borramos lo que hubiera y lo volvemos a crear limpio. Así, si modifica un procedimiento, el script lo reemplaza en lugar de fallar con “ya existe”.

5.2 DELIMITER — la trampa clásica
DELIMITER $$ # cambiamos el terminador a $$ ... aquí van los CREATE PROCEDURE ... DELIMITER ; # lo devolvemos a ;
  • Normalmente ; termina una sentencia.
  • El cuerpo de un procedimiento va entre BEGIN y END y contiene varios ; adentro.
  • Si el terminador siguiera siendo ;, el cliente enviaría al servidor solo la mitad del procedimiento: error de sintaxis.
  • Solución: cambiar temporalmente el terminador a $$. Ahora el cliente corta la sentencia solo cuando encuentra $$, es decir en END$$.
Si olvida el DELIMITER verá errores de sintaxis 1064 en medio del procedimiento. Además, DELIMITER es una directiva del cliente (Workbench), no una sentencia de MySQL: por eso esa línea no lleva punto y coma al final.
5.3 Líneas comunes: DEFINER y SQL SECURITY DEFINER

Los cuatro procedimientos empiezan igual:

CREATE DEFINER='flota_definer'@'localhost' PROCEDURE sp_nombre(...) SQL SECURITY DEFINER BEGIN ... END$$
ConceptoQué significa
DEFINER = 'flota_definer'Quién es el dueño del procedimiento. Lo crea root, pero queda a nombre de flota_definer.
SQL SECURITY DEFINERAl ejecutarse, usa los permisos del definidor, no los de quien lo llama. Por eso flota_app puede leer la tabla a través del procedimiento aunque no tenga SELECT.
SQL SECURITY INVOKERLo contrario: usaría los permisos de quien invoca. Con flota_app esto fallaría.
¿Por qué no dejar root como DEFINER? Porque entonces root sería el contexto privilegiado de todas las rutinas: si alguien lograra modificar un procedimiento, lo modificaría con permisos de administrador. Con flota_definer, el peor caso queda limitado a esa tabla.
5.4 Procedimiento 1 · sp_listar_vehiculos (leer toda la flota)
CREATE DEFINER='flota_definer'@'localhost' PROCEDURE sp_listar_vehiculos() SQL SECURITY DEFINER BEGIN SELECT placa, marca, kilometraje, estado, tipo, nivel_energia, ciclos_carga, tonelaje_maximo, carga_actual, tipo_carga FROM vehiculo ORDER BY placa; END$$
  • No recibe parámetros: los paréntesis van vacíos.
  • Devuelve todas las columnas de todos los vehículos, ordenados por placa.
  • ORDER BY placa hace que la tabla se vea siempre en el mismo orden.
  • Al devolver filas, Java lo llamará con executeQuery().
5.5 Procedimiento 2 · sp_insertar_vehiculo (registrar)
CREATE DEFINER='flota_definer'@'localhost' PROCEDURE sp_insertar_vehiculo( IN p_placa VARCHAR(12), IN p_marca VARCHAR(80), IN p_kilometraje INT, IN p_estado VARCHAR(20), IN p_tipo VARCHAR(20), IN p_energia DECIMAL(5,2), IN p_ciclos INT, IN p_tonelaje DECIMAL(8,2), IN p_carga DECIMAL(8,2), IN p_tipo_carga VARCHAR(20)) SQL SECURITY DEFINER BEGIN INSERT INTO vehiculo(placa,marca,kilometraje,estado,tipo,nivel_energia,ciclos_carga,tonelaje_maximo,carga_actual,tipo_carga) VALUES (p_placa,p_marca,p_kilometraje,p_estado,p_tipo,p_energia,p_ciclos,p_tonelaje,p_carga,p_tipo_carga); END$$

IN significa parámetro de entrada (solo entra, no devuelve). El prefijo p_ es una convención: deja claro que es un parámetro y no una columna.

El orden es sagrado. Este es el “contrato” entre Java y la base de datos:

#ParámetroValor esperado

5.6 Procedimiento 3 · sp_actualizar_vehiculo (editar)
CREATE DEFINER='flota_definer'@'localhost' PROCEDURE sp_actualizar_vehiculo( IN p_placa VARCHAR(12), IN p_marca VARCHAR(80), IN p_kilometraje INT, IN p_estado VARCHAR(20), IN p_tipo VARCHAR(20), IN p_energia DECIMAL(5,2), IN p_ciclos INT, IN p_tonelaje DECIMAL(8,2), IN p_carga DECIMAL(8,2), IN p_tipo_carga VARCHAR(20)) SQL SECURITY DEFINER BEGIN UPDATE vehiculo SET marca=p_marca, kilometraje=p_kilometraje, estado=p_estado, tipo=p_tipo, nivel_energia=p_energia, ciclos_carga=p_ciclos, tonelaje_maximo=p_tonelaje, carga_actual=p_carga, tipo_carga=p_tipo_carga WHERE placa=p_placa; IF ROW_COUNT() = 0 AND NOT EXISTS (SELECT 1 FROM vehiculo WHERE placa=p_placa) THEN SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT='No existe un vehículo con esa placa'; END IF; END$$
  • Recibe los mismos 10 parámetros que el de insertar, en el mismo orden.
  • UPDATE ... WHERE placa = p_placa → modifica solo ese vehículo. Sin el WHERE actualizaría todos: por eso es tan importante.
  • ROW_COUNT() devuelve cuántas filas afectó la sentencia anterior.
  • Si ninguna fila se actualizó hay dos posibilidades: (a) la placa no existe, o (b) la fila existía pero los valores eran idénticos (MySQL no cuenta eso como cambio). El AND NOT EXISTS (...) distingue el caso (a) del (b).
  • SIGNAL SQLSTATE '45000' lanza un error deliberado con un mensaje en español. Ese error viaja hasta Java y se convierte en un SQLException que el programa muestra a la persona usuaria.
5.7 Procedimiento 4 · sp_eliminar_vehiculo (borrar)
CREATE DEFINER='flota_definer'@'localhost' PROCEDURE sp_eliminar_vehiculo(IN p_placa VARCHAR(12)) SQL SECURITY DEFINER BEGIN DELETE FROM vehiculo WHERE placa=p_placa; IF ROW_COUNT() = 0 THEN SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT='No existe un vehículo con esa placa'; END IF; END$$

Un solo parámetro (la placa). Mismo patrón que el anterior: borra y, si no borró nada, avisa con un error. Gracias a eso, si Java intenta eliminar una placa que ya no existe, la aplicación se entera en lugar de creer que todo salió bien.

Después del último END$$ va la línea DELIMITER ;. Es obligatoria: si no la pone, todo lo que venga después en el archivo (la sección 4) intentaría cortarse con $$ y fallaría.

¿Qué es SQLSTATE '45000'?

Es un código reservado por el estándar SQL para errores definidos por el usuario, o sea “un error que yo decidí lanzar”. El MESSAGE_TEXT es el texto que verá la persona usuaria. Java lo recibe dentro de la SQLException.

¿Por qué los parámetros empiezan con p_ y las columnas no?

Para que no haya ambigüedad. Dentro del procedimiento existen a la vez la columna placa (de la tabla) y el parámetro p_placa. Si ambos se llamaran igual, el WHERE placa = placa siempre sería verdadero: ¡actualizaría o borraría todas las filas!

¿Los procedimientos son “mágicamente seguros”?

No. Son una herramienta, no una solución completa. Si dentro de un procedimiento se construyera SQL dinámico concatenando datos de entrada, volvería el riesgo de inyección. La seguridad aquí sale de combinar: parámetros (CallableStatement), procedimientos, un definidor con permisos limitados, una cuenta de aplicación sin permisos de tabla y credenciales fuera del código.

Paso 6 · Sección 4 · Los permisos de la aplicación

6.1 Los permisos del DEFINER

Antes de darle permisos a la aplicación, nos aseguramos de que flota_definer tenga todo lo que necesitan los procedimientos:

-- Dar permisos sobre las tablas al DEFINER GRANT SELECT, INSERT, UPDATE, DELETE ON flota_vehicular.vehiculo TO 'flota_definer'@'localhost'; -- IMPORTANTE: El DEFINER también necesita permiso EXECUTE para invocar procedimientos SQL SECURITY DEFINER GRANT EXECUTE ON flota_vehicular.* TO 'flota_definer'@'localhost';
  • La primera línea le da al definidor las cuatro operaciones sobre la tabla. Los cuerpos de los procedimientos hacen SELECT, INSERT, UPDATE y DELETE, y como se ejecutan con sus permisos, él necesita tenerlos.
  • La segunda línea es la que suele olvidarse. En un procedimiento SQL SECURITY DEFINER, MySQL exige que el definidor también tenga EXECUTE sobre la rutina. Sin este permiso, las llamadas fallan con execute command denied to user 'flota_definer', aunque flota_app sí tenga el suyo.
Note la diferencia de alcance: al definidor se le da EXECUTE ON flota_vehicular.* (todo el esquema) porque es una cuenta interna del servidor, dueña de las rutinas. A flota_app, en cambio, se le dará uno por uno, porque es la cuenta que usa la aplicación y debe tener el mínimo.

La primera línea ya apareció en la sección 2. Repetirla aquí no molesta (otorgar dos veces el mismo permiso no cambia nada) y deja esta sección completa por sí sola.

6.2 Los cuatro GRANT EXECUTE de la aplicación
GRANT EXECUTE ON PROCEDURE flota_vehicular.sp_listar_vehiculos TO 'flota_app'@'localhost'; GRANT EXECUTE ON PROCEDURE flota_vehicular.sp_insertar_vehiculo TO 'flota_app'@'localhost'; GRANT EXECUTE ON PROCEDURE flota_vehicular.sp_actualizar_vehiculo TO 'flota_app'@'localhost'; GRANT EXECUTE ON PROCEDURE flota_vehicular.sp_eliminar_vehiculo TO 'flota_app'@'localhost'; FLUSH PRIVILEGES;

Se otorgan uno por uno, a propósito. Podríamos escribir GRANT EXECUTE ON flota_vehicular.* y sería más corto, pero entonces cualquier procedimiento futuro quedaría accesible automáticamente. Al enumerarlos, la cuenta solo puede ejecutar exactamente estos cuatro.

6.3 FLUSH PRIVILEGES

Recarga la tabla de permisos en memoria del servidor. Dato honesto: cuando se usan CREATE USER y GRANT, MySQL ya recarga los permisos solo, así que no es estrictamente necesario. Se incluye por costumbre y no hace daño. Sí es obligatorio cuando se modifican las tablas de permisos directamente con INSERT o UPDATE.

8.2 ¿Por qué cambia el contrato?
  • Antes, para guardar un cambio había que reescribir toda la lista. Eso funcionaba porque el archivo era solo nuestro.
  • En una base de datos compartida, borrar y reinsertar toda la tabla en cada cambio puede afectar datos de otros usuarios, generar condiciones de carrera y perder actualizaciones hechas al mismo tiempo.
  • Por eso pasamos a una operación por vehículo: insertar, actualizar y eliminar.
La lista que mantiene el FlotaService es una vista de trabajo en memoria. El almacenamiento persistente es MySQL. Si una operación falla en la base, no queremos fingir que se guardó.

9.6 cargarTodos(): llamar al procedimiento y leer las filas
@Override public List<Vehiculo> cargarTodos() { List<Vehiculo> resultado = new ArrayList<>(); try (Connection c = conectar(); CallableStatement cs = c.prepareCall("{CALL sp_listar_vehiculos()}"); ResultSet rs = cs.executeQuery()) { while (rs.next()) resultado.add(mapear(rs)); return resultado; } catch (SQLException e) { throw fallo("consultar la flota", e); } }
  • prepareCall("{CALL sp_listar_vehiculos()}") → prepara una llamada a un procedimiento. Las llaves { } son la sintaxis de escape de JDBC; por dentro, el driver lo traduce a CALL.
  • executeQuery() se usa cuando el procedimiento devuelve filas (como este, que hace un SELECT).
  • rs.next() avanza fila por fila y devuelve false cuando se acaban; por cada fila, mapear(rs) construye un objeto Java.
  • Al final se devuelve la lista completa (o vacía, si no había vehículos).

  • Cada ? es un parámetro. Cuente: hay 10 signos de interrogación → los mismos 10 parámetros del Paso 5.5.
  • El orden de los ? debe ser el orden de los parámetros del procedimiento. Si se equivoca, MySQL recibiría datos en el lugar equivocado.
9.8 ejecutarGuardar(): el método que comparten
private void ejecutarGuardar(String llamada, Vehiculo v) { try (Connection c = conectar(); CallableStatement cs = c.prepareCall(llamada)) { llenarParametros(cs, v); cs.executeUpdate(); } catch (SQLException e) { throw fallo("guardar el vehículo", e); } }
  • Recibe la llamada (un texto) y el vehículo. Así sirve para insertar y para actualizar sin repetir código.
  • llenarParametros(cs, v) escribe los 10 valores dentro de los ? (lo vemos en el sub-paso 9.10).
  • executeUpdate() se usa cuando la operación no devuelve filas (insert, update, delete). Devuelve cuántas filas afectó, pero aquí no lo usamos.
Esto es lo esencial: el texto de la llamada está escrito y fijo. Los valores no se pegan al texto: viajan por separado con setString, setInt, etc. Por eso un valor malicioso no puede alterar el significado de la sentencia. Esa separación es la defensa contra la inyección SQL.
9.9 eliminar(): borrar por placa
@Override public void eliminar(String placa) { try (Connection c = conectar(); CallableStatement cs = c.prepareCall("{CALL sp_eliminar_vehiculo(?)}")) { cs.setString(1, placa); cs.executeUpdate(); } catch (SQLException e) { throw fallo("eliminar el vehículo", e); } }
  • Un solo ? → un solo parámetro: la placa.
  • setString(1, placa) coloca el valor de Java en el primer ?.
  • La placa llega desde la vista, pasa por el Controller y el Service, y aquí se envía como valor, nunca concatenada.

private Vehiculo mapear(ResultSet rs) throws SQLException { String placa = rs.getString("placa"); String marca = rs.getString("marca"); int km = rs.getInt("kilometraje"); double energia = rs.getDouble("nivel_energia"); TipoVehiculo tipo = TipoVehiculo.valueOf(rs.getString("tipo")); Vehiculo v = switch (tipo) { case COMBUSTION -> new VehiculoCombustion(placa, marca, km, energia); case ELECTRICO -> new VehiculoElectrico(placa, marca, km, energia, rs.getInt("ciclos_carga")); case PESADO -> { VehiculoPesado p = new VehiculoPesado(placa, marca, km, energia, rs.getDouble("tonelaje_maximo"), TipoCarga.valueOf(rs.getString("tipo_carga"))); double carga = rs.getDouble("carga_actual"); if (carga > 0) p.cargarMercancia(carga); yield p; } }; v.setEstado(EstadoVehiculo.valueOf(rs.getString("estado"))); return v; }

El ResultSet trae filas y columnas, no objetos Vehiculo. Esta traducción es manual y se llama mapeo objeto–relacional:

  • rs.getString("placa") lee una columna por su nombre. Si es numérica se usa getInt o getDouble.
  • La columna tipo decide qué subclase construir: es la herencia del modelo reconstruida desde una tabla plana. Es un switch de expresión, que devuelve el objeto.
  • En el caso PESADO, además se vuelve a cargar la mercancía si había carga (cargarMercancia). El yield devuelve el objeto construido dentro del bloque { }.
  • Al final se restaura el estado, un dato que comparten todos los subtipos.
9.12 fallo(): errores técnicos vs. mensajes amigables
private PersistenciaException fallo(String operacion, SQLException e) { // El detalle técnico se conserva como causa; la interfaz recibe un mensaje genérico. return new PersistenciaException("No fue posible " + operacion + ". Verifique conexión, permisos y datos.", e); }
  • Recibe qué operación se estaba haciendo y el error real de MySQL.
  • Devuelve una excepción (no la lanza): por eso los métodos de arriba escriben throw fallo(...), que se lee muy claro.
  • El detalle técnico (e) se guarda como causa para poder depurar; la ventana muestra un mensaje genérico y entendible.
  • Nota: aquí se concatena texto de la aplicación (no datos de la persona usuaria) para armar un mensaje de error; eso no es SQL y no representa riesgo.

9.14 El ciclo de JDBC, visible en un solo vistazo
try (Connection c = conectar(); // 1. conexión CallableStatement cs = c.prepareCall(llamada); // 2. sentencia ResultSet rs = cs.executeQuery()) { // 3. resultado ... } // 4. cierre automático

El try ( ... ) es try-with-resources: al salir del bloque cierra Connection, CallableStatement y ResultSet, incluso si ocurre una excepción. No es solo estilo: es administrar bien los recursos del servidor. Si no los cerráramos, el servidor iría acumulando conexiones abiertas hasta quedarse sin capacidad.

¿Qué significa el @Override?

Le dice a Java: “este método implementa uno declarado en la interfaz”. Si usted se equivoca en el nombre (por ejemplo escribe insertarVehiculo en vez de insertar), el compilador marca error inmediatamente. Es una red de seguridad.

¿Por qué executeQuery() en un caso y executeUpdate() en otro?
  • executeQuery() → cuando el procedimiento devuelve filas (un SELECT). Devuelve un ResultSet.
  • executeUpdate() → cuando no devuelve filas (insert, update, delete). Devuelve un entero con las filas afectadas.

Si los intercambia, obtiene un error de tipo: el primero necesita un ResultSet y el segundo un int.

¿Por qué setNull(8, Types.DECIMAL) y no setDouble(8, 0)?

Porque la restricción chk_pesado de la tabla exige que, si el tipo no es PESADO, esas columnas sean NULL. Con 0 el INSERT sería rechazado por la base. Types.DECIMAL le indica a JDBC de qué tipo es el NULL que se está enviando.

No conoce SQL, JDBC ni credenciales. */ public class FlotaService { private final List<Vehiculo> vehiculos; private final RepositorioVehiculo repositorio; public FlotaService(RepositorioVehiculo repositorio) { this.repositorio = repositorio; this.vehiculos = new ArrayList<>(repositorio.cargarTodos()); } public void agregarVehiculo(Vehiculo v) { if (vehiculos.stream().anyMatch(x -> x.getPlaca().equalsIgnoreCase(v.getPlaca()))) throw new IllegalArgumentException("Ya existe un vehículo con esa placa."); repositorio.insertar(v); // Primero persistimos; si falla, no alteramos la lista local. vehiculos.add(v); } public List<Vehiculo> obtenerVehiculos() { return new ArrayList<>(vehiculos); } public void actualizarVehiculo(Vehiculo nuevo) { for (int i = 0; i < vehiculos.size(); i++) { Vehiculo actual = vehiculos.get(i); if (actual.getPlaca().equalsIgnoreCase(nuevo.getPlaca())) { if (actual.getEstado() != EstadoVehiculo.DISPONIBLE) throw new IllegalStateException("Solo se puede editar un vehículo disponible."); repositorio.actualizar(nuevo); vehiculos.set(i, nuevo); return; } } throw new IllegalArgumentException("No se encontró el vehículo."); } public void eliminarVehiculo(String placa) { Vehiculo encontrado = vehiculos.stream().filter(v -> v.getPlaca().equalsIgnoreCase(placa)) .findFirst().orElseThrow(() -> new IllegalArgumentException("No se encontró el vehículo.")); if (encontrado.getEstado() != EstadoVehiculo.DISPONIBLE) throw new IllegalStateException("Solo se puede eliminar un vehículo disponible."); repositorio.eliminar(placa); vehiculos.remove(encontrado); } /** Persiste los cambios de estado/energía realizados por las operaciones de la flota. */ public void guardarCambios(Vehiculo v) { repositorio.actualizar(v); } }

Acordeón · Dudas frecuentes

Haga clic en cada pregunta. Están ordenadas de “concepto” a “error concreto”.

Conceptos

¿MySQL Workbench es la base de datos?

No. La base de datos la administra MySQL Server (el SABD). Workbench es un cliente: una ventana desde la que damos órdenes. IntelliJ Database Tools es otro cliente del mismo servidor. Si cierra Workbench, la base sigue funcionando.

¿Qué diferencia hay entre JDBC y el driver mysql-connector-j?

JDBC es el conjunto de reglas (la API): define qué significa Connection, CallableStatement, ResultSet. Viene con Java (java.sql). mysql-connector-j es la implementación concreta de esas reglas para MySQL: el “traductor” real. Se agrega como dependencia Maven.

¿Por qué CallableStatement y no PreparedStatement?

Porque llamamos procedimientos almacenados. PreparedStatement sirve para enviar una sentencia SQL directa; CallableStatement está hecho para invocar procedimientos con CALL. Ambos parametrizan los valores, así que ambos protegen de la inyección SQL.

¿Por qué la aplicación no puede conectarse como root?

Porque root puede crear usuarios, borrar bases y cambiar la configuración del servidor. Si un error de programación o una vulnerabilidad lograra usar esa conexión, el daño sería total en lugar de limitado. La aplicación solo necesita ejecutar cuatro operaciones: se le da exactamente eso y nada más. Es el principio de mínimo privilegio.

¿Qué significa que un procedimiento sea SQL SECURITY DEFINER?

Que al ejecutarse usa los permisos de quien lo definió (flota_definer), no los de quien lo llama. Gracias a eso flota_app puede obtener datos de la tabla sin tener permiso de SELECT: el permiso efectivo es el del definidor, y el definidor solo tiene permisos sobre flota_vehicular.vehiculo. Con INVOKER sería al revés y la llamada fallaría.

Los procedimientos almacenados, ¿ya me hacen 100% seguro?

No. Son una herramienta. Si dentro de un procedimiento se concatenara SQL dinámico, volvería el riesgo. La seguridad de esta práctica es la combinación: parámetros + procedimientos + definidor limitado + cuenta de aplicación sin permisos de tabla + credenciales fuera del código + restricciones CHECK en la tabla.

¿Por qué tuve que cambiar el contrato del repositorio?

Porque el contrato anterior (cargarTodos + guardarTodos(List)) reescribía toda la información en cada cambio. Eso funcionaba con un archivo propio, pero con una base compartida puede afectar datos de otras personas y perder cambios hechos al mismo tiempo. Ahora cada operación (insertar, actualizar, eliminar) toca solo lo necesario.
