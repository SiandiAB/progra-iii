La misma interfaz, dos implementaciones

El Service no sabe si los datos están en un archivo o en un SABD. 

public interface RepositorioVehiculo {
    List<Vehiculo> cargarTodos();
    void insertar(Vehiculo v);
    void actualizar(Vehiculo v);
    void eliminar(String placa);
}

RepositorioVehiculoTxt

Persistencia en archivo. Ya lo teníamos.

RepositorioVehiculoMySQL

Persistencia en el SABD. Es lo que agregamos hoy.

Idea clave: la aplicación pidió “guardar”, no “un TXT”. Por eso cambiar el medio de almacenamiento no obliga a reescribir el modelo ni la vista.

¿Qué cambió y qué no?

Cambiamos dónde se guarda, no lo que el sistema sabe hacer.

Se conserva

  • El modelo Vehiculo y sus subclases
  • VehiculoFactory y el DTO DatosVehiculo
  • FlotaService y las reglas de negocio
  • La vista y el Controller

Cambia

  • La implementación del Repository
  • El contrato de persistencia (más granular)
  • La configuración de arranque y las credenciales
  • Dónde se declaran las restricciones

Si eso es lo único que cambia, la arquitectura está bien separada.

Una conexión no es solo usuario y contraseña

La pregunta real es: ¿con cuántos privilegios se conecta Java?

Mínimo privilegio: dar a cada parte únicamente los permisos que necesita para cumplir su trabajo.

Cuenta administradora

Crea el esquema y las cuentas. Se usa una sola vez, desde una instancia local de laboratorio.

flota_definer

Contexto de ejecución de los procedimientos. Permisos limitados sobre la tabla.

flota_app

La cuenta que usa Java. Solo recibe permiso para ejecutar procedimientos concretos.

Controlada · es lo que buscamos

Un procedimiento no es una solución mágica

Es una herramienta más dentro del mapa de seguridad.

Lo que sí aporta

  • Reduce la superficie de acceso a operaciones concretas
  • Java no necesita conocer el SQL interno de la tabla
  • Centraliza la operación en el servidor

Lo que no evita

  • SQL dinámico concatenado dentro del procedimiento
  • Un definidor con permisos excesivos
  • Falta de validación y de credenciales bien manejadas

Recuerden: parametrizar y usar procedimientos no sustituyen la autorización. La seguridad sale de combinar varias decisiones correctas.

¿Por qué Java no se conecta como root?

Dos decisiones que se toman antes de escribir la primera línea de JDBC.

El daño posible

Con root la aplicación puede crear usuarios, borrar bases o cambiar el servidor completo. Un error o una vulnerabilidad deja de ser un problema local.

La aplicación no necesita eso.

El secreto fuera del código

Una contraseña escrita en una clase Java termina en Git, en un ZIP o en una captura de pantalla.

Se lee del entorno; el archivo .env.example es solo una plantilla de nombres.

Variables que configuramos: FLOTA_DB_URL FLOTA_DB_USER FLOTA_DB_PASSWORD — Java no lee el archivo .env por su cuenta.

¿Qué es un procedimiento almacenado?

Una operación definida en el servidor, a la que llamamos por su nombre.

En vez de darle a la cuenta de Java permiso para ejecutar cualquier SELECT, INSERT, UPDATE o DELETE, le damos permiso para ejecutar operaciones específicas. 

CALL flota_vehicular.sp_listar_vehiculos();

sp_listar_vehiculos

sp_insertar_vehiculo

sp_actualizar_vehiculo

sp_eliminar_vehiculo

El contrato y la llamada

Java no necesita el SQL interno: necesita el nombre y los parámetros en orden.

CallableStatement 

cs = cn.prepareCall(
  "{CALL sp_insertar_vehiculo(?,?,?,?,?,?,?,?,?,?)}");
cs.setString(1, datos.placa());
cs.setInt(3, datos.kilometraje());

Qué sí y qué no hacemos

  • Cada ? es un parámetro tipado
  • El texto de la llamada permanece fijo
  • Los valores viajan por separado
  • No pegamos la placa dentro del texto de la sentencia

Permisos: de la tabla al procedimiento

Dos preguntas: ¿quién otorga el permiso? y ¿quién ejecuta la operación?

Cláusula El procedimiento se ejecuta…
SQL SECURITY DEFINER con los privilegios de quien lo definió (flota_definer). Es la opción segura cuando el definidor tiene permisos limitados.
SQL SECURITY INVOKER con los privilegios de quien lo invoca. Si el invocador es la app, la app necesita permisos sobre la tabla.

Lo único que recibe la aplicación 

GRANT EXECUTE ON PROCEDURE flota_vehicular.sp_insertar_vehiculo
  TO 'flota_app'@'localhost';

Sin SELECT, sin INSERT, sin DROP. Solo permiso para ejecutar.

DriverManager hoy, pool de conexiones después

Abrir una conexión cuesta; cerrar recursos no es opcional.

DriverManager

Una conexión nueva por operación. Deja visible el ciclo de vida de JDBC: ideal para aprender.

Pool de conexiones

Reutiliza conexiones abiertas. Lo esperable en una aplicación de mayor tráfico.

try-with-resources 

try (Connection cn = conectar();
     CallableStatement cs =
       cn.prepareCall(llamada)) {
  ...
}

No es solo estilo: Connection, CallableStatement y ResultSet son recursos del servidor. El bloque los cierra incluso si ocurre una excepción.

El contrato del Repository cambió

Antes guardábamos la lista completa; ahora hacemos una operación por vehículo.

Antes

Reescribir todo

  • Se guardaba la lista entera
  • Funciona cuando el archivo es solo nuestro
  • No funciona bien con varios usuarios
Ahora

Una operación por vehículo

  • insertar, actualizar, eliminar
  • Cada llamada expresa una intención
  • Si la base falla, no fingimos que se guardó

¿Por qué no borrar y reinsertar toda la tabla? Afectaría datos de otros usuarios y podría perder actualizaciones concurrentes. La lista en memoria es una vista de trabajo; MySQL es el almacenamiento persistente.

Cierre: el mapa completo

Cada práctica insegura tiene su alternativa.

Práctica insegura Lo que hacemos en el laboratorio
Concatenar datos dentro del SQL Parámetros en CallableStatement
Conectarse como root flota_app, con mínimo privilegio
Contraseñas en el código fuente Variables de entorno
Permisos directos sobre la tabla EXECUTE solo en procedimientos concretos
SQL dentro del Controller Repository como frontera de acceso a datos
Reescribir toda la tabla en cada cambio Operaciones específicas por vehículo

Y recuerden: los procedimientos almacenados no son una solución mágica. Son una herramienta. La seguridad sale de combinar decisiones correctas y de comprobarlas.
