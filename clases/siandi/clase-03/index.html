Puente de Refuerzo: Primitivos, Wrappers y Memoria en Backend

Conexion arquitectonica con la Semana 2 — Del dato en RAM al dato en base de datos

Contexto previo: Que es una base de datos?

Imagine un archivo de Excel gigante que vive en un servidor remoto (otra computadora), no en su maquina personal. Ese archivo esta organizado en hojas (tablas), cada hoja tiene columnas con nombres fijos (id, email, contraseña) y cada fila representa un registro (en nuestro caso, un usuario del sistema). A eso se le llama base de datos relacional.

En esta clase no necesita saber SQL ni administrar bases de datos. Solo necesita entender que cuando su programa Java se conecta a una base de datos para leer o guardar informacion, algunos campos pueden estar vacios (NULL). Ese hecho —aparentemente inocente— tiene consecuencias profundas en como declaramos nuestras variables en Java. En una sesion futura del curso se explicaran las bases de datos con todo detalle.

El Problema Real en Backend

Considere una tabla usuarios en una base de datos relacional remota (PostgreSQL, MySQL). El campo token_recuperacion es opcional: solo existe si el usuario solicito un reseteo de contraseña. Si nadie lo ha solicitado, la base de datos almacena NULL. 

-- Consulta SQL: el campo puede ser NULL
SELECT id, email, token_recuperacion 
FROM usuarios 
WHERE id = 1042;

-- Resultado posible:
-- 1042 | admin@sistema.com | NULL

Si en su codigo Java declara long tokenRecuperacion; (primitivo) y la base de datos devuelve NULL, el driver JDBC asignara 0 al primitivo, destruyendo la distincion semantica entre "token不存在" y "token con valor 0".

La Solucion: Wrapper Classes

Declare Long tokenRecuperacion; (clase envoltura). Al ser un objeto (no un primitivo), puede contener o bien un valor numerico valido o bien null, reflejando fielmente el estado del campo en la base de datos. 

// CORRECTO: Wrapper Class tolera null
public class Usuario {
    private Long id;               // null = no persistido aun
    private String email;
    private Long tokenRecuperacion;  // null = no hay token activo
    private Integer intentosFallidos; // null = nunca ha fallado
    
    public boolean tieneTokenActivo() {
        return tokenRecuperacion != null;
    }
}

Stack vs. Heap: Rendimiento vs. Seguridad

Seleccione para ver la comparacion completa de memoria

Stack vs. Heap: Arquitectura de Memoria en la JVM

Rendimiento, seguridad y ciclo de vida de los datos en la Maquina Virtual de Java

Comparacion Formal: Almacenamiento en Pila (Stack) vs. Monton (Heap)

Criterio Stack (Pila) Heap (Monton)
Almacena Primitivos (int, boolean, double) y referencias a objetos Objetos completos (String, Usuario, ArrayList) con su estado interno
Velocidad Extremadamente rapida (operacion LIFO de CPU) Mas lenta (requiere recoleccion de basura y desfragmentacion)
Gestion Automatica por marco de metodo (stack frame). Se libera al salir del metodo. Gestionada por el Garbage Collector. El objeto vive mientras sea alcanzable.
Tamaño Limitado (~1 MB por hilo en JVM estandar). StackOverflowError si se agota. Configurable con -Xmx. Puede crecer hasta gigabytes.
Seguridad Datos confinados al hilo actual. Thread-safe por diseño. Datos compartidos entre hilos. Requiere sincronizacion explicita para seguridad concurrente.
Analogia Nota adhesiva en el escritorio del operador: inmediata, desechable. Boveda del Data Center: acceso mas lento pero almacenamiento masivo y persistente durante la sesion.

Referencias en Memoria, Aliasing y Paso por Valor

¿Cómo Java gestiona los objetos en tiempo de ejecucion y por qué dos variables pueden modificar el mismo estado?

La Variable como Puntero de Memoria

Cuando usted escribe Usuario admin = new Usuario("root");, el JVM realiza dos acciones distintas:

  1. Stack (Pila): Crea la variable admin, que almacena una referencia (direccion de memoria, como un "gafete de acceso" o "credencial de visitante").
  2. Heap (Monton): Reserva espacio para el objeto Usuario con todos sus atributos (el "expediente completo" en la "boveda del Data Center").
// La variable 'admin' esta en el Stack
// El objeto 'new Usuario("root")' reside en el Heap
Usuario admin = new Usuario("root");

// 'admin' NO contiene al objeto.
// 'admin' contiene la direccion donde esta el objeto.
// Analogia: admin es el numero de casillero, no el contenido.

El Fenomeno de Aliasing

El aliasing ocurre cuando dos referencias distintas apuntan al mismo objeto en el Heap. Cualquier modificacion a traves de una referencia es visible a traves de la otra. 

Usuario admin1 = new Usuario("root");
admin1.setIntentosFallidos(2);

// ALIASING: admin2 apunta al MISMO objeto que admin1
Usuario admin2 = admin1;  // NO copia el objeto, copia la referencia

admin2.setIntentosFallidos(5); // Modifica el unico objeto en el Heap

System.out.println(admin1.getIntentosFallidos()); // Imprime 5, no 2
// admin1 y admin2 son dos gafetes distintos 
// colgados en la misma puerta de la boveda

Riesgo de ciberseguridad: Si un metodo recibe una referencia a Usuario y la almacena sin copia defensiva, el codigo externo puede modificar el estado interno del objeto fuera del control del sistema de autenticacion.

Principio Fundamental: Java Siempre Pasa Argumentos por Valor

En Java no existe el paso por referencia como en C++ (&) o C# (ref). Cuando se pasa un objeto como argumento, se pasa el valor de la referencia (la direccion de memoria), no la variable original. Esto significa que:

  • Dentro del metodo no puede reasignar la variable original del llamante a un nuevo objeto.
  • Pero si puede modificar el estado interno del objeto apuntado (porque la copia de la referencia sigue apuntando al mismo objeto en el Heap).

Modularidad, Paquetes y Principio de Menor Privilegio

Como la division en carpetas dentro de IntelliJ IDEA materializa la seguridad en capas del backend

Que es un paquete (package) en Java?

Un paquete es simplemente una carpeta dentro del disco duro para organizar los archivos .java. Usted lo crea en IntelliJ IDEA con clic derecho en src → New → Package, escribe seguridad.model (el punto crea una subcarpeta), y al inicio de cada archivo declara package seguridad.model;. Sin esta organizacion, un proyecto de 300 clases seria imposible de mantener.

seguridad.auth

Capa de Autenticacion: los guardias de seguridad que verifican usuarios y contrasenas. Autenticador, GestorSesion.

seguridad.audit

Capa de Auditoria: la camara de seguridad que registra quien entro y a que hora. LogEvento, Auditor.

seguridad.model

Capa de Modelo: las fichas de datos del negocio. Usuario, Administrador, Rol.

Modificadores de Acceso: Quien puede ver cada atributo?

Un modificador de acceso es la palabra que define quien desde afuera puede ver y cambiar un atributo o metodo. La tabla responde: "Si pongo este modificador, que clases pueden acceder?"

Modificador Clase Paquete Subclase Mundo Analogia
private Su contraseña bancaria
(default) Nota en la refri de su casa
protected El carro familiar
public Letrero en la calle

Aplicacion directa al Principio de Menor Privilegio

PoLP: cada clase debe tener exclusivamente los permisos indispensables. private es la opcion por defecto. Solo se sube el nivel cuando sea estrictamente necesario. 

// INSEGURO: atributos public = cualquiera los modifica
public class UsuarioInseguro {
    public String contraseñaHash;  // Un hacker puede leerla y cambiarla
    public int intentosFallidos;   // Un atacante resetea el bloqueo
}
// ataque: usuario.intentosFallidos = 0;  // Bloqueo burlado

// SEGURO: encapsulamiento estricto con private
public class Usuario {
    private String contraseñaHash;      // Solo esta clase accede
    private int intentosFallidos;       // Solo se modifica via metodo

    public boolean verificarContraseña(String intento) {
        // Toda interaccion pasa por este metodo controlado
        // que aplica bcrypt/scrypt, registra intentos y bloquea
    }
}
Regla de ingenieria: Ponga private a todos sus atributos por defecto. Si otra clase necesita acceder, crea un metodo que valide y audite la operacion. Nunca exponga un atributo como public.

Miembros Estaticos Avanzados y Ciclo de Vida

Del estado individual del usuario a la alarma perimetral global del sistema

Atributos de Instancia vs. Atributos Estaticos

Un atributo de instancia (sin static) pertenece a cada objeto individual. Un atributo estatico pertenece a la clase misma y es compartido por todas las instancias. 

public class Usuario {
    // INSTANCIA: cada usuario tiene su propio contador
    private int intentosFallidos = 0;       
    
    // ESTATICO: UNICO contador global para toda la aplicacion
    private static int totalAtaquesGlobales = 0;
    
    public void registrarIntentoFallido() {
        this.intentosFallidos++;       // Afecta solo a ESTE usuario
        Usuario.totalAtaquesGlobales++; // Afecta el contador GLOBAL
    }
}

// En Main:
Usuario u1 = new Usuario("admin");
Usuario u2 = new Usuario("operador");

u1.registrarIntentoFallido(); // u1.intentos=1, totalAtaques=1
u1.registrarIntentoFallido(); // u1.intentos=2, totalAtaques=2
u2.registrarIntentoFallido(); // u2.intentos=1, totalAtaques=3

// u1.intentosFallidos != u2.intentosFallidos (instancia)
// Ambos comparten totalAtaquesGlobales (estatico)

Bloques Estaticos y Constantes de Seguridad

Un bloque estatico se ejecuta una unica vez, cuando la clase es cargada por el ClassLoader, antes de que exista ninguna instancia. Es el lugar ideal para inicializar politicas de seguridad del sistema. 

public class PoliticaSeguridad {
    // Constante de seguridad: inmutable, global, garantia de integridad
    public static final int MAX_INTENTOS_PERMITIDOS = 3;
    public static final int TIEMPO_BLOQUEO_MINUTOS = 15;
    public static final int LONGITUD_MINIMA_CONTRASEÑA = 12;
    
    private static List<String> ipsBloqueadas;
    
    // Bloque estatico: se ejecuta al cargar la clase
    static {
        System.out.println("[SEGURIDAD] Inicializando politicas...");
        ipsBloqueadas = new ArrayList<>();
        cargarConfiguracionSeguridad();
        System.out.println("[SEGURIDAD] MAX_INTENTOS = " 
            + MAX_INTENTOS_PERMITIDOS);
    }
    
    private static void cargarConfiguracionSeguridad() {
        // Carga desde archivo de configuracion o variable de entorno
    }
}
Analogia de ciberseguridad: intentosFallidos es el contador del detector de humo en la oficina de cada usuario. totalAtaquesGlobales es la alarma perimetral central del edificio: si alcanza un umbral critico, activa protocolos de contencion para todo el sistema, independientemente de quien gatillo la alerta.

Ciclo de Vida de un Miembro Estatico

Carga de Clase

El ClassLoader carga Usuario.class. Se asigna memoria para atributos static en el Metaspace.

Inicializacion

Se ejecutan los bloques static { } y se asignan valores iniciales en orden textual.

Vida Util

Los atributos static viven mientras la clase permanece cargada. Sobreviven a todas las instancias.

Descarga

Cuando el ClassLoader es descargado (raro en aplicaciones convencionales; comun en servidores de aplicaciones al redeployar).

Arquitectura en JDK 25: Inmutabilidad y Records

Del POJO tradicional al Record inmutable — Como Java moderno garantiza la integridad de la auditoria

Antes (Java 8-20): POJO para Auditoria

Clase tradicional con constructor, getters, setters, toString, equals y hashCode manuales o via IDE.

// Java 8: ~55 lineas para un simple DTO de auditoria
public class LogEvento {
    private final String usuario;
    private final String accion;
    private final long timestamp;
    
    public LogEvento(String usuario, String accion, long timestamp) {
        this.usuario = usuario;
        this.accion = accion;
        this.timestamp = timestamp;
    }
    
    public String getUsuario() { return usuario; }
    public String getAccion()  { return accion; }
    public long getTimestamp() { return timestamp; }
    
    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof LogEvento)) return false;
        LogEvento that = (LogEvento) o;
        return timestamp == that.timestamp 
            && usuario.equals(that.usuario) 
            && accion.equals(that.accion);
    }
    
    @Override
    public int hashCode() {
        return Objects.hash(usuario, accion, timestamp);
    }
    
    @Override
    public String toString() {
        return "LogEvento{usuario='" + usuario 
            + "', accion='" + accion 
            + "', timestamp=" + timestamp + "}";
    }
}

Ahora (JDK 25): Record Inmutable

Una sola linea. El compilador genera automaticamente constructor canonico, accessors, equals, hashCode y toString.

// JDK 25: 1 linea. Inmutable por diseño.
public record LogEvento(
    String usuario, 
    String accion, 
    long timestamp
) {
    // Constructor compacto: validacion sin redundancia
    public LogEvento {
        if (usuario == null || usuario.isBlank()) {
            throw new IllegalArgumentException(
                "usuario no puede ser nulo ni vacio");
        }
        if (accion == null || accion.isBlank()) {
            throw new IllegalArgumentException(
                "accion no puede ser nula ni vacia");
        }
    }
    
    // Metodo de consulta derivado (no almacena dato extra)
    public boolean esReciente() {
        long ahora = System.currentTimeMillis();
        return (ahora - timestamp) < 3600_000; // 1 hora
    }
}

// Uso: inmutable, legible, sin boilerplate
var evento = new LogEvento("admin", "LOGIN_EXITOSO", 
    System.currentTimeMillis());
Resultado: De ~55 lineas de codigo repetitivo y propenso a errores a 1 linea declarativa. El compilador garantiza la correccion de equals, hashCode y toString.
Impacto en ciberseguridad: La inmutabilidad del record garantiza el no repudio (nadie puede modificar retroactivamente la auditoria), la thread-safety (multiples hilos leen sin sincronizacion) y la integridad referencial (los accessors no exponen referencias mutables).

Programacion Generica en Java (Generics)

Como los tipos parametrizados <T> eliminan errores en tiempo de ejecucion y refuerzan la seguridad del backend

Analogia: El problema que resuelven los Generics

Imagine que tiene una caja de carton (ArrayList) donde puede guardar cualquier cosa: un libro, un sandwich, una llave. Cuando mete la mano para sacar algo, no sabe que va a encontrar. Podria esperar un libro y sacar un sandwich podrido. Eso es lo que pasaba antes de Java 5: la caja aceptaba cualquier objeto (Object) y al sacarlo habia que "adivinar" que era (casting). Con Generics, usted le pone una etiqueta a la caja: ArrayList<Libro> solo acepta libros. El compilador se convierte en un guardia que revisa la etiqueta al escribir el codigo, no cuando el programa ya esta corriendo.

El Problema Historico (Antes de Java 5)

Antes de Generics, un ArrayList era una caja sin etiqueta: guardaba cualquier tipo de objeto. Para recuperar un elemento, el programador debia hacer un casting manual, "adivinando" el tipo. El compilador no podia verificar si el casting era correcto: 

// ⚠ ANTES de Java 5: codigo peligroso

// 1️⃣ Creamos una lista SIN etiqueta de tipo
ArrayList lista = new ArrayList();

// 2️⃣ Guardamos un Usuario... ✅
lista.add(new Usuario("admin"));

// 3️⃣ ...y tambien un String por accidente
lista.add("texto arbitrario"); // El compilador NO avisa 😱

// 4️⃣ Al sacar el elemento, "adivinamos" que es Usuario
Usuario u = (Usuario) lista.get(1);
// 💥 ClassCastException en tiempo de ejecucion!
// El programa truena porque el elemento #1 es String

El ClassCastException ocurre mientras el programa esta corriendo, quizas frente al usuario final. En un sistema de seguridad, esto podria tumbar todo el backend.

La Solucion Moderna: Type Safety

Con type safety, usted etiqueta el ArrayList al declararlo: ArrayList<Usuario> significa "esta caja solo acepta Usuarios". El compilador se convierte en un guardia que rechaza cualquier objeto de otro tipo: 

// ✅ DESDE Java 5+: codigo seguro

// 1️⃣ La etiqueta <Usuario> es un CONTRATO:
//    "Esta lista solo guarda objetos de tipo Usuario"
ArrayList<Usuario> lista = new ArrayList<>();

// 2️⃣ Guardamos un Usuario ✅
lista.add(new Usuario("admin"));

// 3️⃣ Si intentamos guardar otra cosa...
// lista.add("texto"); // ❌ ERROR DE COMPILACION
// IntelliJ lo subraya en rojo ANTES de ejecutar

// 4️⃣ Al sacar, NO necesitamos adivinar el tipo
Usuario u = lista.get(0); // Sin casting, el tipo esta 100% garantizado
Resultado: El error se detecta mientras usted escribe (IntelliJ lo subraya en rojo), no cuando el sistema ya esta en produccion. Es como que el arquitecto revise los planos antes de construir el edificio.

Aplicacion Real: Una Clase de Respuesta para Gobernarlos a Todos

En un sistema de seguridad, el metodo login() devuelve un Usuario, pero consultarAuditoria() devuelve una List<LogEvento>. Sin Generics necesitaria crear una clase distinta para cada tipo de respuesta (RespuestaUsuario, RespuestaLogEvento, RespuestaLista...). Con Generics, crea una sola clase que se adapta a cualquier tipo: 

// ✅ UNA sola clase, INFINITOS usos
// <T> significa "T va a ser el tipo que YO (el programador) decida al usarla"
public class RespuestaSeguridad<T> {
    private boolean exito;       // ¿La operacion funciono?
    private String mensaje;      // Detalle legible para humanos
    private T datos;             // El contenido real (puede ser cualquier tipo)
    
    public RespuestaSeguridad(boolean exito, String mensaje, T datos) {
        this.exito = exito;
        this.mensaje = mensaje;
        this.datos = datos;
    }
    
    public T getDatos() { return datos; }    // Retorna el tipo T que definiste al crear la respuesta
    public boolean esExitoso() { return exito; }
}

// === USO: la misma clase, tres tipos distintos ===

// 1️⃣ Cuando T = Usuario (respuesta de login)
RespuestaSeguridad<Usuario> r1 =
    new RespuestaSeguridad<>(true, "Autenticado", admin);
Usuario user = r1.getDatos(); // El compilador SABE que es Usuario

// 2️⃣ Cuando T = LogEvento (respuesta de auditoria)
RespuestaSeguridad<LogEvento> r2 =
    new RespuestaSeguridad<>(true, "Evento registrado", evento);
LogEvento log = r2.getDatos(); // El compilador SABE que es LogEvento

// 3️⃣ Cuando T = List<LogEvento> (respuesta de historial)
RespuestaSeguridad<List<LogEvento>> r3 =
    new RespuestaSeguridad<>(true, "Historial completo", listaEventos);

// Sin Generics → 3 clases distintas (RespuestaUsuario, RespuestaLog, RespuestaLista)
// Con Generics  → 1 sola clase. El compilador verifica cada uso.
En resumen: <T> es un comodin. Usted dice parametrizar — "quiero que T sea Usuario" — y el compilador reemplaza mentalmente cada T por Usuario y verifica que todo cuadre. Esto se llama polimorfismo parametrico.

Herencia, Interfaces y Composicion

Tres herramientas distintas para reutilizar codigo — Saber cual usar evita dolores de cabeza

Antes de empezar: tres conceptos que NO son lo mismo

extends

= Herencia

Palabra clave de Java. Relacion "es-un". La subclase recibe automaticamente todos los metodos y atributos (no privados) de la superclase.

Admin extends Usuario
→ Admin es un Usuario

implements

= Interfaces

Palabra clave de Java. Relacion "cumple-el-contrato-de". La clase se compromete a implementar ciertos metodos, pero no recibe codigo heredado.

Usuario implements Auditable
→ Usuario cumple el contrato Auditable

Composicion

≠ Interfaces

Principio de diseño (no una palabra clave). Relacion "tiene-un". Una clase guarda una referencia a otra como atributo y le delega trabajo.

Auditor tiene un Usuario
→ Auditor usa un Usuario, no lo extiende

extends = Herencia: "es-un"

Cuando una clase "es" otra clase pero con esteroides. Administrador no es un tipo de usuario cualquiera: es un Usuario con superpoderes adicionales. Al poner extends, recibe gratis todos los metodos ya escritos en Usuario. 

// Clase PADRE: define lo que TODO usuario tiene
public class Usuario {
    protected String nombreUsuario;   // 'protected' = visible para subclases
    protected String contraseñaHash;
    private int intentosFallidos;     // 'private' = NI los hijos lo ven
    
    public boolean autenticar(String pass) {
        // 30 lineas de validacion segura...
    }
}

// Clase HIJA: hereda todo lo de Usuario + agrega lo suyo
public class Administrador extends Usuario {
    // ⬆ extends = "soy un Usuario PERO ADEMAS..."
    
    private String nivelAcceso; // "TOTAL", "AUDITORIA"
    
    // ✅ Hereda autenticar() sin escribir ni una linea
    // ✅ Hereda nombreUsuario y contraseñaHash
    // ❌ NO hereda intentosFallidos (es private)
    
    // Nuevo metodo EXCLUSIVO del administrador:
    public void desbloquearUsuario(Usuario u) {
        // Solo un Admin TOTAL puede desbloquear
        if (!"TOTAL".equals(this.nivelAcceso)) {
            throw new SecurityException("Acceso denegado");
        }
        u.bloqueado = false;
    }
}
Regla mental: Preguntese "¿X ES un Y?" → Si la respuesta es un SI rotundo, use extends. "¿Administrador ES un Usuario?" → SI ✅

implements = Interfaces: "cumple-el-contrato-de"

Una interfaz es un contrato: dice qué métodos deben existir, pero NO regala código. La clase que firma el contrato (implements) debe escribir la implementación con su propio esfuerzo. Esto permite que clases sin parentesco compartan un comportamiento común. 

// El CONTRATO: define QUE metodos deben existir
public interface Auditable {
    void generarLogAuditoria(String evento);  // Firma sin cuerpo
    List<LogEvento> obtenerHistorial();
    
    // Metodo default (Java 8+): implementacion de cortesia
    default void auditarConTimestamp(String evento) {
        System.out.println("[AUDIT " 
            + System.currentTimeMillis() + "] " + evento);
        generarLogAuditoria(evento); // Usa el metodo que la clase implemento
    }
}

// Usuario FIRMA el contrato Auditable
public class Usuario implements Auditable {
    // ⬆ implements = "me comprometo a tener estos metodos"
    
    private List<LogEvento> historial = new ArrayList<>();
    
    @Override // Obligatorio: YO escribo el codigo
    public void generarLogAuditoria(String evento) {
        historial.add(new LogEvento(
            this.nombreUsuario, evento,
            System.currentTimeMillis()));
    }
    
    @Override
    public List<LogEvento> obtenerHistorial() {
        return List.copyOf(historial); // copia defensiva
    }
}
Regla mental: Preguntese "¿X DEBE cumplir con el comportamiento Y?" → Use implements. "¿Usuario DEBE ser Auditable?" → SI ✅ (todo usuario debe dejar rastro).

Composicion = "tiene-un": La alternativa a extends

Composicion NO es una palabra clave de Java. Es un principio de diseño: en lugar de heredar de una clase, guarda una referencia a esa clase como atributo y le pide que haga el trabajo por usted. Es como un gerente que no sabe programar pero tiene programadores en su equipo: él delega, no hereda.

❌ Herencia forzada (lo que NO debe hacer)

Un Auditor NO es un Usuario. Es un empleado que usa usuarios. Si igual fuerza extends, arrastra atributos que no necesita.

// ❌ MAL: Auditor NO es un Usuario
public class Auditor extends Usuario {
    // Hereda cosas SIN SENTIDO:
    // contraseñaHash, intentosFallidos, autenticar()...
    // ¡Un auditor no necesita contraseña!
    
    public void revisarLogs() { /* ... */ }
}

✅ Composicion: "tiene-un" (lo correcto)

El Auditor tiene una lista de usuarios para revisar. No hereda nada: simplemente guarda referencias y les pide datos.

// ✅ BIEN: Auditor TIENE usuarios (no ES uno)
public class Auditor {
    private String nombreEmpleado;
    private List<Usuario> usuariosAsignados; // ← composicion
    
    public Auditor(String nombre, List<Usuario> users) {
        this.nombreEmpleado = nombre;
        this.usuariosAsignados = users; // Guarda referencia
    }
    
    public void revisarLogs() {
        for (Usuario u : usuariosAsignados) {
            u.obtenerHistorial(); // Delega: pide al usuario su data
        }
    }
}

¿Cuando usar extends?

  • La relacion "es-un" es indiscutible (Administrador ES Usuario).
  • Quiere heredar codigo ya escrito y agregarle mas.
  • La clase padre fue diseñada para ser extendida.

¿Cuando usar Composicion?

  • La relacion es "tiene-un" o "usa-un" (Auditor tiene Usuarios).
  • No quiere heredar atributos que no necesita.
  • Quiere poder cambiar el comportamiento en tiempo de ejecucion (cambiar el objeto guardado).
En resumen: extends = "ES un" (herencia de codigo). implements = "CUMPLE el contrato de" (interfaces). Composicion = "TIENE un" (atributo que referencia a otro objeto). De estos tres, composicion es el mas seguro y flexible. Empiece siempre preguntandose "¿puedo resolver esto con composicion?" antes de usar extends.

Rendimiento vs. Seguridad: Stack vs. Heap en Profundidad

Stack (Pila de Llamadas)

Cada hilo en la JVM posee su propia pila. Cuando un metodo es invocado, se crea un stack frame que contiene las variables locales y las referencias a objetos. Al finalizar el metodo, el marco se destruye automaticamente.

Heap (Monton de Objetos)

Region de memoria compartida entre todos los hilos. Aqui residen todas las instancias de clase y arrays. El Garbage Collector monitorea que objetos han perdido toda referencia desde el Stack para liberar su memoria. 

public class DemostracionMemoria {
    public static void main(String[] args) {
        int x = 42;                    // [STACK] variable local primitiva
        Usuario u = new Usuario("admin"); // [STACK] referencia 'u'
                                         // [HEAP]  objeto Usuario{nombre="admin"}
        
        modificarDatos(x, u);
        System.out.println(x);           // 42 (int es primitivo: paso por valor)
        System.out.println(u.getIntentos()); // 99 (el objeto en Heap fue modificado)
    }
    
    static void modificarDatos(int numero, Usuario ref) {
        numero = 999;                  // Modifica la COPIA local en el stack frame
        ref.setIntentosFallidos(99);   // Modifica el OBJETO en el Heap via la copia de la referencia
        ref = new Usuario("otro");     // Reasigna la COPIA de la referencia (no afecta a main)
    }
}

// Resultado: x sigue siendo 42, u.getIntentos() es 99
// La referencia se paso por valor: main() y modificarDatos() 
// tienen copias independientes de la direccion, pero ambas 
// apuntaban (inicialmente) al mismo objeto.
Conclusion de arquitectura: En el backend del sistema de seguridad, los primitivos deben usarse para contadores locales y operaciones de corta duracion donde la velocidad es critica. Los wrappers (Long, Integer) y objetos deben usarse para datos que cruzan la frontera con la base de datos, donde null tiene significado semantico. Comprender que vive en el Stack y que en el Heap es fundamental para diagnosticar problemas de memoria y condiciones de carrera en sistemas concurrentes.

Anatomia del NullPointerException

Que ocurre realmente?

Cuando el JVM ejecuta u.autenticar("pass") y u es null, intenta desreferenciar el puntero nulo. Es como intentar abrir un casillero con un gafete que dice "NINGUNO". El sistema operativo detecta el acceso a la direccion de memoria 0x0 y la JVM traduce esa senal en la excepcion.

Como prevenirlo estructuralmente

  • Validacion temprana: Objects.requireNonNull(param, "mensaje") en constructores y setters.
  • Optional<T>: Para valores que legtimamente pueden estar ausentes. No usar Optional como campo de clase (no es Serializable), sino como tipo de retorno de metodos.
  • Anotaciones: @Nullable y @NotNull (javax.annotation, JetBrains, o Checker Framework) para documentar la intencion y permitir que IntelliJ IDEA advierta en tiempo de edicion.
  • Records: Los records con constructor compacto pueden validar que ningun campo sea null desde la construccion.
// PRACTICA DEFENSIVA RECOMENDADA
public class UsuarioSeguro {
    private String nombreUsuario;
    
    public UsuarioSeguro(String nombreUsuario) {
        // Validacion temprana: falla rapido con mensaje claro
        this.nombreUsuario = Objects.requireNonNull(
            nombreUsuario, 
            "nombreUsuario no puede ser null");
    }
    
    // Metodo que puede retornar ausencia de valor
    public Optional<String> getEmailRecuperacion() {
        return Optional.ofNullable(emailRecuperacion);
    }

// El llamante maneja la ausencia explicitamente:
usuario.getEmailRecuperacion()

Regla de ingenieria: Un NullPointerException en produccion es un fallo de diseño, no un problema del usuario. Si el sistema permite que una referencia sea null sin que el codigo que la consume este preparado, hay una violacion del contrato entre componentes. La validacion defensiva en los puntos de entrada (constructores, metodos publicos) es la unica estrategia robusta.
