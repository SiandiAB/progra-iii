Arquitectura de Software

El cimiento de toda aplicación profesional.

Definición

La arquitectura de software es la organización fundamental de un sistema, reflejada en sus componentes, las relaciones entre ellos, y los principios que guían su diseño y evolución.

No se trata solo de cómo se ve el código, sino de cómo se comporta ante cambios, cómo se mantiene y cómo se escala.

  • Robustez: Tolerancia a errores y cambios.
  • Flexibilidad: Facilidad para incorporar nuevas funcionalidades.
  • Fluidez: Comprensión clara de la estructura.
  • Portabilidad: Independencia de plataforma.

MVC: Modelo-Vista-Controlador

El estándar de oro para interfaces de usuario.

Modelo

  • Datos y lógica de negocio.
  • Estado de la aplicación.
  • No sabe nada de la interfaz.
  • Ejemplo: clases Factura, Usuario.

Vista

  • Interfaz gráfica (Swing, JavaFX).
  • Renderiza los datos del Modelo.
  • Captura eventos del usuario.
  • Ejemplo: JFrame, JButton.

Controlador

  • Intermediario entre Vista y Modelo.
  • Recibe eventos, invoca lógica.
  • Actualiza la Vista según resultados.
  • Ejemplo: FacturaControlador.
Flujo: Usuario → Vista → Controlador → Modelo → Controlador → Vista (actualizada)

El Modelo

El corazón de la lógica de negocio.

El Modelo encapsula el dominio de la aplicación. Es la representación de los datos y las reglas que los gobiernan.

  • Estado: atributos que describen una entidad.
  • Comportamiento: métodos que implementan la lógica.
  • Independencia: no debe importar cómo se muestra ni cómo se persiste.
Ejemplo: Una clase Producto con precio, nombre, y métodos para calcular descuentos.
Producto.java 
public class Producto {
    private String nombre;
    private double precio;
    private double iva = 0.13;

    public Producto(String n, double p) {
        this.nombre = n;
        this.precio = p;
    }

    public double calcularPrecioFinal() {
        return precio * (1 + iva);
    }

    // Getters y setters (omitidos)
}

La Vista

La cara visible de la aplicación.

La Vista es la interfaz de usuario. Su responsabilidad es renderizar el estado del Modelo y capturar las interacciones del usuario (clics, tecleo).

  • Pasiva: No contiene lógica de negocio.
  • Observadora: Escucha cambios en el Modelo (a través del patrón Observer).
  • Delega: Todas las acciones del usuario se pasan al Controlador.
Ejemplo: Una ventana con campos de texto y botones, sin ningún cálculo.
VentanaProducto.java 
public class VentanaProducto extends JFrame {
    private JTextField txtNombre, txtPrecio;
    private JLabel lblResultado;
    private JButton btnCalcular;

    public VentanaProducto() {
        // Inicializa componentes (setText, setLayout...)
        // El listener del botón llama al Controlador
        btnCalcular.addActionListener(e -> {
            // NO calcular aquí, solo invocar al controlador
            ControladorProducto ctrl = new ControladorProducto();
            double resultado = ctrl.calcular(txtPrecio.getText());
            lblResultado.setText("Total: $" + resultado);
        });
    }
}

El Controlador

El cerebro que coordina todo.

El Controlador actúa como intermediario. Recibe las solicitudes de la Vista, las traduce en operaciones sobre el Modelo y decide qué vista mostrar a continuación.

  • Orquestador: Coordina el flujo de la aplicación.
  • Ligero: Idealmente, no contiene lógica de negocio; solo la invoca.
  • Reutilizable: Un controlador puede servir para múltiples vistas.
Ejemplo: Un controlador que recibe un precio, instancia un Producto, calcula el total y lo retorna.
ControladorProducto.java 
public class ControladorProducto {
    public double calcular(String precioTexto) {
        try {
            double precio = Double.parseDouble(precioTexto);
            Producto p = new Producto("Genérico", precio);
            return p.calcularPrecioFinal();
        } catch (NumberFormatException e) {
            // Podría lanzar una excepción o devolver 0
            return 0;
        }
    }
}

Flujo MVC en acción

Cómo se comunican las capas paso a paso.

1. Interacción

Usuario hace clic en un botón.

2. Delegación

La Vista invoca al Controlador.

3. Lógica

Controlador opera sobre el Modelo.

4. Resultado

El Modelo retorna datos al Controlador.

5. Actualización

Controlador ordena a la Vista refrescarse.

6. Visualización

El usuario ve el nuevo estado.

La Vista nunca toca el Modelo directamente; todo pasa por el Controlador.

Variantes de MVC

Adaptaciones del patrón para diferentes contextos.

MVP

Modelo-Vista-Presentador. La Vista se vuelve completamente pasiva y el Presentador (similar al Controlador) maneja toda la lógica de presentación. Muy usado en Android.

MVVM

Modelo-Vista-Modelo de Vista. Introduce un ViewModel que expone datos y comandos a la Vista mediante enlace de datos (data binding). Popular en WPF y frameworks web modernos.

N-capas

Arquitectura en capas. Separa físicamente las responsabilidades en capas: presentación, lógica de negocio, acceso a datos. Cada capa puede estar en diferentes servidores.

Aunque existen variantes, MVC sigue siendo la base conceptual que todas comparten.

¿Por qué son diferentes?

Cambian qué tan pasiva es la Vista y quién media la comunicación con el Modelo.

Patrón ¿La Vista ve al Modelo? ¿Quién dirige?
MVC Sí (lo observa) El Controlador
MVP No, es pasiva El Presentador
MVVM No El ViewModel
N-capas No cambia el flujo: separa físicamente las capas

¿Cuándo usar cada una?

  • MVC: referencia estándar de partida.
  • MVP: cuando el testing de la UI es prioridad (Android).
  • MVVM: con data binding (WPF, web moderno).
  • N-capas: sistemas empresariales grandes.

Regla mental: MVC deja la Vista activa; MVP la vuelve pasiva; MVVM automatiza la comunicación; N-capas cambia dónde vive cada capa.

Observer

Notificación automática de cambios.

El patrón Observer define una dependencia uno-a-muchos entre objetos, de modo que cuando un objeto cambia de estado, todos sus dependientes son notificados y actualizados automáticamente.

  • Sujeto: El objeto que mantiene el estado (ej. el Modelo).
  • Observadores: Los objetos que dependen del estado (ej. las Vistas).
En Swing, los ActionListener son observadores que esperan eventos del botón (sujeto).
Observer en Java 
import java.util.Observable;
import java.util.Observer;

// Sujeto
class Modelo extends Observable {
    private int valor;
    public void setValor(int v) {
        valor = v;
        setChanged();
        notifyObservers(valor); // Notifica a todos
    }
}

// Observador
class Vista implements Observer {
    public void update(Observable o, Object arg) {
        System.out.println("Nuevo valor: " + arg);
    }
}

¿Se hace solo?

  • No por sí solo: el patrón lo implementas tú (el Sujeto guarda y notifica).
  • Observable / Observer es semiautomático: debes llamar setChanged() y notifyObservers() manualmente. Deprecados desde Java 9.
  • En Swing/JavaFX sí es automático: con addActionListener() el framework notifica por ti y el emisor no conoce a los oyentes.

¿Cuándo usarlo?

Relación uno-a-muchos y quieres desacoplar al emisor de los receptores.

  • Usar: varias vistas de un mismo modelo; eventos de UI.
  • No usar: un solo receptor, o si basta un acoplamiento simple — agrega complejidad y es difícil de depurar.

Composite

Tratar objetos individuales y compuestos de forma uniforme.

El patrón Composite permite construir estructuras de árbol donde los objetos compuestos y los primitivos son tratados de la misma manera. Es fundamental en las jerarquías de componentes gráficos.

  • Componente: Interfaz común para todos los elementos.
  • Hoja: Objeto simple (ej. un botón).
  • Compuesto: Contiene hijos (ej. un panel con varios botones).
En Swing, JComponent es la base; JButton es hoja y JPanel es compuesto.
Composite en GUI 
// Todos son JComponent
JFrame frame = new JFrame();
JPanel panel = new JPanel(); // compuesto
panel.add(new JButton("Aceptar")); // hoja
panel.add(new JButton("Cancelar"));
frame.add(panel); // frame también es compuesto

// Se puede recorrer la jerarquía con getComponents()
for (Component c : frame.getComponents()) {
    System.out.println(c.getName());
}

¿Para qué sirve?

  • Trata igual un objeto simple y un contenedor: no pregunta "¿es un grupo?".
  • La recursividad la maneja cada nodo, no el cliente.

¿Cuándo se usa?

  • Estructuras de árbol parte-todo: menús y submenús, sistemas de archivos, organigramas, componentes GUI.
  • Pista: "Composite hace que un panel con botones y un botón se traten igual."

Strategy

Algoritmos intercambiables en tiempo de ejecución.

El patrón Strategy permite definir una familia de algoritmos, encapsularlos y hacerlos intercambiables. El cliente puede seleccionar la estrategia adecuada en tiempo de ejecución.

  • Contexto: El objeto que usa la estrategia.
  • Estrategia: Interfaz común para todos los algoritmos.
  • Implementaciones concretas: Cada variante del algoritmo.
En MVC, el Controlador actúa como la estrategia que la Vista utiliza para manejar las acciones del usuario.
Strategy en Java 
// Interfaz estrategia
interface Operacion {
    int ejecutar(int a, int b);
}

// Estrategias concretas
class Suma implements Operacion {
    public int ejecutar(int a, int b) { return a + b; }
}
class Multiplicacion implements Operacion {
    public int ejecutar(int a, int b) { return a * b; }
}

// Contexto que usa la estrategia
class Calculadora {
    private Operacion estrategia;
    public void setEstrategia(Operacion e) { this.estrategia = e; }
    public int calcular(int a, int b) {
        return estrategia.ejecutar(a, b);
    }
}

¿No es solo una interfaz?

La interfaz es la herramienta; Strategy es la intención de diseño.

  • Con herencia el comportamiento queda fijo (se elige al compilar).
  • Con Strategy se intercambia en tiempo de ejecución: setEstrategia(new Multiplicacion()), sin recompilar ni if/else.

¿Cuándo usarlo?

  • Usar: familia de algoritmos (ordenamientos, descuentos, pagos); cambiar de algoritmo en caliente; eliminar switch largos; testear cada variante por separado.
  • No usar: si hay una sola implementación o nunca cambiará — una interfaz normal basta.

Separación de Componentes

Organización física del código en módulos reutilizables.

La separación de componentes va más allá de la división lógica en paquetes. Implica empaquetar físicamente el código en unidades independientes llamadas bibliotecas o JARs.

  • Modularidad: Cada biblioteca tiene una responsabilidad única.
  • Reutilización: Una biblioteca puede usarse en múltiples proyectos.
  • Mantenimiento: Cambios en un módulo no afectan a otros si la interfaz se mantiene.

Código Fuente (.java)

Módulos lógicos.

Compilación y empaquetado

Biblioteca (.jar)

Definición y Construcción de Bibliotecas

Creando artefactos reutilizables.

Una biblioteca en Java es un archivo .jar que contiene clases compiladas, recursos y metadatos. Se construye mediante el comando jar o desde el IDE (IntelliJ: Build Artifact).

Las bibliotecas permiten compartir funcionalidades como acceso a bases de datos, utilidades matemáticas, o incluso capas enteras de una aplicación (ej. acceso-datos.jar).

Pasos básicos para crear un JAR:
  1. Compilar todas las clases.
  2. Crear un archivo de manifiesto (MANIFEST.MF) opcional.
  3. Ejecutar: jar cf mi-biblioteca.jar *.class.
Comando jar 
# Crear JAR con todas las clases
$ jar cf utilidades.jar com/miempresa/util/*.class

# Ver contenido del JAR
$ jar tf utilidades.jar

# Extraer JAR
$ jar xf utilidades.jar

# Incluir manifiesto personalizado
$ jar cfm mi-app.jar MANIFEST.MF -C classes/ .

En IntelliJ, puedes crear un JAR desde File → Project Structure → Artifacts.

Referencias entre Bibliotecas

Cómo vincular módulos en el classpath.

Para que una biblioteca A pueda usar clases de la biblioteca B, debemos agregar B al classpath de A. Esto se hace al compilar y al ejecutar.

  • Compilación: javac -cp "lib/b.jar" src/*.java
  • Ejecución: java -cp "lib/b.jar;classes" MiApp
  • IDEs: IntelliJ maneja las referencias a través de Libraries o Modules.

Ejemplo en IntelliJ

  1. Ve a File → Project Structure → Modules.
  2. En la pestaña Dependencies, haz clic en + → JARs or directories.
  3. Selecciona el archivo .jar de la biblioteca B.
  4. El IDE ahora reconoce las clases de B en el proyecto A.
Las referencias también pueden ser transitivas: si A depende de B y B depende de C, A necesita a C en el classpath.

Dependencia

Dirección y control del acoplamiento.

Dependencia significa que un módulo necesita a otro para funcionar. En arquitectura limpia, las dependencias deben apuntar hacia adentro, desde las capas externas (Vista) hacia las internas (Modelo).

  • Acoplamiento bajo: Los módulos dependen de abstracciones, no de implementaciones concretas.
  • Inversión de dependencias: Las capas de alto nivel no dependen de las de bajo nivel; ambas dependen de abstracciones.
Ejemplo: La Vista depende del Controlador (interfaz), no del Controlador concreto. Esto permite cambiar la implementación sin afectar la Vista.

Dirección de dependencia en MVC

Vista Controlador Modelo

El Modelo no depende de nadie.

Dependencias unidireccionales reducen el impacto de los cambios.

Persistencia Básica

Guardar datos más allá de la memoria RAM.

La persistencia es el mecanismo para almacenar el estado de los objetos en medios no volátiles. Existen varias estrategias:

  • Serialización de texto: Archivos CSV, TXT con separadores.
  • Serialización binaria: Usando ObjectOutputStream (específico de Java).
  • XML: Formato estándar y legible por humanos.
  • Bases de datos: Relacionales o NoSQL (se verán más adelante).

En proyectos sin BD, la serialización en archivos permite mantener datos entre ejecuciones.

Serialización de texto

Ejemplo: "Juan,25,30000" separado por comas.

Serialización binaria

Utiliza Serializable y flujos de bytes. Eficiente pero no interoperable.

XML

Estructura jerárquica con etiquetas: <nombre>Juan</nombre>

¿Qué estrategia conviene?

Criterio Binaria Texto (CSV) XML
Legible
Interoperable solo Java manual
Automático parseo manual anotaciones
Tamaño/velocidad verboso

¿Cuál usar?

  • Binaria: persistir objetos entre ejecuciones sin BD (rápida y automática).
  • Texto: datos simples y editables a mano.
  • XML/JSON: intercambiar con otros sistemas o datos legibles.

Serialización en Java

Guardar y restaurar objetos con Serializable.

Java proporciona el mecanismo de serialización a través de la interfaz Serializable. Basta con marcar la clase y usar ObjectOutputStream para escribir el objeto en un archivo.

  • Restricciones: Todos los atributos deben ser serializables (o marcados transient).
  • Versiones: Se recomienda definir serialVersionUID para controlar la compatibilidad.
  • Uso: Ideal para guardar configuraciones, sesiones o datos temporales.
Serialización 
// Clase serializable
class Empleado implements Serializable {
    private static final long serialVersionUID = 1L;
    private String nombre;
    private double salario;
}

// Guardar
try (ObjectOutputStream oos = new ObjectOutputStream(
        new FileOutputStream("empleado.dat"))) {
    oos.writeObject(new Empleado("Ana", 35000));
}

// Recuperar
try (ObjectInputStream ois = new ObjectInputStream(
        new FileInputStream("empleado.dat"))) {
    Empleado e = (Empleado) ois.readObject();
}

Detalles clave

  • Serializable es una interfaz de marcado: no tiene métodos.
  • serialVersionUID: si la clase cambia sin actualizarlo, al leer datos viejos lanza InvalidClassException.
  • transient: el campo no se guarda (contraseñas, conexiones) y se recupera con su valor por defecto.
  • Los campos static tampoco se serializan (son de la clase, no del objeto).
  • Conserva el grafo de objetos: referencias y ciclos se mantienen.

Ventajas y riesgos

  • Ventaja: automático, rápido y sin código extra por campo.
  • Desventaja: formato propietario de Java — no lo leen otros lenguajes.
  • Desventaja: frágil ante cambios de clase.
  • Riesgo de seguridad: deserializar datos no confiables puede ejecutar código. ¡Nunca deserialices archivos de dudosa procedencia!

Serialización XML

Estructura legible y estándar para el intercambio de datos.

XML (eXtensible Markup Language) es un formato de texto que organiza los datos en una estructura jerárquica de etiquetas. Es ampliamente usado en servicios web, archivos de configuración y persistencia.

  • Autodescriptivo: Las etiquetas indican el significado de los datos.
  • Interoperable: Puede ser leído por cualquier lenguaje.
  • Java: Se puede usar JAXB para mapear objetos a XML.
En el curso, veremos XML como alternativa a la serialización binaria cuando se requiera interoperabilidad.
XML con JAXB 
// Clase anotada para JAXB
@XmlRootElement
class Empleado {
    @XmlElement private String nombre;
    @XmlElement private double salario;
}

// Serializar a XML
JAXBContext ctx = JAXBContext.newInstance(Empleado.class);
Marshaller marshaller = ctx.createMarshaller();
marshaller.marshal(new Empleado("Ana", 35000), System.out);

// Deserializar desde XML
Unmarshaller unmarshaller = ctx.createUnmarshaller();
Empleado e = (Empleado) unmarshaller.unmarshal(new File("empleado.xml"));

Anotaciones de JAXB

  • @XmlRootElement: define el nodo raíz del documento.
  • @XmlElement: el campo se convierte en un elemento.
  • @XmlAttribute: el campo se convierte en un atributo del elemento.
  • @XmlTransient: el campo se ignora.
  • Marshaller: objeto → XML. Unmarshaller: XML → objeto.

JAXB en JDK 11+

JAXB venía incluido en Java 8, pero fue removido del JDK en Java 11 (módulo java.xml.bind).

En JDK 11 o superior hay que agregar la dependencia manualmente:

<dependency>
    <groupId>jakarta.xml.bind</groupId>
    <artifactId>jakarta.xml.bind-api</artifactId>
    <version>4.0.2</version>
</dependency>
