¿Por qué se necesita la Arquitectura?

El peligro del botón "habelotodo" (código espagueti monolítico).

Sin Arquitectura (Todo Mezclado)

Todo centralizado dentro del método del botón en la ventana:

VentanaChat.java 
// En el controlador o evento de la vista:
btnEnviar.setOnAction(e -> {
    // 1. Extrae datos de la pantalla (GUI)
    String texto = txtMensaje.getText();
    
    // 2. Valida reglas de negocio
    if (texto.contains("spam")) return;
    
    // 3. Escribe directamente en archivo/disco
    FileWriter fw = new FileWriter("chat.txt", true);
    fw.write(texto); 
    fw.close();
    
    // 4. Modifica la interfaz gráfica
    lblAlerta.setText("¡Enviado!");
});

¿Qué sucede si el sistema crece?

1. Se cambia la interfaz a Web/Móvil: Se debe descartar y reescribir todo porque las validaciones y el guardado estaban amarrados al botón de JavaFX.

2. Se cambia el archivo plano por MySQL: Se debe abrir cada ventana y modificar código visual para adaptar la persistencia.

3. Solución (Separación de Responsabilidades): Cada clase tiene un único rol: renderizar pantalla, procesar lógica o persistir datos.

Principio de Responsabilidad Única (SRP): Un módulo debe tener una, y solo una, razón para cambiar.

Pregunta para la clase:

"Si tuviera que cambiar el almacenamiento de archivo plano a MySQL en ese código... ¿Cuántas líneas y en cuántos lugares tendría que modificar?"

Respuesta: prácticamente todo el método del botón, y además todas las otras ventanas que también escriben en el archivo.

Arquitectura MVC (Modelo - Vista - Controlador)

Desacoplando la interfaz de usuario en tres componentes especializados.

M

Modelo (Model)

"El Cerebro y Estado"

Contiene las entidades de datos (Message, User) y el estado interno. No sabe que existe una ventana gráfica ni qué botón se acciona.

public class Message { ... }
V

Vista (View)

"Los Ojos y la Cara"

El archivo .fxml y estilos CSS. Expone la información gráfica al usuario y captura clics/teclado. No calcula ni procesa datos.

<BorderPane prefWidth="700">
C

Controlador (Controller)

"El Mediador / Director"

Escucha los eventos de la Vista (@FXML handleSend), los interpreta, solicita al Modelo o Servicios que actúen, y actualiza la Vista.

@FXML private void handleSend()

Flujo de comunicación en MVC

Usuario (clic) Controlador (llama) Modelo (cambia estado) (notifica) Vista (se actualiza)

Ejemplo concreto: cuando el usuario hace clic en "Enviar", el Controlador NO guarda el archivo, solo le indica al Modelo: "agregue este mensaje". El Modelo modifica su lista interna y la Vista se actualiza sola gracias a ObservableList.

Variantes Modernas de MVC:

MVP (Model-View-Presenter): El Presenter maneja toda la actualización de la UI estrictamente mediante interfaces.
MVVM (Model-View-ViewModel): Popular en WPF y Android/iOS mediante enlace de datos bidireccional (Data Binding).

Pausa activa:

¿Cuál de estas NO es una responsabilidad del Controlador en MVC?

  • A) Validar que el formato de un texto sea correcto
  • B) Escuchar clics del usuario en la interfaz
  • C) Guardar los datos permanentemente en un archivo de texto
Respuesta: C (persistir datos es tarea del Modelo o de la capa de acceso a datos).

Patrones Subyacentes en MVC

MVC no es un solo patrón: es una orquesta de tres patrones clásicos en conjunto.

¿Dónde se han usado estos patrones previamente?

Patrón¿Qué resuelve?Ejemplo en JavaFX
Observer Notificar cambios a varios objetos sin acoplarlos. ObservableList + ListView
Cuando se agrega un elemento, la lista gráfica se refresca sola sin llamar a un método repintar().
Composite Tratar objetos individuales y compuestos de forma uniforme. El Árbol de Nodos FXML
Un BorderPane contiene VBox, que contiene Buttons. Todos heredan de Node.
Strategy Cambiar el comportamiento de un objeto en tiempo de ejecución. Los EventHandler (onAction)
El botón delega su estrategia de respuesta al método que se le asigne en el controlador.

Esta tabla conecta los conceptos abstractos con la experiencia cotidiana programando en JavaFX.

1. Observer

Suscripción y Notificación

El Modelo no conoce a la Vista. Cuando el chat recibe un mensaje, la lista emite un aviso y la interfaz gráfica se repinta automáticamente.

ObservableList<String>

2. Composite

Jerarquía Gráfica

La Vista trata contenedores y componentes de la misma forma. Todo elemento visual hereda de una clase base común, permitiendo tratarlos en grupo.

Parent > Node > Control

3. Strategy

Comportamiento Intercambiable

La Vista delega la respuesta a los eventos en diferentes estrategias (ActionHandlers). Se puede cambiar la forma de responder al clic dinámicamente.

EventHandler<ActionEvent>

Arquitectura vs Patrones de Diseño

¿Son lo mismo? La diferencia principal radica en la escala.

Arquitectura de Software

Nivel Macro (El plano de la ciudad)

  • Define la estructura global de todo el sistema. Cómo se organizan y comunican los grandes módulos.
  • Si hay un error en el diseño general, corregirlo requiere reescribir casi todo el código.
  • Ejemplos: N-Capas (N-Layers), N-Tiers, Microservicios, Cliente-Servidor.

Patrón de Diseño

Nivel Micro (La bisagra de la puerta)

  • Soluciona un problema técnico específico dentro de un módulo o clase puntual.
  • Solo afecta a una porción pequeña de código. Es fácil de cambiar o refactorizar.
  • Ejemplos: Observer, Strategy, Composite, Singleton (Catálogo GoF).

La Arquitectura es como los planos de una casa (dónde van la cocina y los cuartos). Si cambia la distribución, tiene que rehacer la casa.

Los Patrones son los mecanismos de las puertas (las bisagras). Si cambia una bisagra defectuosa, la casa no colapsa, solo se repara esa puerta.

Reflexión rápida:

¿Qué pasa si la arquitectura es de 3 capas pero se utiliza el patrón Singleton incorrectamente en una clase? ¿Afecta a toda la app o solo a esa parte?

Respuesta: Solo a esa parte, el sistema global sigue en pie.

N-Layers (Lógico) vs N-Tiers (Físico)

El concepto clave para escalar sistemas al mundo real.

Imagine que el Mini-Discord crece a 10,000 usuarios. Con 3 capas lógicas (Layers) ejecutándose en una sola computadora, el sistema colapsa. Se decide mover el acceso a base de datos a un servidor en la nube, y la lógica de validación a otro servidor.
Las capas de código son las mismas, pero ahora están distribuidas en distintos equipos físicos (Tiers).

1 Tier (El Monolito)

Vista + Lógica + Base de Datos
Todo en la misma máquina.

2 Tiers (Cliente-Servidor)

La Aplicación corre en la PC,
los datos en un Servidor Remoto.

3 Tiers (Empresarial)

Cliente (PC/Web) Servidor API Servidor Base de Datos.

Serialización y DTOs

Estrategias para preservar datos y trasladarlos de forma segura.

Persistencia: Serializable

Si se cierra la aplicación, los objetos en RAM desaparecen. Serializar es convertir un objeto vivo en bytes para almacenarlo en el disco duro.

Sin serializar: class User {
// Pérdida al cerrar
}
Con serializable: class User implements
Serializable {
// Permite guardado en disco
}

Transporte: DTO

Data Transfer Object. Es una clase plana (solo atributos, getters y setters) que se utiliza como "caja de transporte" para mover datos entre capas sin exponer lógica interna.

// DTO simple para enviar a la capa de datos
public class UserDTO {
  public String nombre;
  public String rol;
}

Si se hace una versión por consola, hay que duplicar validaciones.

Actual: Mini-Discord (MVC + N-Tier)

ChatViewController.java 
@FXML
private void handleSendMessage() {
    try {
        // 1. El controlador delega a la capa de negocio
        Message msg = chatService.processMessage(usr, txtMsg.getText());
        
        // 2. Observer: la lista observable actualiza la vista sola
        messages.add(msg.toString());
        txtMsg.clear();
    } catch (IllegalArgumentException e) {
        mostrarAlerta(e.getMessage()); // Regla del Service
    }
}

ChatService contiene todas las reglas aisladas.

Catálogo Completo: Patrones de Diseño (GoF)

Creacionales

  • Singleton: Instancia única.
  • Factory Method: Fábrica en métodos.
  • Abstract Factory: Familias de objetos.
  • Builder: Paso a paso.
  • Prototype: Clonación de objetos.

Estructurales

  • Adapter: Adaptador de interfaces.
  • Bridge: Desacopla abstracción e implementación.
  • Composite: Jerarquías tipo árbol.
  • Decorator: Añade funcionalidad dinámica.
  • Facade: Interfaz simplificada.
  • Flyweight: Ahorro de memoria compartida.
  • Proxy: Sustituto de acceso controlado.

Comportamiento

  • Observer: Suscripción y aviso.
  • Strategy: Algoritmos intercambiables.
  • Command: Petición encapsulada.
  • Iterator: Recorrido secuencial.
  • Mediator: Comunicación centralizada.
  • State: Cambia según estado interno.
  • Template Method: Esqueleto de algoritmo.

ChatViewController.java 
@FXML private ListView<String> messageListView;
@FXML private TextField messageInputField;

private final ChatService chatService = new ChatService();
private final User currentUser = new User("u1", "UsuarioLocal");

// ObservableList nativa: patrón Observer integrado en JavaFX
private final ObservableList<String> messages = FXCollections.observableArrayList();

@FXML
public void initialize() {
    messageListView.setItems(messages); // La vista queda suscrita al modelo observable
}

@FXML
private void handleSendMessage() {
    String text = messageInputField.getText();
    try {
        Message nuevo = chatService.processMessage(currentUser, text);
        messages.add(nuevo.toString()); // Dispara la notificación automática a la UI
        messageInputField.clear();
    } catch (IllegalArgumentException e) {
        System.out.println("Aviso: " + e.getMessage());
    }
}

Glosario de Términos Clave

  • MVC: Modelo-Vista-Controlador. Patrón arquitectónico que separa datos, interfaz y lógica de control.
  • DAO (Data Access Object): Objeto que encapsula el acceso a la fuente de datos (archivo, base de datos).
  • DTO (Data Transfer Object): Objeto simple que transporta datos entre capas sin exponer la lógica interna.
  • Serialización: Proceso de convertir un objeto en una secuencia de bytes para almacenarlo de forma persistente.
  • Observer: Patrón que permite que un objeto notifique a otros de forma desvinculada sobre cambios en su estado.
  • Strategy: Patrón que permite seleccionar un algoritmo o respuesta en tiempo de ejecución.
  • Composite: Patrón que trata objetos individuales y estructuras jerárquicas (árboles) de manera uniforme.
  • N-Layers: División lógica del código en paquetes según su responsabilidad dentro de un mismo programa.
  • N-Tiers: División física de la aplicación ejecutándose en diferentes equipos de cómputo en una red.
